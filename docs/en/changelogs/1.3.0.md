# Polhem 1.3.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.3.0.md)

This file holds the details behind the `[1.3.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version is a security fix: Polhem now runs on [Polhem.JsonRpc](https://github.com/polhem-dev/polhem-jsonrpc) 1.1
(1.1.1 or later), which binds each Encrypted payload to its method and its direction. **Its payload wire format is
incompatible with that of Polhem 1.2.0, so the server and every remote client must upgrade together.** Polhem's own
public .NET API changes only by the addition of `DefinitionNotFoundException`, so this ships in a minor version, the
third exception within 1.x after 1.1.0 and 1.2.0; the reasons are under
[Encrypted payloads are bound to their method and direction](#encrypted-payloads-are-bound-to-their-method-and-direction)
and in [ADR-050](../../../maintainers/adr/adr-050-jsonrpc-1-1-wire-break-in-1-3.md).

What each kind of application has to act on:

- **Servers**: [Encrypted payloads are bound to their method and direction](#encrypted-payloads-are-bound-to-their-method-and-direction),
  [Polhem.JsonRpc 1.1.1 is required](#polhemjsonrpc-111-is-required) and
  [A missing definition throws `DefinitionNotFoundException`](#a-missing-definition-throws-definitionnotfoundexception);
  with `RequireFrame` on, also
  [Guarded methods take only Encrypted remote calls under `RequireFrame`](#guarded-methods-take-only-encrypted-remote-calls-under-requireframe).
- **.NET clients** on `Polhem.Api.Client`: upgrade with the server; nothing in the calling code changes.
- **Browser and other JavaScript clients**: rebuild polhem-connector-js (see the first breaking change), and check
  [`RequireFrame`](#guarded-methods-take-only-encrypted-remote-calls-under-requireframe).
- **Clients in other languages**: implement the new binding, and see
  [A call with no value to bind is answered `-32602`](#a-call-with-no-value-to-bind-is-answered--32602).
- **Applications that extend the JSON-RPC layer** (filters, an `IPayloadEncryptor` of their own):
  [Polhem.JsonRpc 1.1.1 is required](#polhemjsonrpc-111-is-required).

## New features and changes

### `DefinitionNotFoundException`

A new `FileNotFoundException` in `Polhem.Definition.Storage` that names the definition type and its key. Where the
framework throws it, and what changes for existing code, is under
[A missing definition throws `DefinitionNotFoundException`](#a-missing-definition-throws-definitionnotfoundexception).
([#51](https://github.com/polhem-dev/polhem/pull/51))

### In-process calls are not checked for repeated sequence numbers

They never cross a network, so there is nothing to replay, and the local provider sends Plain outside debug mode,
which the rule under
[Guarded methods take only Encrypted remote calls under `RequireFrame`](#guarded-methods-take-only-encrypted-remote-calls-under-requireframe)
would otherwise refuse. Whether a call is local is still decided by the transport alone.
([#60](https://github.com/polhem-dev/polhem/pull/60))

### Fixes

- **Connecting checks the endpoint with the ping alone.** `ApiConnectValidator`, and through it `ClientInfo` in the UI
  heads, no longer sends an HTTP `HEAD` request before the ping. The endpoint accepts only POST, so every connect was
  answered with 405, which the browser head logged as an error. A host that cannot be reached is still reported as
  `Endpoint not reachable`. ([#50](https://github.com/polhem-dev/polhem/pull/50))

### Documentation

- The guide for migrating from Bee.NET moves out of the root README into
  [its own page](../guides/migrating-from-bee-net.md), and the README keeps a short pointer to it.
  ([#52](https://github.com/polhem-dev/polhem/pull/52))

## Breaking changes

### Encrypted payloads are bound to their method and direction

- **Affects:** every server and every remote client: .NET clients on `Polhem.Api.Client`, browser clients built from
  [polhem-connector-js](https://github.com/polhem-dev/polhem-connector-js), and clients in other languages that speak
  the payload.
- **Before:** the HMAC of an Encrypted payload covered its bytes and nothing else. Someone who captured an Encrypted
  request could send it to another method of the same session, for example to turn a read into a delete, and could
  send a result back as a request: the receiving end had no way to tell, because the bytes were genuine. A `null`
  result was a plain `null` whatever format the request was sent in, so a result could be swapped on the way for a
  plain one, which carries no HMAC at all.
- **Now:**
  - The HMAC also covers the direction of the payload and the JSON-RPC method of the call, so a payload only opens for
    the method and direction it was written for. `ApiConnector` seals each request with its method and opens the
    result with the same method; the server does the same through the payload filter.
  - A result is answered in the format its request was sent in, a `null` result included: when the request was
    Encoded or Encrypted, it is an envelope in the request's format with an empty body. `ApiConnector` reads the format
    it actually sent, after any downgrade from Encrypted to Encoded for a session without a key, and refuses a result
    in another format with `InvalidPayloadException`.
  - A result can still be swapped with another result of the same method, error responses are not authenticated, and
    replaying an unchanged call is a matter for frames.
  - There is no compatibility mode: a server that accepted both the bound and the unbound form would accept the
    unbound one from an attacker as well, which is exactly what the binding closes. A mismatched server and client,
    either way round, fail every Encrypted call, and the server answers each one with `-32603 Internal error`. Plain
    and Encoded calls carry no HMAC, so a mismatched pair may look healthy until its first Encrypted call.
- **Migrate:** upgrade the server and every remote client in the same window.
  1. **The server**: raise the Polhem packages to 1.3.0, and the `Polhem.JsonRpc.*` packages it references directly
     (see [Polhem.JsonRpc 1.1.1 is required](#polhemjsonrpc-111-is-required)).
  2. **.NET clients** on `Polhem.Api.Client`: raise the package to 1.3.0. `ApiConnector` binds its calls and reads
     results in the format it sent; nothing in the calling code changes.
  3. **Browser and other JavaScript clients**: rebuild polhem-connector-js from `main` at or after the commit that
     merges [polhem-dev/polhem-connector-js#11](https://github.com/polhem-dev/polhem-connector-js/pull/11), and
     reinstall it. It is not published to npm, and its package version does not change, so the commit is what tells an
     old build from a new one.
  4. **A client in another language** that speaks the payload: implement
     [ADR-003 of Polhem.JsonRpc](https://github.com/polhem-dev/polhem-jsonrpc/blob/main/maintainers/adr/adr-003-bind-method-into-payload-hmac.md).
     That repository's cross-language test vectors are the reference.
  5. **Clients installed on users' devices**, such as a desktop or mobile head, cannot always move in the same window.
     One way through is to keep a Polhem 1.2.0 server, with every `Polhem.JsonRpc.*` package it references pinned to
     1.0.0, on a separate endpoint for the clients that have not been updated, and retire it once they have. That
     server keeps the weakness described under **Before**, so open it only to the clients that need it, and retire it
     early.
- **Background:** [ADR-050](../../../maintainers/adr/adr-050-jsonrpc-1-1-wire-break-in-1-3.md) records the decisions
  and the alternatives; how the binding is computed, and what it leaves out, is in
  [ADR-003 of Polhem.JsonRpc](https://github.com/polhem-dev/polhem-jsonrpc/blob/main/maintainers/adr/adr-003-bind-method-into-payload-hmac.md).
  Semantic versioning asks for 2.0.0. Polhem's own public .NET API only gains `DefinitionNotFoundException`; nothing
  in the `PublicAPI.Shipped.txt` baselines is removed or changed, so an application that references only the Polhem
  packages compiles against 1.3.0 as it did against 1.2.0. The break is on the wire, and a version number does not
  change who can talk to whom: a 1.2.0 client cannot call a 1.3.0 server whatever the server's version is called, and
  polhem-connector-js has to be rebuilt either way. A minor version does carry one cost: a floating reference such as
  `1.*`, or a tool that merges minor updates on its own, can move a server to 1.3.0 without anyone deciding to, and its
  remote clients then fail; the changelog entry opens with the warning for that reason. Like 1.1.0 and 1.2.0, this
  exception has its own ADR. After publishing 1.3.0, the maintainer marks the Polhem 1.2.0 packages deprecated on
  nuget.org: Polhem 1.2.0 accepts any later Polhem.JsonRpc, and Polhem.JsonRpc 1.1 refuses to start under code
  compiled against 1.0 (from 1.1.1 with no way around it), so an application that updates its transitive packages
  under 1.2.0 ends up with a server that does not start. ([#60](https://github.com/polhem-dev/polhem/pull/60))

### Polhem.JsonRpc 1.1.1 is required

- **Affects:** servers, in particular hosts that serve the API over HTTP; applications that reference a
  `Polhem.JsonRpc.*` package directly; applications with code of their own compiled against `Polhem.JsonRpc.Server`
  1.0, such as a filter added through `AddJsonRpcServer`; applications with an `IPayloadEncryptor` of their own.
- **Before:** the packages depended on Polhem.JsonRpc `1.0.0` or later.
- **Now:** the packages depend on Polhem.JsonRpc `[1.1.1, 2.0.0)`, so NuGet does not resolve the 1.0 packages for
  Polhem's own dependencies, and a later major version waits until Polhem is built against it. 1.1.1 is the first
  version whose dispatcher refuses to start beside any assembly compiled against `Polhem.JsonRpc.Server` 1.0 that is
  loaded when it is created, naming it, with no exception: in it `JsonRpcServerOptions.AllowCodeCompiledAgainst10` has
  no effect, because code compiled against 1.0 that reads or sets the transport kind can take an HTTP call for an
  in-process one, and Polhem lets in-process calls past its access checks.
- **Migrate:**
  1. Raise every `Polhem.JsonRpc.*` package the application references directly to 1.1.1 or later. A direct reference
     left at 1.0.0, such as `Polhem.JsonRpc.Payload.Server` for a replay store of your own, fails the restore with
     NU1605, because the Polhem packages need 1.1.1.
  2. A host that serves the API over HTTP references `Polhem.JsonRpc.AspNetCore` itself. Version 1.0 of it was
     compiled against `Polhem.JsonRpc.Server` 1.0 and stops the dispatcher from starting:

     ```diff
     - <PackageReference Include="Polhem.Hosting" Version="1.2.0" />
     - <PackageReference Include="Polhem.JsonRpc.AspNetCore" Version="1.0.0" />
     + <PackageReference Include="Polhem.Hosting" Version="1.3.0" />
     + <PackageReference Include="Polhem.JsonRpc.AspNetCore" Version="1.1.1" />
     ```

  3. Recompile code of your own compiled against `Polhem.JsonRpc.Server` 1.0 against 1.1.1 or later.
     `AllowCodeCompiledAgainst10` cannot get past the startup error, so everything compiled against 1.0 has to be
     upgraded or recompiled.
  4. An `IPayloadEncryptor` of your own must implement the `Encrypt` and `Decrypt` overloads that take associated data,
     and authenticate that data. Until it implements them, every Encrypted call through it fails. An implementation
     that ignores the associated data accepts the 1.2.0 form and reopens both attacks described under
     [Encrypted payloads are bound to their method and direction](#encrypted-payloads-are-bound-to-their-method-and-direction).
  5. The rest of Polhem.JsonRpc's own changes are in
     [its changelog](https://github.com/polhem-dev/polhem-jsonrpc/blob/main/CHANGELOG.md).
- **Background:** [ADR-050](../../../maintainers/adr/adr-050-jsonrpc-1-1-wire-break-in-1-3.md)
  ([#60](https://github.com/polhem-dev/polhem/pull/60))

### Guarded methods take only Encrypted remote calls under `RequireFrame`

- **Affects:** servers that turn on `RequireFrame`, and their clients without a session key: a .NET browser
  (WebAssembly) head, and polhem-connector-js.
- **Before:** while the wire frame was required, a method that declares `ReplayProtection = UniqueSequence` accepted a
  remote Plain call without a sequence check, and checked an Encoded call against a sequence number anyone could forge,
  because only an Encrypted frame is covered by the HMAC.
- **Now:** with `RequireFrame` on, such a method refuses a remote Plain or Encoded call from a signed-in session with
  `-32602 Invalid params`, so a client of it needs a session key. The framework's own `Save`, `Delete`, `ExecFunc`,
  `EnterCompany` and `LeaveCompany` are such methods. A .NET browser (WebAssembly) head signs in without a session key,
  so its calls to them are downgraded to Encoded and refused. polhem-connector-js does not write frames yet, so under
  `RequireFrame` its Encoded and Encrypted calls were refused already, and its Plain calls to these methods are now
  refused too.
- **Migrate:** keep `RequireFrame` off for a deployment with such clients until they can hold a key and write frames.
- **Background:** [ADR-050](../../../maintainers/adr/adr-050-jsonrpc-1-1-wire-break-in-1-3.md)
  ([#60](https://github.com/polhem-dev/polhem/pull/60))

### A call with no value to bind is answered `-32602`

- **Affects:** clients that send a request with no `params`, or a payload envelope without a `value` or with a `null`
  one, and code that reads the error code of such a call.
- **Before:** the method ran with a `null` argument. Most framework methods checked for it with
  `ArgumentNullException`, which answered `-32099` with "The request is not valid.", and the others failed with
  `-32603 Internal error`.
- **Now:** such a request is answered `-32602 Invalid params` before the method runs. This is what the default binder
  of Polhem.JsonRpc answers. A request with `"params": null` is still refused with `-32600`, as JSON-RPC 2.0 asks.
- **Migrate:** send the parameter value, or expect `-32602` where `-32099` or `-32603` was handled.
  ([#60](https://github.com/polhem-dev/polhem/pull/60))

### A missing definition throws `DefinitionNotFoundException`

- **Affects:** code that catches `InvalidOperationException` from a database definition storage for a missing
  definition, code that compares the exact exception type, and remote callers that read the error code or message of
  a missing definition.
- **Before:** a missing definition in a file storage answered a remote caller with a generic `-32603` InternalError,
  and in a database storage with a fixed message; the database storage threw `InvalidOperationException`. The two
  disagreed, and neither told the caller what was missing.
- **Now:** a form schema, a table schema, the program registry or the database categories that the built-in file or
  database storage must hold but does not throws `DefinitionNotFoundException`, a `FileNotFoundException` that carries
  the definition type and the key. The `GetFormSchema` API throws it too when a storage of your own returns no form
  schema; a storage of your own is otherwise unchanged. A remote caller receives its message, such as
  `FormSchema 'Employee' not found.`, under the UserMessage code (`-32099`). The message names only the definition
  type and its key, never a path.
- **Migrate:** code that caught `InvalidOperationException` for a missing definition catches
  `DefinitionNotFoundException` (or `FileNotFoundException`) instead. Existing `catch (FileNotFoundException)` blocks
  still catch it; code that compares the exact type sees the subtype.
  ([#51](https://github.com/polhem-dev/polhem/pull/51))
