# Polhem 1.3.0 — Detailed Release Notes

[繁體中文](../../zh-TW/changelogs/1.3.0.md)

This file is the detailed companion to the `[1.3.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). The changelog lists
each change in one line; this file keeps the reasons and the background, and also lists changes to how the repository
is maintained, which the changelog leaves out.

> Polhem now runs on [Polhem.JsonRpc](https://github.com/polhem-dev/polhem-jsonrpc) 1.1 (1.1.1 or later), whose
> payload wire format is incompatible with that of Polhem 1.2.0. **The server and every remote client must upgrade
> together.** The change closes a weakness of 1.2.0, described under "Why the wire changed". The decisions and the
> alternatives are recorded in [ADR-050](../../../maintainers/adr/adr-050-jsonrpc-1-1-wire-break-in-1-3.md).

## Why the wire changed

**This is a security fix.** Up to 1.2.0, the HMAC of an Encrypted payload covered its bytes and nothing else. Someone
who captured an encrypted request could therefore send it to another method of the same session, for example turn a
read into a delete, and could send a result back as a request: the receiving end had no way to tell, because the
bytes were genuine. Polhem.JsonRpc 1.1.0 closes both. The HMAC now also covers the direction of the payload and the
JSON-RPC method of the call, so a payload only opens for the method and direction it was written for. A result can
still be swapped with another result of the same method, error responses are not authenticated, and replaying an
unchanged call is a matter for frames. How the binding is computed, and what it leaves out, is recorded in
[ADR-003 of Polhem.JsonRpc](https://github.com/polhem-dev/polhem-jsonrpc/blob/main/maintainers/adr/adr-003-bind-method-into-payload-hmac.md).

The same release makes a result answer in the format of its request, a `null` result included, and makes a reader
refuse a result in another format. Otherwise a result could be swapped on the way for a plain one, which carries no
HMAC at all.

Neither has a compatibility mode. A server that accepted both the bound and the unbound form would accept the unbound
one from an attacker as well, which is exactly what the binding closes.

## Why a minor version

Semantic versioning asks for 2.0.0. Polhem's own public .NET API only gains `DefinitionNotFoundException` in this
release; nothing in the `PublicAPI.Shipped.txt` baselines is removed or changed, so an application that references
only the Polhem packages compiles against 1.3.0 as it did against 1.2.0. The break is on the wire, and a version number
does not change who can talk to whom: a 1.2.0 client cannot call a 1.3.0 server whatever the server's version is
called, and polhem-connector-js has to be rebuilt either way. A minor version does carry one cost: a floating
reference such as `1.*`, or a tool that merges minor updates on its own, can move a server to 1.3.0 without anyone
deciding to, and its remote clients then fail. This note and the changelog entry open with the warning for that
reason. This is the third exception to semantic versioning within 1.x, after 1.1.0 and 1.2.0, and like them it has
its own ADR.

After publishing 1.3.0, the maintainer marks the Polhem 1.2.0 packages deprecated on nuget.org. Polhem 1.2.0 accepts
any later Polhem.JsonRpc, and Polhem.JsonRpc 1.1 refuses to start under code compiled against 1.0, so an application
that updates its transitive packages under 1.2.0 ends up with a server that does not start.

## How to upgrade

**Upgrade the server and every remote client in the same window.** A mismatched pair, either way round, fails every
Encrypted call, and the server answers each one with `-32603 Internal error`. Plain and Encoded calls carry no HMAC, so
a mismatched pair may look healthy until its first Encrypted call.

- **The server**: raise the Polhem packages to 1.3.0, and every `Polhem.JsonRpc.*` package the application references
  directly to 1.1.1 or later. A host that serves the API over HTTP references `Polhem.JsonRpc.AspNetCore` itself;
  version 1.0 of it was compiled against `Polhem.JsonRpc.Server` 1.0, and the 1.1 dispatcher refuses to start next to
  such an assembly, naming it. A direct reference left at 1.0.0, such as `Polhem.JsonRpc.Payload.Server` for a replay
  store of your own, also fails the restore with NU1605, because the Polhem packages need 1.1.1.
- **Do not set `JsonRpcServerOptions.AllowCodeCompiledAgainst10` to get past that startup error.** Code compiled
  against 1.0 that reads or sets the transport kind can take an HTTP call for an in-process one, and Polhem lets
  in-process calls past its access checks. From 1.1.1 the option no longer covers the Polhem.JsonRpc packages at all,
  but it still covers your own code.
- **.NET clients** on `Polhem.Api.Client`: raise the package to 1.3.0. `ApiConnector` binds its calls and reads
  results in the format it sent; nothing in the calling code changes.
- **Browser and other JavaScript clients**: rebuild polhem-connector-js from `main` at or after the commit that merges
  [polhem-dev/polhem-connector-js#11](https://github.com/polhem-dev/polhem-connector-js/pull/11), and reinstall it. It
  is not published to npm, and its package version does not change, so the commit is what tells an old build from a
  new one.
- **A client in another language** that speaks the payload: implement ADR-003 of Polhem.JsonRpc. That repository's
  cross-language test vectors are the reference.
- **If you turn on `RequireFrame`**: the framework's own `Save`, `Delete`, `ExecFunc`, `EnterCompany` and
  `LeaveCompany` declare `ReplayProtection = UniqueSequence`, and now take only Encrypted remote calls. A .NET browser
  (WebAssembly) head signs in without a session key, so its calls to them are downgraded to Encoded and refused with
  `-32602`. polhem-connector-js does not write frames yet, so under `RequireFrame` its Encoded and Encrypted calls
  were refused already, and its Plain calls to these methods are now refused too. Keep `RequireFrame` off for a
  deployment with such clients until they can hold a key and write frames.

Clients installed on users' devices, such as a desktop or mobile head, cannot always move in the same window. One way
through is to keep a Polhem 1.2.0 server, with every `Polhem.JsonRpc.*` package it references pinned to 1.0.0, on a
separate endpoint for the clients that have not been updated, and retire it once they have.

These only apply to an application that extends the JSON-RPC layer itself:

- Code of your own compiled against `Polhem.JsonRpc.Server` 1.0, such as a filter added through `AddJsonRpcServer`,
  must be recompiled against 1.1.1 or later.
- An `IPayloadEncryptor` of your own must implement the `Encrypt` and `Decrypt` overloads that take associated data,
  so that the authentication covers that data. Until it implements them, every Encrypted call through it fails. An
  implementation that ignores the associated data accepts the 1.2.0 form and reopens both attacks described above.

The rest of Polhem.JsonRpc's own changes are in [its changelog](https://github.com/polhem-dev/polhem-jsonrpc/blob/main/CHANGELOG.md).

## Changed behaviour

- **Encrypted calls are bound to their method.** `ApiConnector` seals each request with its method and opens the
  result with the same method; the server does the same through the payload filter. See "Why the wire changed".
  ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **Results answer in the request's format.** A `null` result is no longer a plain `null` when the request was Encoded
  or Encrypted; it is an envelope in the request's format with an empty body. `ApiConnector` reads the format it
  actually sent, after any downgrade from Encrypted to Encoded for a session without a key, and refuses a result in
  another format with `InvalidPayloadException`. ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **Guarded methods take only Encrypted remote calls while the frame is required.** With `RequireFrame` on, a method
  that declares `ReplayProtection = UniqueSequence` refuses a remote Plain or Encoded call from a signed-in session with
  `-32602 Invalid params`. A Plain call used to be accepted without a sequence check, and an Encoded call was checked
  against a sequence number anyone could forge, because only an Encrypted frame is covered by the HMAC. A client of
  such a method therefore needs a session key; see "If you turn on `RequireFrame`" above for the framework methods and
  clients this concerns.
  ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **In-process calls are not checked for repeated sequence numbers.** They never cross a network, so there is nothing
  to replay, and the local provider sends Plain outside debug mode, which the rule above would otherwise refuse.
  Whether a call is local is still decided by the transport alone. ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **A call with no value to bind is `-32602`.** A request with no `params`, or a payload envelope without a `value` or
  with a `null` one, is answered `-32602 Invalid params` before the method runs. Before, the method ran with a `null`
  argument: most framework methods answered `-32099` with "The request is not valid.", and the others failed with
  `-32603 Internal error`. This is what the default binder of Polhem.JsonRpc answers. A request with `"params": null`
  is still refused with `-32600`, as JSON-RPC 2.0 asks. ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **Dependency range.** The packages depend on Polhem.JsonRpc `[1.1.1, 2.0.0)` instead of `1.0.0` or later, so NuGet
  does not resolve the 1.0 packages for Polhem's own dependencies, and a later major version waits until Polhem is
  built against it. A package the application references directly is its own to raise (see "How to upgrade"). 1.1.1
  is the minimum because it is the first version whose dispatcher refuses to start beside a Polhem.JsonRpc package
  compiled against 1.0, whatever `AllowCodeCompiledAgainst10` is set to.
  ([#60](https://github.com/polhem-dev/polhem/pull/60))
- **A missing definition is a user message.** A form schema, a table schema, the program registry or the database
  categories that the built-in file or database storage must hold but does not now throw
  `DefinitionNotFoundException`, a `FileNotFoundException` that carries the definition type and the key. The
  `GetFormSchema` API throws it too when a storage of your own returns no form schema; a storage of your own is
  otherwise unchanged. A remote caller receives its message, such as `FormSchema 'Employee' not found.`, under the
  UserMessage code (-32099). Before, a file storage answered a generic `-32603` and a database storage a fixed message,
  so the two disagreed and neither told the caller what was missing. The message names only the definition type and
  its key, never a path. Existing `catch (FileNotFoundException)` blocks still catch it; code that compares the exact
  type sees the subtype. A database storage threw `InvalidOperationException` before, so code that caught that type
  for a missing definition must catch `DefinitionNotFoundException` (or `FileNotFoundException`) instead.
  ([#51](https://github.com/polhem-dev/polhem/pull/51))
- **Connecting checks the endpoint with the ping alone.** `ApiConnectValidator`, and through it `ClientInfo` in the UI
  heads, no longer sends an HTTP `HEAD` request before the ping. The endpoint accepts only POST, so every connect was
  answered with 405, which the browser head logged as an error. A host that cannot be reached is still reported as
  `Endpoint not reachable`. ([#50](https://github.com/polhem-dev/polhem/pull/50))

## Repository

These change how the repository is maintained, not the packages:

- A pull request that changes only Markdown files skips the build steps of the required `build` check.
  ([#53](https://github.com/polhem-dev/polhem/pull/53))
- Contributors work from a fork and the maintainer reviews and merges their pull requests. `CONTRIBUTING.md`, the
  branch protection notes and the agent guidance point to the polhem-dev organization's
  [shared contributing guide](https://github.com/polhem-dev/.github/blob/main/CONTRIBUTING.md) instead of keeping their
  own copies. ([#55](https://github.com/polhem-dev/polhem/pull/55), [#56](https://github.com/polhem-dev/polhem/pull/56),
