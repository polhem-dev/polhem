# Polhem 1.2.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.2.0.md)

This file holds the details behind the `[1.2.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). JSON-RPC now runs on
the [`Polhem.JsonRpc`](https://github.com/polhem-dev/polhem-jsonrpc) packages, and the payload envelope, its encryption
and its replay frame on their optional payload packages. `Polhem.Api.AspNetCore` and `ApiServiceOptions` are removed,
which breaks hosts in a minor version: a second exception to semantic versioning within 1.x, after the one in 1.1.0.
On the wire, the parameters and the result envelope are the same bytes as in 1.1.0 and the wire fixtures did not
change, but the internal error code and the `method` member of responses are aligned with JSON-RPC 2.0, so a non-.NET
client has to move with the server: a [polhem-connector-js](https://github.com/polhem-dev/polhem-connector-js) client
needs the release that targets 1.2.0. The decisions, the alternatives and the full migration steps are recorded in
[ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md).

What each kind of application has to act on:

- **Hosts that serve the API over HTTP:** [The `Polhem.Api.AspNetCore` package is removed](#the-polhemapiaspnetcore-package-is-removed)
  and [Rejected credentials are answered with a JSON-RPC error](#rejected-credentials-are-answered-with-a-json-rpc-error).
- **Every host:** [`ApiServiceOptions` and the payload types are removed](#apiserviceoptions-and-the-payload-types-are-removed),
  [Log categories follow the types that write them](#log-categories-follow-the-types-that-write-them), and, for a host
  that also calls the API in-process, [In-process calls serialize their parameters](#in-process-calls-serialize-their-parameters).
- **.NET clients:** [`IJsonRpcProvider` and the JSON-RPC message types are removed](#ijsonrpcprovider-and-the-json-rpc-message-types-are-removed),
  the client side of [`ApiServiceOptions` and the payload types are removed](#apiserviceoptions-and-the-payload-types-are-removed),
  and [Rejected credentials are answered with a JSON-RPC error](#rejected-credentials-are-answered-with-a-json-rpc-error).
- **Non-.NET clients:** [Error responses follow JSON-RPC 2.0](#error-responses-follow-json-rpc-20).

## New features and changes

### JSON-RPC runs on the `Polhem.JsonRpc` packages

Up to 1.1.0, Polhem carried its own JSON-RPC 2.0 implementation: the executor and its message types in
`Polhem.Api.Core`, a controller in `Polhem.Api.AspNetCore`, and two client providers in `Polhem.Api.Client`. None of
that was specific to Polhem. What is specific sits on top of it: API key and access token checks, method-level access
control, the error contract, the anomaly records, and the session key and wire types behind the payload envelope.

The protocol half is now maintained as its own packages, which know nothing about Polhem and can be used without it.
Polhem attaches its own behaviour through their extension points, in `Polhem.Api.Core.Dispatch`. The payload
envelope, its encryption and its replay frame followed for the same reason: they are a protocol of their own, which
polhem-connector-js also speaks, so they now live in `Polhem.JsonRpc.Payload` and `Polhem.JsonRpc.Payload.Server`.

ADR-049 also names the **framework pipeline types**: public types that exist only for `Polhem.*` packages to
cooperate, such as everything in `Polhem.Api.Core.Dispatch`. Changes to them are not counted as breaking, so an
application should not build on them.

### `AddPolhemApiKeyGateCheck()`

`AddPolhemApiKeyGateCheck()` in `Polhem.Hosting` writes the startup log while no API key has been issued, for hosts
that serve the API over HTTP. It takes over the startup check `UsePolhemFramework()` ran, and is opt-in because an
in-process host has no HTTP endpoint for an API key to guard. ([#46](https://github.com/polhem-dev/polhem/pull/46))

### Payload options built the framework's way

`AddPolhemPayload()` in `Polhem.Hosting` registers the payload options on a server, `ApiClientInfo.PayloadOptions` in
`Polhem.Api.Client` holds them on a .NET client, and `PolhemPayload` in `Polhem.Api.Core` builds them the framework's
way. ([#47](https://github.com/polhem-dev/polhem/pull/47))

### Samples

`QuickStart.Server`, the Northwind server and the load test host serve the API with `MapJsonRpc("/api")`, and register
the payload options with `AddPolhemPayload()`. They show the upgrade below on a working host.
([#46](https://github.com/polhem-dev/polhem/pull/46), [#47](https://github.com/polhem-dev/polhem/pull/47))

## Breaking changes

### The `Polhem.Api.AspNetCore` package is removed

- **Affects:** hosts that serve the API over HTTP.
- **Before:** a host referenced `Polhem.Api.AspNetCore`, derived a controller from `ApiServiceController`, and called
  `UsePolhemFramework()`.
- **Now:** the package is removed, with `ApiServiceController` and `UsePolhemFramework()`. A host serves the API with
  `Polhem.JsonRpc.AspNetCore`: `AddJsonRpcServer()` and `MapJsonRpc("/api")`. The startup check `UsePolhemFramework()`
  ran moves to `AddPolhemApiKeyGateCheck()`. ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:**
  1. Replace the package reference:

     ```diff
     - <PackageReference Include="Polhem.Api.AspNetCore" Version="1.1.0" />
     + <PackageReference Include="Polhem.JsonRpc.AspNetCore" Version="1.0.0" />
     ```

  2. Replace the controller setup:

     ```diff
       builder.Services.AddPolhemFramework(configuration, paths);
     - builder.Services.AddControllers();
     + builder.Services.AddJsonRpcServer();
     + builder.Services.AddPolhemApiKeyGateCheck();
       var app = builder.Build();
     - app.UsePolhemFramework();
     - app.MapControllers();
     + app.MapJsonRpc("/api");
     ```

  3. Delete the controller derived from `ApiServiceController`. A check that overrode one of its members becomes a
     filter, added with `AddJsonRpcServer(options => options.Filters.Add(...))`.
- **Background:** Moving the protocol left `ApiServiceController` with nothing to do but call the endpoint. Keeping it
  would mean two ways to host the API, and every later change would have to keep them in step. See
  [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md).

### `ApiServiceOptions` and the payload types are removed

- **Affects:** every host; .NET clients that set payload options or catch `ReplayRejectedException`; servers with a
  custom `IApiAuthorizationValidator`; code that uses the payload codec, compressor, encryptor or replay store types.
- **Before:** `ApiServiceOptions` configured the payload, and `Polhem.Api.Core` held the payload types: the
  transformer, serializer, compressor and encryptor interfaces and their implementations, `ApiPayloadOptionsFactory`,
  the envelope types (`ApiPayload`, `JsonRpcParams`, `JsonRpcResult`, `ApiPayloadConverter`), `ApiPayloadFrame`,
  `IReplayWindowStore`, `MemoryReplayWindowStore` and `ReplayRejectedException`.
- **Now:** these are removed. Their replacements are in `Polhem.JsonRpc.Payload`: codecs, the replay store and the
  frame settings move to the package's `PayloadOptions`. A server registers the payload options with
  `AddPolhemPayload()`, and a .NET client holds them in `ApiClientInfo.PayloadOptions`.
  ([#47](https://github.com/polhem-dev/polhem/pull/47))
- **Migrate:**
  1. Every host replaces its `ApiServiceOptions` calls:

     ```diff
     - ApiServiceOptions.Initialize(settings.CommonConfiguration.ApiPayloadOptions, settings.CommonConfiguration.IsDebugMode);
     - ApiServiceOptions.RequireWireFrame = true;
     + builder.Services.AddPolhemPayload(settings.CommonConfiguration.ApiPayloadOptions, settings.CommonConfiguration.IsDebugMode,
     +     options => options.RequireFrame = true);
     ```

  2. A .NET client sets `ApiClientInfo.PayloadOptions.RequireFrame` to match the server.
  3. Update the members that moved:

     | Before | Now |
     |--------|-----|
     | `ApiServiceOptions.AuthorizationValidator` | `IApiAuthorizationValidator` resolved from the service collection; register your own to replace the default |
     | `MessagePackPayloadSerializer` | `MessagePackPayloadCodec`, which implements the package's `IPayloadCodec` |
     | `ReplayRejectedException` (`Polhem.Api.Core`) | `Polhem.JsonRpc.Payload.ReplayRejectedException`, the exception a client catches for a replayed call |
     | the other payload, envelope, frame and replay types | `Polhem.JsonRpc.Payload` and its `PayloadOptions` |

  4. The rest of the migration, including the steps most hosts do not need (custom codecs, a shared replay store, a
     host that also calls the API in-process), is in decisions 3 and 5 of
     [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md).
- **Background:** `ApiServiceOptions` had become a second configuration surface that would have had to mirror the
  payload package's options. Keeping it would mean two ways to configure the payload, and every later change would
  have to keep them in step. [ADR-048](../../../maintainers/adr/adr-048-rename-base-to-core-in-1-1.md) said the rename
  in 1.1.0 was the only exception to semantic versioning in 1.x;
  [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md) is a second one, and it says further breaking
  changes within 1.x need an ADR of their own.

### `IJsonRpcProvider` and the JSON-RPC message types are removed

- **Affects:** .NET client code that uses `ApiConnector.Provider` or implements `IJsonRpcProvider`, and code that uses
  `JsonRpcExecutor` or the message types of `Polhem.Api.Core.JsonRpc`.
- **Before:** `RemoteApiProvider` and `LocalApiProvider` implemented `IJsonRpcProvider`, and `Polhem.Api.Core.JsonRpc`
  held `JsonRpcExecutor` and the message types `JsonRpcRequest`, `JsonRpcResponse` and `JsonRpcError`.
- **Now:** `IJsonRpcProvider`, `JsonRpcExecutor` and the message types are removed. `RemoteApiProvider` and
  `LocalApiProvider` implement the package's `IJsonRpcTransport`, and `ApiConnector.Provider` has that type.
  ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:** use `IJsonRpcTransport` in place of `IJsonRpcProvider`, and the `Polhem.JsonRpc` packages' types in
  place of the removed executor and message types.
- **Background:** [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md)

### Error responses follow JSON-RPC 2.0

- **Affects:** clients that compare against -32000, read the `method` member of a response, or handle a malformed or
  unknown method name; code that reads `JsonRpcErrorCode.InternalError`.
- **Before:** an internal error was answered with -32000, and a response echoed the method name in a `method` member.
  A malformed method name was answered with `UserMessage`.
- **Now:** the parameters and the result envelope are the same bytes as in 1.1.0. Two things that were Polhem's own are
  aligned with JSON-RPC 2.0: an internal error is answered with -32603, the code the specification defines for it, and
  `JsonRpcErrorCode.InternalError` has that value; a response no longer carries a `method` member. A malformed method
  name is answered with `MethodNotFound` (-32601), as the specification asks. An action that does not exist is answered
  by the dispatcher itself with a fixed message, also in debug mode, and leaves no anomaly record.
  ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:** a client that compares against -32000 or reads `method` moves with the server; for polhem-connector-js
  that is the release that targets 1.2.0.
- **Background:** [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md)

### Rejected credentials are answered with a JSON-RPC error

- **Affects:** clients that handle HTTP 401, and .NET code that catches `HttpRequestException` for a rejected API key
  or access token.
- **Before:** a rejected API key or `Authorization` header was answered with HTTP 401.
- **Now:** it is answered with HTTP 200 and a JSON-RPC error. The check runs before the business object is created,
  inside the JSON-RPC pipeline, so its failure is reported like every other failure, and the .NET client throws the
  error contract's exception instead of `HttpRequestException`. ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:** handle the rejection as a JSON-RPC error: in .NET, catch the error contract's exception.

### In-process calls serialize their parameters

- **Affects:** hosts that call the API in-process and rely on the server receiving the caller's objects.
- **Before:** an in-process call handed its parameter objects to the server as they were.
- **Now:** in-process calls serialize their parameters like remote calls, so the server never holds the caller's
  objects. A filter value in a `Plain` body arrives as text, as it always did over HTTP.
  ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:** treat parameters on the server the same way for in-process and remote calls.

### A payload envelope with an unknown format is refused

- **Affects:** clients that send a payload envelope whose `format` is not 0, 1 or 2.
- **Before:** such an envelope was accepted and failed further on.
- **Now:** it is refused as invalid parameters. ([#47](https://github.com/polhem-dev/polhem/pull/47))
- **Migrate:** send `format` 0, 1 or 2.

### Log categories follow the types that write them

- **Affects:** logging configuration keyed on the old categories.
- **Before:** masked failures and the API key startup check logged under other categories.
- **Now:** masked failures log under `Polhem.Api.Core.Dispatch.PolhemExceptionMapper`, and the API key startup check
  under `Polhem.Hosting.ApiKeys.ApiKeyGateWarningService`. ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **Migrate:** update a log filter on the old categories to the new names.
