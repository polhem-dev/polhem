# Polhem 1.5.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.5.0.md)

This file holds the details behind the `[1.5.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version makes form reads return every numeric and boolean column in the type its FormSchema field declares, on
every provider, and adds the option that does it, `DbCommandSpec.ColumnTypes`. It adds that one public member and
removes nothing from the `PublicAPI.Shipped.txt` baselines. The wire format is the one of 1.4.0: the server now sends
the cell values its column types already announced, so a 1.4.0 client and a 1.5.0 server, or the other way round, talk
to each other, and servers and clients do not have to upgrade together.

## New features and changes

### `DbCommandSpec.ColumnTypes`

Names the CLR type to build each named result column with, in place of the type the provider reports. When it is set,
`DbAccess` creates those columns before reading any row, on both the synchronous and the asynchronous path, so each
value is converted into the declared type as it loads. The option is public, so hand-written SQL can use it too:

```csharp
var spec = new DbCommandSpec(DbCommandKind.DataTable, "SELECT seq, flag, amount FROM my_table");
spec.ColumnTypes["flag"] = typeof(bool);
spec.ColumnTypes["amount"] = typeof(decimal);
var table = dbAccess.Execute(spec).Table;
```

- It applies to `DataTable` commands only; setting it on another kind throws when the command runs, as `DateColumns`
  does.
- Names match case-insensitively, and a name the result set does not contain is ignored, because a caller declaring
  from a schema declares every field while a query may select some of them.
- Columns keep their position in the result set.
- A value that does not fit its declared type throws. A value keeps the precision of the type the provider read it as:
  a SQLite `REAL` arrives as a `double`.
- When it is set, the table is built from the result set alone: a column name that appears twice throws instead of
  being renamed, and no key, nullability or length information is read into the columns.

### Fixes

#### Form reads return the declared types

`GetList`, `GetData` and the reads by row id now return every numeric and boolean column in the CLR type its FormSchema
field declares, on every provider. ([#99](https://github.com/polhem-dev/polhem/issues/99),
[#100](https://github.com/polhem-dev/polhem/pull/100))

**What went wrong.** SQLite has no column types, only a storage class per value, and Microsoft.Data.Sqlite gives each
result column the type of its first row. A `NUMERIC` column whose first row held a whole number became an `Int64`
column, and every later value was converted into it: `100.5` read as `100`, with no error anywhere. Boolean, Short,
Integer and AutoIncrement columns read as `Int64`. MySQL read AutoIncrement as `long`, and Oracle as `decimal`.

The JSON codec writes a `long` or `decimal` cell as a string, to keep JavaScript's precision, and writes the column type
the FormSchema declares. A Boolean column therefore went out as `"type":"Boolean"` with the cells `"1"` and `"0"`, and
polhem-connector-js, which decodes each cell by its column type, refused the table. A `Save` was hit after the fact:
the row was written, then the returned data set failed to decode, so a caller that took the error for a failed save and
retried wrote the row twice.

**Why converting after the read was not enough.** The form repository already replaced columns whose provider type is
only a storage form of the declared one (an Oracle `RAW(16)` Guid, a SQLite date stored as text). A `Boolean ⇐ long`
case there would have fixed the symptom that was reported, but by then the decimal's fractional part is gone.

**The fix.** The form repository declares every Boolean, Short, Integer, AutoIncrement, Long, Decimal and Currency
field through [`DbCommandSpec.ColumnTypes`](#dbcommandspeccolumntypes), so the columns carry the declared type before
the first row loads.

**Limits.**

- **AutoIncrement stays `int`.** SQL Server and PostgreSQL create it as a 32-bit identity, and both codecs rebuild it as
  `int`. MySQL (`BIGINT`), Oracle (`NUMBER(19)`) and SQLite store 64 bits, so a value above `int.MaxValue` fails a form
  read, in process as it already did on the wire.
- **A SQLite Guid column still reads as `string`.** Converting it would round-trip the stored text through `Guid`, and a
  GUID that SQLite's column default stored without hyphens would no longer match when written back.
- **SQLite rounds long decimals when it stores them.** A value with more than about 15 significant digits is rounded as
  it is stored under `NUMERIC` affinity; nothing on the read side can restore it.
- **Hand-written SQL is not covered.** A query that does not go through the form repository reads columns typed by the
  provider, unless it declares `ColumnTypes` itself.

## Breaking changes

### In-process form reads return the declared column types

- **Affects:** code that reads form tables in process (a business object, a Local provider) on SQLite, MySQL or
  Oracle, and applications whose MySQL, Oracle or SQLite AutoIncrement values exceed `int.MaxValue`.
- **Before:** those reads returned the provider's own types: `long` for a Boolean, Short, Integer or AutoIncrement cell
  on SQLite, `long` for AutoIncrement on MySQL, `decimal` for AutoIncrement on Oracle, and a SQLite decimal column
  could come back as `long`. An AutoIncrement value above `int.MaxValue` read in process as a 64-bit value.
- **Now:** they return the type the FormSchema field declares, as SQL Server and PostgreSQL already did, and as every
  remote call already did, because both codecs rebuild a column from its declared type on the receiving side. An
  AutoIncrement value above `int.MaxValue` fails the form read in process, as it already failed on the wire. Why this
  changed is under [Form reads return the declared types](#form-reads-return-the-declared-types).
- **Migrate:** remove casts and conversions that expected the provider's types, such as reading a Boolean cell as
  `long` or an Oracle AutoIncrement cell as `decimal`, and read the declared type.
