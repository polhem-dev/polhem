# Polhem 1.0.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.0.0.md)

This file holds the details behind the `[1.0.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

Polhem continues [Bee.NET](https://github.com/jeff377/bee-library) under a new name. Polhem 1.0.0 is Bee.NET 4.33.0,
the last Bee.NET release, renamed, plus the changes of a pre-release review, so "breaking" below means breaking
relative to Bee.NET 4.33.0. Every name that contained `Bee` was renamed and there is no compatibility layer. The wire
is not compatible with Bee.NET: a Bee.NET client and a Polhem server, or the other way round, cannot talk to each
other, so clients and servers are upgraded together. The step-by-step guide is
[Migrating from Bee.NET](../guides/migrating-from-bee-net.md).

## New features and changes

### A new name and a new repository

Polhem is the framework formerly published as Bee.NET, moved to the `polhem-dev` organization so that it can be
maintained by more than one person. It starts as a new repository, `polhem-dev/polhem`, without the git history; the
history before the move stays in `jeff377/bee-library`, which is frozen. The `Bee.*` packages are not developed
further, and the new package IDs start their own version line at 1.0.0.

The authors and the copyright holder are Polhem contributors, the project and repository URLs point to
`polhem-dev/polhem`, and the packages carry the new Polhem icon. The license is still MIT. `Polhem.Cli` shares the same
metadata, and ships a README and a symbol package. ([#3](https://github.com/polhem-dev/polhem/pull/3))

Before 1.0.0 the framework went through a full review: security, the wire contract, concurrency, the public API,
tests, internationalization, performance and trimming. Its fixes landed before the first release, so the version
number did not have to wait for a 2.0.0 to correct the public API. The rules the public API now follows are recorded
in [ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md).

### Security hardening

The changes that make the server refuse requests it used to accept are under
[The server checks requests more strictly](#the-server-checks-requests-more-strictly); the ones that end sessions and
old password hashes are under
[Sessions end and old password hashes no longer verify](#sessions-end-and-old-password-hashes-no-longer-verify). The
rest:

- **Passwords.** New hashes use PBKDF2-SHA256 with 600,000 iterations (the OWASP recommendation at the time) in a
  format that records its own iteration count, and a hash with fewer iterations is replaced at the next successful
  sign-in (`PasswordHasher.NeedsRehash`). An unknown user name runs a decoy hash, so the time a failed sign-in takes
  does not reveal whether the account exists, and the login attempt tracker stays bounded.
  ([#5](https://github.com/polhem-dev/polhem/pull/5))
- **Audit rules and ProgId casing.** A caller cannot slip past an audit rule by changing the casing of a ProgId. A
  progId resolves to its form whatever casing the caller uses, so the audit rule must too. Business objects for
  reserved and registered progIds are created with the casing `ProgramSettings` declares
  ([#4](https://github.com/polhem-dev/polhem/pull/4)). That left the forms the registry does not list: they keep the
  caller's casing, and an exact rule lookup let a caller reach such a form under another casing and fall back to the
  deployment default. `CompanyAuditRules` now looks rules up case-insensitively (of two rules that differ only in case,
  the first is kept), and audit records carry the FormSchema's ProgId spelling (see
  [Audit and log records change](#audit-and-log-records-change)). ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Server paths in errors.** A missing definition file used to be reported with its full path. A debug-mode host
  passes the message of an unmapped exception to the remote caller, and a FormSchema is reached by the progId a request
  names, so any caller could learn the server's directory layout. `FileUtilities.EnsureFileExists` names only the file;
  the full path stays on `FileNotFoundException.FileName` for the server log.
  ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Keys on disk.** The master key file and the client's `apikey.txt` are written with owner-only permissions, and a
  warning is logged when `DatabaseSettings` holds passwords but no `ConfigEncryptionKey` protects them.
  ([#5](https://github.com/polhem-dev/polhem/pull/5))
- **DDL and connection strings.** SQL Server string defaults are escaped, and connection string placeholders are
  filled through `DbConnectionStringBuilder` (`ConnectionStringTemplate`).
  ([#4](https://github.com/polhem-dev/polhem/pull/4))

### Localization

English is the base language of the built-in text, with shipped `zh-TW` translations; what that changes for an
existing application is under [English is the base language](#english-is-the-base-language). The new members are
`LanguageFallback`, `MenuLocalizer`, `FrameworkLanguageService`, `PolhemMessages`, `PolhemUIText` and
`ILocalizableMessage`, and English defaults with `zh-TW` translations for the Avalonia and Blazor UI text. Framework
messages meant for end users are thrown as `UserMessageException` with a key and arguments. `FormView`, `ListView` and
`LookupDialog` localize definitions through `ClientInfo.DefinitionLoader` by default.
([#15](https://github.com/polhem-dev/polhem/pull/15), [#22](https://github.com/polhem-dev/polhem/pull/22))

### A date-and-time editor, and list-item text in lists

`ControlType.DateTimeEdit` edits a `DateTime` field: the Avalonia `DateTimeEdit` editor is a text box that shows and
parses the date and time in the user's culture, and Blazor uses a `datetime-local` input. `DateEdit` stays for `Date`
fields. Lists show the list-item text of a drop-down field through `FormValueBinding.TryGetListItemText`, and
`GridControl.Bind` gains an overload that takes the `FormTable`, as does `DynamicGrid.FormTable`. Which layouts get the
new editor is under [Generated layouts use other editors](#generated-layouts-use-other-editors).
([#33](https://github.com/polhem-dev/polhem/pull/33))

### Configuration and startup

- **Components.** `BackendComponents` entries are blank by default and a blank entry selects the framework default, so
  a settings file no longer has to name internal framework types. Clear the entries that only repeat a Bee.NET default
  instead of renaming them. ([#8](https://github.com/polhem-dev/polhem/pull/8),
  [#11](https://github.com/polhem-dev/polhem/pull/11))
- **Custom definition components.** A `DefineAccess` or `DefineStorage` type named in `BackendComponents` had to
  declare one of a fixed set of constructors. It is now created by `ActivatorUtilities`, so its constructor can take
  any registered service; a `byte[]` parameter still receives the configuration encryption key, and a storage's
  `(IServiceProvider)` constructor is still preferred, because a database-backed storage resolves its dependencies
  lazily. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Startup warnings.** Startup logs a warning when methods require `ApiReplayProtection.UniqueSequence` while
  `RequireWireFrame` is off, and lists the forms that declare no permission model. That list used to look only at
  `ProgramSettings`, but a progId the registry does not name is still served by `FormBusinessObject`, so it now also
  lists the forms the definition storage holds (`IDefineStorage.GetFormSchemaIds`). That member has a default
  implementation that returns an empty list, so a custom storage still compiles; implement it to have its forms
  covered. ([#4](https://github.com/polhem-dev/polhem/pull/4), [#6](https://github.com/polhem-dev/polhem/pull/6),
  [#26](https://github.com/polhem-dev/polhem/pull/26))

### Cached definitions stay unchanged when serialized

Serializing a cached definition no longer changes it, so concurrent saves and deletes no longer fail while a cached
definition is being serialized. The per-object serialize state is gone; empty collections are omitted through
get-only `XSpecified` properties, which the reflection-only `XmlSerializer` on iOS accepts. The built-in definition
files re-serialize byte-identically. ([#8](https://github.com/polhem-dev/polhem/pull/8))

### Performance

Measured at the time of the change:

- A definition cache hit with a file token took 62 ns instead of 1,216 ns, because the source file is checked at most
  once per second per entry. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- Gzip compresses at the fastest level by default: a 570 KB payload in 0.48 ms instead of 1.67 ms, with 110 KB of
  output instead of 80 KB. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- `AesCbcHmacCryptor` uses span APIs and allocated 174 KB instead of 694 KB to encrypt a 173 KB payload, with the same
  output format. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- The access-control lookup took 20 ns instead of 506 ns once per-request reflection was cached, and the Avalonia heads
  share one expression evaluator. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- For a 20-column `DataTable` of 10,000 rows over MessagePack: 57% fewer raw bytes, 10% fewer compressed bytes, 86%
  less serialization time and 83% fewer allocations (the new layout is under
  [The wire contract changes](#the-wire-contract-changes)). ([#12](https://github.com/polhem-dev/polhem/pull/12))
- The audit batch writer persists a batch in one transaction. ([#14](https://github.com/polhem-dev/polhem/pull/14))

### Platform support

- **Trimming.** Polhem supports untrimmed and partial-trim builds. `POLHEM9004` warns when a consuming project
  publishes with NativeAOT, trims with `TrimMode=full` or disables System.Text.Json reflection; set
  `PolhemSuppressTrimSupportWarning` to `true` to silence it. `Polhem.Expressions` ships an ILLink descriptor so that
  the default mobile trim keeps the members expressions reach by reflection.
  ([#7](https://github.com/polhem-dev/polhem/pull/7), [#17](https://github.com/polhem-dev/polhem/pull/17))
- **Mobile and browser.** `LookupDialog` and `RowEditDialog` open a native window only on desktop and use the overlay
  host everywhere else, so lookups work on iOS, Android and the browser. The MessagePack value formatter handles Polhem
  enums and nested `ParameterCollection`s without dynamic code, and the HTTP client uses the platform default handler
  on the browser, Android and Apple mobile heads.
  ([#7](https://github.com/polhem-dev/polhem/pull/7), [#17](https://github.com/polhem-dev/polhem/pull/17))
- **Expressions on iOS.** Where code cannot be generated at run time, `LambdaExpression.Compile()` falls back to an
  interpreter, but the interpreter still builds a delegate of the lambda's exact signature, and beyond two parameters
  that needs generated code. On iOS a computed field such as `quantity * unit_price * (1 - discount)` terminated the
  app with an `ExecutionEngineException`; Mac Catalyst failed the same way. `DynamicExpressoEvaluator` now compiles
  every expression to one delegate that takes its variables as an object array, which needs no dynamic code; caching,
  null handling and exceptions are unchanged. ([#30](https://github.com/polhem-dev/polhem/pull/30))
- **Local mode on macOS and Linux.** `FileUtilities.IsLocalPath` accepted only Windows drive and UNC paths, so a
  desktop head on macOS or Linux could not connect in Local mode ("Unrecognized connection type"). It accepts paths
  fully qualified on the current operating system, and the Windows forms everywhere.
  ([#29](https://github.com/polhem-dev/polhem/pull/29))
- **Overlays on phones.** A panel's minimum width beat the overlay card's maximum, so a phone cut the lookup dialog off
  on both sides, and on iOS the on-screen keyboard covered the row-edit buttons. Hosted panels no longer set a minimum
  width of their own, the overlay host keeps the card inside the safe areas and above the keyboard, and the lookup and
  row-edit panels keep their buttons outside the scrolled content. ([#33](https://github.com/polhem-dev/polhem/pull/33))

### Fixes

- **Plain reads.** Plain `GetList` with a valued filter failed at the SQL parameter, and the client read Plain
  `DataTable` results as empty tables. ([#9](https://github.com/polhem-dev/polhem/pull/9))
- **Cache races.** Cache fills that raced an invalidation could keep stale values.
  ([#8](https://github.com/polhem-dev/polhem/pull/8))
- **Language resources.** Saving a language resource from a client always failed.
  ([#17](https://github.com/polhem-dev/polhem/pull/17))
- **AuditRule form.** The shipped AuditRule form showed empty mode drop-downs without a definition loader.
  ([#7](https://github.com/polhem-dev/polhem/pull/7))
- **Blazor circuits.** Sign-in did not set the circuit's time zone, and `FormDataObject` did not resume on the circuit
  context. ([#8](https://github.com/polhem-dev/polhem/pull/8))
- **Database settings.** `SaveDatabaseSettings` encrypted the passwords of the instance it was given instead of a copy.
  ([#8](https://github.com/polhem-dev/polhem/pull/8))
- **Narrowing on rebuild.** `UpgradeOptions.AllowColumnNarrowing` was checked only on the `ALTER` path, so a table
  rebuild (every column change on SQLite) could narrow a column and truncate data without the opt-in. The rebuild path
  now applies the same check. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Relation joins.** A form table without a `DbTableName` produced a join against a blank table name; the join now
  falls back to `TableName` like the rest of the SQL builder. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Chinese script tags.** Language resources are named by region (`zh-TW`, `zh-CN`), while macOS and iOS report the
  script (`zh-Hant-TW`), so the `zh-TW` resources were never reached there. `LanguageFallback` follows `zh-Hant-TW` and
  `zh-Hant` with `zh-TW`, and `zh-Hans-CN` and `zh-Hans` with `zh-CN`; a resource named by the script itself is still
  tried first. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Detail rows out of scope.** A save refused a detail row that belongs to a record the save does not carry with an
  English-only message; it now has a message key (`PolhemMessages.PermissionDetailOutOfScope`) and a `zh-TW`
  translation. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Host-supplied layouts.** `FormView` narrowed a `Layout` the host assigned in place when it applied permission
  capabilities, so the host's instance changed under it; it now works on a copy.
  ([#27](https://github.com/polhem-dev/polhem/pull/27))
- **Lists.** Grids, card lists, lookups and detail grids in Avalonia and Blazor showed a drop-down field's stored code;
  they show its list-item text in the user's language. A boolean shows a disabled check box in the card list and a
  localized yes or no elsewhere. At phone width the Avalonia card list showed a time part on dates and ignored number
  formats; it formats values as the grid does.
  ([#29](https://github.com/polhem-dev/polhem/pull/29), [#33](https://github.com/polhem-dev/polhem/pull/33))
- **Row-edit overlay.** The Avalonia row-edit overlay recomputed computed fields only once the row was confirmed; it
  recomputes them while the row is edited (`FormDataObject.RowEditFieldChanged`), and Cancel restores them.
  ([#30](https://github.com/polhem-dev/polhem/pull/30))
- **Blazor dates.** The Blazor `DateEdit` showed a blank box for a value that has a time of day, because a date input
  accepts only a date; it shows the date part. ([#33](https://github.com/polhem-dev/polhem/pull/33))
- **Blazor Remote mode.** Following the Blazor Server README in Remote mode failed with `401 Unauthorized`, because the
  server requires the application's API key and nothing said to set it. The README, `platform-support` and the remarks
  of `UseRemoteProvider` say that `ApiClientInfo.ApiKey` must be set at startup.
  ([#29](https://github.com/polhem-dev/polhem/pull/29))

## Breaking changes

### Packages, namespaces and Bee names are renamed

- **Affects:** every application built on Bee.NET.
- **Before:** the packages and namespaces were `Bee.*`, several types and members carried `Bee` in their names, and the
  command-line tool was `Bee.Cli`, invoked as `dotnet bee`.
- **Now:** package IDs and namespaces are `Polhem.*`, and versions restart at 1.0.0. The split into packages is
  unchanged. `Bee` in a type or member name is `Polhem`. The compiler reports every use of the old names.
- **Migrate:**
  1. Replace each `Bee.<Name>` package reference with `Polhem.<Name>` and each `Bee.<Name>` namespace with
     `Polhem.<Name>`.
  2. Rename the types and members below. `IBeeContext`, `BeeContext` and `BeeStringLocalizer<T>` were renamed again
     by the review; they are under [Public types are renamed, moved or sealed](#public-types-are-renamed-moved-or-sealed).

     | Bee.NET | Polhem |
     |---------|--------|
     | `AddBeeFramework`, `UseBeeFramework` | `AddPolhemFramework`, `UsePolhemFramework` |
     | `AddBeeBlazor`, `BeeBlazorOptions`, `BeeBlazorProviderMode` | `AddPolhemBlazor`, `PolhemBlazorOptions`, `PolhemBlazorProviderMode` |
     | `BeeApiConnectorFactory`, `BeeAccessTokenProvider` | `PolhemApiConnectorFactory`, `PolhemAccessTokenProvider` |
     | `BeeLoginPanel` | `PolhemLoginPanel` |
     | `BeeFrameworkServiceCollectionExtensions`, `BeeFrameworkApplicationBuilderExtensions`, `BeeBlazorServiceCollectionExtensions` | `PolhemFrameworkServiceCollectionExtensions`, `PolhemFrameworkApplicationBuilderExtensions`, `PolhemBlazorServiceCollectionExtensions` |
     | `Bee.Cli` (`dotnet bee`) | `Polhem.Cli` (`dotnet polhem`) |

  3. Rename the strings the compiler does not see, under
     [Names the compiler does not check are renamed too](#names-the-compiler-does-not-check-are-renamed-too).
- **Background:** the renaming was done mechanically, and it was checked by changing every name back to `Bee` and
  comparing the result with the Bee.NET source it started from (`jeff377/bee-library` at commit `7d6cc9d9`, whose
  `src/` and `tools/Bee.Cli` are identical to the `v4.33.0` tag). What remained were the license, the package metadata
  and the icon. The full test suite, including the database tests, ran with the same number of tests as on Bee.NET and
  passed. Several kinds of name are strings the compiler does not check, such as type names in definition files,
  analyzer lookups by metadata name and the assembly name in the trimming descriptor; tests were added for the kinds
  that had none. This check covered the renaming step; the pre-release review that followed changed the code, and
  those changes are the other items of these notes.

### Names the compiler does not check are renamed too

- **Affects:** definition files and settings that name framework types, deployments that rely on the default master
  key variable, analyzer suppressions, MSBuild properties, style sheets for the Blazor components, code that reads the
  data keys below, and every mix of a Bee.NET client with a Polhem server or the other way round.
- **Before:** these strings carried `Bee`.
- **Now:** they carry `Polhem`, and the old names are not recognized. A build with the old names succeeds, and the
  problem only shows at run time or not at all: settings that use the old names are ignored without a warning, a type
  or assembly name left over from Bee.NET fails with the same message as any other name that cannot be resolved, and a
  missing `POLHEM_MASTER_KEY` is reported the same way whether or not `BEE_MASTER_KEY` is set. The server only accepts
  payload types from allowed namespaces, so a Bee.NET client and a Polhem server cannot talk to each other.
- **Migrate:**

  | What | Bee.NET | Polhem |
  |------|---------|--------|
  | Type names in payloads, in the default settings and in the `BusinessObject` / `Repository` bindings of definition files | `Bee.*` | `Polhem.*` |
  | Default environment variable of the master key | `BEE_MASTER_KEY` | `POLHEM_MASTER_KEY`; a `SystemSettings.xml` that names the variable in `MasterKeySource` keeps using that name |
  | Analyzer diagnostic IDs | `BEEnnnn`, for example `BEE1008` | `POLHEMnnnn` with the same numbers, for example `POLHEM1008` |
  | MSBuild properties for definition file checks | `BeeDefinitionFilesGlob`, `BeeRequireDefinitionFiles`, `BeeAnalyzeDefinitionFiles` | `PolhemDefinitionFilesGlob`, `PolhemRequireDefinitionFiles`, `PolhemAnalyzeDefinitionFiles` |
  | CSS classes of the Blazor components | `bee-…` | `polhem-…` |
  | The `DataColumn` extended property that records a declared field type | `Bee.FieldDbType` | `Polhem.FieldDbType` |
  | The `Exception.Data` key `SerializationErrorData.FilePath` | `Bee.FilePath` | `Polhem.FilePath` |
  | Labels that derive session encryption keys (`DerivedApiEncryptionKeyProvider`) | `bee-api-*` | `polhem-api-session-key`, `polhem-api-encryption-root-key` |

  Applications built on Bee.NET are mostly kept in repositories their own developers control, so a one-time search and
  replace is enough; [Migrating from Bee.NET](../guides/migrating-from-bee-net.md#names-the-compiler-does-not-check)
  has a command that finds these names. Upgrade clients and servers together.
- **Background:** `POLHEM4001`–`POLHEM4004` are reserved and never reused: Bee.NET shipped and then retired
  `BEE4001`–`BEE4004`, and a suppression mapped by number must not silence a future rule. The derived session keys are
  never stored, so no stored data depends on their labels; sessions created by Bee.NET end in any case (see
  [Sessions end and old password hashes no longer verify](#sessions-end-and-old-password-hashes-no-longer-verify)).
  Audit records that Bee.NET wrote keep `Bee.FieldDbType` (see [Audit and log records change](#audit-and-log-records-change)).
  ([#10](https://github.com/polhem-dev/polhem/pull/10))

### Public types are renamed, moved or sealed

- **Affects:** code that uses the types below, and code that derives from a framework class.
- **Before:** some types were named after the framework or an abbreviation, some lived in an assembly that did not own
  their responsibility, and most public classes could be inherited.
- **Now:** types are named after what they are and moved to the assembly that owns their responsibility. Classes that
  are not designed for inheritance are sealed, so later versions can change their internals without breaking a
  subclass nobody planned for: data and definition types, attributes, exceptions, caches, service implementations
  without hooks, database dialects and builders, and leaf UI controls and Blazor components. Extension goes through the
  interfaces and the documented base classes, which stay open: the business object, repository and collection bases,
  `TextEdit`, `DateEdit`, `ListView`, `FormView`, the connectors and `AuditRuleBusinessObject`. `KeyCollectionBase<T>`
  is abstract. Enums without a zero value gained `None = 0`. `Polhem.ObjectCaching` no longer references
  `Polhem.Repository.Abstractions`.
- **Migrate:** rename and re-import as below, and replace a subclass of a sealed class with composition or with one of
  the open bases and interfaces.

  | Bee.NET | Polhem |
  |---------|--------|
  | `IBeeContext`, `BeeContext` | `IBusinessObjectContext`, `BusinessObjectContext` |
  | `BeeStringLocalizer<T>` | `LanguageResourceStringLocalizer<T>` |
  | `LogBusinessObject`, `LogListResult`, `LogAggregateResult`, `LogApiConnector`, `LogListResponse`, `LogAggregateResponse`, `ILogListResponse`, `ILogAggregateResponse`, `LogActions` | `AuditLogBusinessObject`, `AuditLogListResult`, `AuditLogAggregateResult`, `AuditLogApiConnector`, `AuditLogListResponse`, `AuditLogAggregateResponse`, `IAuditLogListResponse`, `IAuditLogAggregateResponse`, `AuditLogActions` |
  | `PermissionAction` | `PermissionActions` (a flags enum) |

### The client API takes a service provider and cancellation tokens

- **Affects:** code that creates a `LocalApiProvider` or a local connector, uses `ApiClientInfo.LocalServiceProvider`,
  `ApiClientInfo.ApiEncryptionKey` or `ApiClientInfo.UserTimeZoneId`, implements `IUIViewService`, overrides the
  protected `Resolve*Async` hooks of `FormView` or `ListView`, calls `ExecuteAsync<T>` on a `SystemApiConnector` or an
  `AuditLogApiConnector`, or calls `JsonRpcExecutor.ExecuteAsync`.
- **Before:** local providers and connectors read the `IServiceProvider` from a static property, per-session state sat
  on `ApiClientInfo`, async members took no `CancellationToken`, and failures of a cancelled call were reported on the
  view.
- **Now:**
  - `LocalApiProvider` and the local connector constructors take the `IServiceProvider`; per-session state lives on
    `ApiSessionContext`.
  - Every public async member of the client surface, of the UI packages (`Polhem.UI.Core`, `Polhem.UI.Avalonia`,
    `Polhem.Web.Blazor.Server`) and `JsonRpcExecutor.ExecuteAsync` take a trailing `CancellationToken`, which reaches
    `HttpClient`. The server answers 499 for a cancelled request, and a cancelled call throws to its caller instead of
    being reported on the view.
  - The connectors' action methods are virtual.
  - `ExecuteAsync<T>` of `SystemApiConnector` and `AuditLogApiConnector` is protected, because every framework action
    on them has a typed method and a host that adds actions exposes them from a subclass. `FormApiConnector` keeps it
    public, because a form's business object can declare actions of its own.
- **Migrate:**
  1. Pass the `IServiceProvider` to `LocalApiProvider` and the local connectors; read the encryption key and the user's
     time zone from `ApiSessionContext`.
  2. Add the `CancellationToken` parameter to implementations of `IUIViewService` and to overrides of the
     `Resolve*Async` hooks, and catch `OperationCanceledException` where a cancelled call used to be shown on the view.
  3. Expose an extra action of `SystemApiConnector` or `AuditLogApiConnector` from a subclass.
- **Background:** [#10](https://github.com/polhem-dev/polhem/pull/10), [#11](https://github.com/polhem-dev/polhem/pull/11),
  [#12](https://github.com/polhem-dev/polhem/pull/12), [#26](https://github.com/polhem-dev/polhem/pull/26),
  [#27](https://github.com/polhem-dev/polhem/pull/27)

- **Affects:** hosts that implement `IReplayWindowStore`, `ICacheDataSourceProvider` or `IFormRuleProcessor`, add a
  payload codec, or set properties of a cached database-dependent type or of the session's company scope.
- **Before:** the members and setters below existed in their Bee.NET shape.

  | Type | Change |

### Tunable constants are static readonly

- **Affects:** code that uses one of the members below in a constant expression, such as an attribute argument or a
  `case` label.
- **Before:** they were `const` in Bee.NET.
- **Now:** they are `static readonly`: `ApiKeyFormat.MinSysIdLength`, `ApiKeyFormat.MaxSysIdLength`,
  `LoginAttemptTracker.DefaultLockoutMinutes`, `DefaultMaxFailedAttempts` and `DefaultMaxTrackedAccounts`,
  `CurrencySettings.FallbackRounding`, `UnitSettings.FallbackDecimals`, `ApiKeyCache.AbsoluteMinutes` and
  `NegativeMinutes`, `RowEditPanel.CompactWidthThreshold` and `FormView.DefaultCompactWidthThreshold`. Protocol names,
  identifiers and formats stay `const`.
- **Migrate:** move the use out of the constant expression, for example from a `case` label into an `if`.
- **Background:** a `const` is compiled into every caller, so changing its value later would not reach code built
  against the old one. ([#26](https://github.com/polhem-dev/polhem/pull/26))

### Sessions end and old password hashes no longer verify

- **Affects:** every deployment that moves over from Bee.NET: its signed-in users, and accounts whose password hash is
  in the old format.
- **Before:** `st_session` stored the access token, the session seed contained it, and password hashes in the
  unprefixed PBKDF2-SHA1 format verified.
- **Now:** access tokens are not stored. `st_session` keeps `AccessTokenHasher.ComputeStorageKey` of the token, a
  SHA-256 derived key, in its `access_token` column, and the session seed no longer contains the token, so read access
  to the table yields no usable bearer token. Rows written before the switch match no token, so every existing session
  ends. The unprefixed PBKDF2-SHA1 format inherited from Bee.NET no longer verifies.
- **Migrate:**
  1. Users sign in again. Delete the rows Bee.NET left in `st_session`: they hold its tokens and match nothing.
  2. Reset the password of every account whose `st_user.password` does not start with `v2.`. Hashes that start with
     `v2.` keep working and are rehashed with more iterations at the next successful sign-in.
- **Background:** [#5](https://github.com/polhem-dev/polhem/pull/5)

### Audit and log records change

- **Affects:** queries and reports over the log tables, code that reads `AuditEntry.AccessToken`, and code that reads
  the declared field types of audit records Bee.NET wrote.
- **Before:** `st_log_access`, `st_log_anomaly_api`, `st_log_change` and `st_log_login` stored the access token in
  `access_token`. Audit records of a form that `ProgramSettings` does not list carried the caller's spelling of the
  ProgId.
- **Now:**
  - The four log tables keep a short token fingerprint in `token_fingerprint`, which still correlates the records of
    one session, and `AuditEntry.AccessToken` is `AuditEntry.TokenFingerprint`.
  - Audit records carry the FormSchema's ProgId spelling, so one form's records share one `prog_id` in
    `st_log_change` and `st_log_access`. Records written before keep the spelling they were written with.
  - Audit records that Bee.NET wrote keep `Bee.FieldDbType` in their stored XML (`msprop:Bee.FieldDbType` in the
    `changes_xml` column of `st_log_change`); their values read the same, and only the declared type of their columns
    is no longer known: `GetDeclaredFieldDbType()` returns `null` for them.
- **Migrate:**
  1. The schema upgrade adds `token_fingerprint` but never drops a column, so the old `access_token` column stays with
     the tokens Bee.NET wrote. Clear it or drop it yourself.
  2. Compare `prog_id` case-insensitively in queries over older records.
  3. Read `AuditEntry.TokenFingerprint` instead of `AuditEntry.AccessToken`.
- **Background:** [#5](https://github.com/polhem-dev/polhem/pull/5), [#26](https://github.com/polhem-dev/polhem/pull/26)

### Anonymous calls and protocol errors answer differently

- **Affects:** clients that check for HTTP 401, that show the message of a server exception, or that rely on the error
  code of an unknown action or an unreadable body; servers that override `IsAuthorizationRequired`.
- **Before:** the server kept a hand-written list of methods that could be called without a Bearer header, and
  rejected every other request without one with HTTP 401. An action name that resolved to no method and a `Plain` body
  that could not be read surfaced as other codes, and `-32601` and `-32602` had no producer. Messages of BCL exceptions
  reached remote callers.
- **Now:**
  - A request without an `Authorization` header is simply anonymous and `[ApiAccessControl]` alone decides. A method
    that needs a session answers JSON-RPC `-32001` (Unauthorized, `AuthenticationRequiredException`), which the .NET
    client turns into an `UnauthorizedAccessException`. `RemoteApiProvider` sends the header only once it has an
    access token, so it sends none before sign-in, and a deployment that overrides `IsAuthorizationRequired` to refuse
    anonymous requests is not bypassed by a placeholder empty token.
  - An unknown action answers `-32601` (`MethodNotFound`), and a `Plain` body that cannot be read into the method's
    type answers `-32602` (`InvalidParams`), each with a fixed message.
  - BCL exception messages stay in the server log (`JsonRpcExecutor.Logger`); the caller gets a fixed message per
    error code. Framework messages meant for users are thrown as `UserMessageException`.
- **Migrate:** check for error code `-32001` (or `UnauthorizedAccessException` in .NET) instead of HTTP 401, and throw
  `UserMessageException` from a business object for a message the user should see.
- **Background:** [#6](https://github.com/polhem-dev/polhem/pull/6), [#18](https://github.com/polhem-dev/polhem/pull/18),
  [#22](https://github.com/polhem-dev/polhem/pull/22)

### The server checks requests more strictly

- **Affects:** callers and business objects whose requests the checks below now refuse, and clients that relied on the
  server's debug settings.
- **Before:** Bee.NET accepted these requests.
- **Now:**
  - **Record scope on writes.** A save checks the master scope against the row an UPDATE or DELETE actually binds,
    refuses rows that change their row id, checks against the database that modified and deleted detail rows belong to
    an in-scope master of the same payload, and checks the values an added or modified master row leaves behind
    against the caller's Create or Update scope. The rules are described in
    [Permission and authorization](../security/permission-authorization.md).
    ([#4](https://github.com/polhem-dev/polhem/pull/4))
  - **Record scope on reads.** `GetList` and `GetCount` accept only filter and sort fields the form declares and never
    protected fields, and `GetLookup` applies the Read record scope. ([#4](https://github.com/polhem-dev/polhem/pull/4))
  - **Definitions over the API.** Remote `GetDefine` serves only an explicit list of definition types (the ones a
    client renders with, listed in `SystemBusinessObject.GetDefine`); deployment settings such as `SystemSettings` and
    `DatabaseSettings` are read only in process. ([#4](https://github.com/polhem-dev/polhem/pull/4))
  - **Encoded and Encrypted bodies** are decoded into the parameter type of the action the request resolves to; the
    type name the client declares is only a consistency check. Decoding enforces one depth limit on both codecs, nested
    filters included. Only public, non-generic, one-parameter instance methods that are not accessors can be called as
    actions (`JsonRpcExecutor.IsResolvableAction`), the same rule `POLHEM3001` applies at build time.
    ([#6](https://github.com/polhem-dev/polhem/pull/6))
  - **Plain bodies.** A `Plain` body used to be deserialized straight into the argument type of the business object's
    method, so a caller could set any public member of that type, including ones the contract does not declare. It is
    now read into the action's request type first and copied into the arguments, as the Encoded path already did.
    ([#22](https://github.com/polhem-dev/polhem/pull/22))
  - **Sessions and keys.** `CreateSession` accepts only local calls. The API key methods `CreateApiKey`,
    `SetApiKeyEnabled` and `SetApiKeyExpiry` are replay-protected like the other state-changing system methods. The
    database anomaly log is readable only by a deployment administrator.
    ([#5](https://github.com/polhem-dev/polhem/pull/5))
  - **DDL.** Defaults of columns that are not strings must be literals of their column type.
    ([#4](https://github.com/polhem-dev/polhem/pull/4))
  - **Collections.** A nil element in a `KeyCollectionBase` payload is rejected instead of skipped.
    ([#9](https://github.com/polhem-dev/polhem/pull/9), [#14](https://github.com/polhem-dev/polhem/pull/14))
  - **Client.** A client refuses the "none" encryptor a server advertises unless the client itself runs in debug mode,
    and no longer adopts the server's debug flag or allowed type namespaces.
    ([#6](https://github.com/polhem-dev/polhem/pull/6))
- **Migrate:**
  1. Declare in the form every field a caller filters or sorts on. A business object whose lookups should ignore the
     record scope sets `FormBusinessObject.LookupAppliesRecordScope` to `false`.
  2. Call `CreateSession` in process, and send a frame sequence with `CreateApiKey`, `SetApiKeyEnabled` and
     `SetApiKeyExpiry` when replay protection is on.
  3. Read `SystemSettings` and `DatabaseSettings` in process instead of through `GetDefine`.
  4. Give non-string column defaults a literal of the column type.
  5. Run a client in debug mode when it has to talk to a server with the "none" encryptor.
- **Background:** [#4](https://github.com/polhem-dev/polhem/pull/4), [#5](https://github.com/polhem-dev/polhem/pull/5),
  [#6](https://github.com/polhem-dev/polhem/pull/6), [#9](https://github.com/polhem-dev/polhem/pull/9),
  [#14](https://github.com/polhem-dev/polhem/pull/14), [#22](https://github.com/polhem-dev/polhem/pull/22)

### The wire contract changes

- **Affects:** clients that are not built on the Polhem .NET packages, such as a TypeScript client, and anything else
  that reads or writes payloads itself.
- **Before:** the wire had Bee.NET's shape.
- **Now:**
  - `CreateSessionRequest.userID` is `userId` and has no `oneTime`; `LoginResponse` gains `culture`; the audit log
    response types are renamed (`AuditLog…`).
  - Over MessagePack a `DataTable` is written as one column table plus positional rows instead of a name/value map per
    row. JSON and Plain are unchanged.
  - Every wire member whose initializer is not the CLR default is always written, so an absent member means the CLR
    default on every codec. Plain requests bind object-typed filter and parameter values by JSON kind, so Plain, JSON
    and MessagePack carry the same values.
- **Migrate:** update your own client to these shapes. The TypeScript client `polhem-connector-js` follows the
  contract changes.
- **Background:** [#9](https://github.com/polhem-dev/polhem/pull/9), [#10](https://github.com/polhem-dev/polhem/pull/10),
  [#11](https://github.com/polhem-dev/polhem/pull/11), [#12](https://github.com/polhem-dev/polhem/pull/12),
  [#15](https://github.com/polhem-dev/polhem/pull/15)

### `GetList` without paging returns one page

- **Affects:** callers of `GetList` that pass no paging options and expect every row.
- **Before:** `GetList` without paging options returned every row.
- **Now:** it returns the first page, capped at `PagingOptions.MaxPageSize`.
- **Migrate:** pass paging options and read the pages you need.
- **Background:** [#4](https://github.com/polhem-dev/polhem/pull/4)

### English is the base language

- **Affects:** applications that show the built-in text, settings that use `CommonConfiguration.DefaultLang` or
  `BackendConfiguration.DefaultLanguage`, code that reads `UserInfo.Culture` before sign-in, code that passes Chinese
  words to `ValueUtilities.CBool`, and code that passes labels to `PolhemLoginPanel` or sets `DynamicGrid.EmptyText`.
- **Before:** the built-in text was Chinese, two settings held the default language, `UserInfo.Culture` was `zh-TW`
  before sign-in, and `CBool` recognized the Chinese words for yes and true.
- **Now:**
  - The built-in definition files, the Avalonia and Blazor UI text and the framework messages use English as their
    base text, and the Chinese text moves to the shipped `zh-TW` resources. One fall-back chain (`LanguageFallback`)
    serves captions, enums, menus, rule messages and framework text: the requested culture, its parents, the
    deployment default, then the base text.
  - The deployment default is `CommonConfiguration.DefaultLanguage` (default `zh-TW`). It replaces
    `CommonConfiguration.DefaultLang` and `BackendConfiguration.DefaultLanguage`, which are no longer read. It is the
    culture of users who have no `st_user.culture` of their own and the last language fall-back.
  - The login response carries the user's culture (`st_user.culture` or the deployment default), which the client
    adopts, so `UserInfo.Culture` is empty until sign-in instead of `zh-TW`.
  - Framework messages meant for end users carry a key and arguments (`UserMessageException`) and are resolved in the
    session culture; form rule messages resolve `{ProgId}.Rule.{RuleId}.Message`. Numbers and dates are displayed and
    parsed in the user's culture, while the wire stays culture-invariant.
  - `ValueUtilities.CBool` accepts language-neutral codes only: `1`, `T`, `TRUE`, `Y` and `YES`, ignoring case.
  - `PolhemLoginPanel` label parameters and `DynamicGrid.EmptyText` are `string?`; `null` shows the localized text.
- **Migrate:**
  1. Move the default language to `CommonConfiguration/DefaultLanguage`.
  2. Set `st_user.culture` for users who should not get the deployment default.
  3. Add translations of your form rule messages under `{ProgId}.Rule.{RuleId}.Message`.
  4. Convert a value typed in the user's language in the UI before passing it to `CBool`.
- **Background:** the Chinese words for yes and true made one language special in a culture-neutral conversion; a
  value typed in a user's language is the UI's to convert. [#15](https://github.com/polhem-dev/polhem/pull/15)

### Required fields are enforced on save

- **Affects:** applications whose FormSchemas mark fields `Required` that are empty in stored or submitted data.
- **Before:** `FormField.Required` was a caption cue only: the server saved an empty required field.
- **Now:** a save refuses an added or modified row, master or detail, whose required field is empty, and names the
  field by its caption in the caller's language (`PolhemMessages.SaveFieldRequired`, `SaveDetailFieldRequired`). The
  Avalonia `FormView` and the Blazor `FormPage` run the same rule, `RequiredFieldCheck` with `MissingRequiredField`,
  before sending a save, name every empty required field (`PolhemUIText.RequiredFieldsEmpty`) and do not send it.
  Empty means `null`, text that is empty or white space, `Guid.Empty` and a zero-length binary value; a number, a
  boolean or a date is never empty, because those columns always hold a value. Only persisted fields are checked, so a
  `Required` flag on a relation or virtual field has no effect on saving.
- **Migrate:** before upgrading, review the `Required` flags of your FormSchemas. An existing record stored with an
  empty required field cannot be saved again until the field is filled, so fill the data or clear the flag. Mark the
  stored key field instead of a relation or virtual field.
- **Background:** [#26](https://github.com/polhem-dev/polhem/pull/26), [#27](https://github.com/polhem-dev/polhem/pull/27)

### Default-value expressions win when a row is created

- **Affects:** forms whose fields have a `DefaultValueExpression`, especially together with a literal `DefaultValue`,
  and code that reads the defaults of `Short`, `Long`, `Decimal` or `Binary` fields.
- **Before:** the per-type seed (0, empty text, today, `Guid.Empty`) made most fields non-empty, so an expression such
  as `Today()` on a date field never ran.
- **Now:** when a new row is created, by `GetNewData` on the server or by a UI client, a field's
  `DefaultValueExpression` is written over its literal `DefaultValue` and over the per-type seed. At save the
  expression still fills only fields that are empty, so a value the user entered is kept. Default values of `Short`,
  `Long`, `Decimal` and `Binary` fields are typed and non-null.
- **Migrate:** check fields that have both an expression and a literal default; the expression's value is the one a
  new row now shows. A custom `IFormRuleProcessor` implements `ApplyNewRowDefaults` (see
  [Extension interfaces and cached types change](#extension-interfaces-and-cached-types-change)).
- **Background:** [#14](https://github.com/polhem-dev/polhem/pull/14), [#22](https://github.com/polhem-dev/polhem/pull/22)

### Views localize definitions by default

- **Affects:** Avalonia heads and Blazor Server hosts that render definitions.
- **Before:** the views rendered definitions as stored unless a definition loader was set up.
- **Now:** `ClientInfo.UseDefinitionLoader` is on by default, so the Avalonia views show captions in the user's
  language, the tenant's customized layout and the company's number formats without any setup. The Blazor `FormPage`
  localizes its definitions through a definition loader by default as well (`PolhemBlazorOptions.UseDefinitionLoader`):
  captions in the circuit's culture, the tenant's layout and the framework's number formats; the page's own parameter
  still overrides it per page.
- **Migrate:** set `ClientInfo.UseDefinitionLoader` or `PolhemBlazorOptions.UseDefinitionLoader` to `false` to render
  definitions as stored and save the loader's extra round trips.
- **Background:** [#22](https://github.com/polhem-dev/polhem/pull/22), [#27](https://github.com/polhem-dev/polhem/pull/27)

### Clients keep their endpoint in a new place

- **Affects:** desktop and mobile clients that stored their endpoint and API key with Bee.NET.
- **Before:** they were kept in a `{ExeName}.Settings.xml` file beside the assembly.
- **Now:** the endpoint and the API key are kept in `endpoint.txt` and `apikey.txt` under the per-user local
  application data folder (`FileEndpointStorage`, now in `Polhem.UI.Core` and the default), because the folder beside
  the assembly is read-only on iOS and lost on WebAssembly. The previous `{ExeName}.Settings.xml` is not read.
- **Migrate:** users enter the endpoint and the API key again.
- **Background:** [#12](https://github.com/polhem-dev/polhem/pull/12)

### Configuration and startup checks

- **Affects:** deployments with a wrong component type name, without a `common` database item, or with a
  `ProgramSettings.xml` in the nested `<Categories>` layout.
- **Before:** a wrong `CacheProvider` or component type name failed later with a null reference, a missing `common`
  database item failed on the first request that reached a framework table, and a `ProgramSettings.xml` in the nested
  layout was refused.
- **Now:**
  - A wrong `CacheProvider` or component type name fails at startup with the name of the setting.
    ([#8](https://github.com/polhem-dev/polhem/pull/8), [#11](https://github.com/polhem-dev/polhem/pull/11))
  - A host built with `AddPolhemFramework` calls `IDatabaseSettingsProvider.ValidateRequired` before any other hosted
    service starts, so a deployment without a `common` database item does not start.
    ([#22](https://github.com/polhem-dev/polhem/pull/22))
  - The `ProgramSettings` format is not checked: `ProgramSettings.xml` is read like every other definition file. A file
    still in the nested `<Categories>` layout of earlier Bee.NET versions, which carried the menu, loads as an empty
    registry, so every progId falls back to the framework's default business object.
    ([#28](https://github.com/polhem-dev/polhem/pull/28))
- **Migrate:**
  1. Correct the component type names the startup error names.
  2. Add a `DatabaseItem` whose `Id` is `common`.
  3. Bee.NET 4.33.0 refused a nested `ProgramSettings.xml` and named the conversion command, so a deployment that ran
     on it already has the flat layout. Any other converts the file with Bee.NET's `dotnet bee defines split-menu`
     before moving over.

### Generated layouts use other editors

- **Affects:** deployments that materialize or generate layouts, and layouts with `DateTime` fields.
- **Before:** the default `AuditRule`, `Department` and `Employee` layouts showed every field as a text box, including
  mode codes, a flag and row ids. A `DateTime` field got `DateEdit`, a date picker that writes the date alone, so
  editing the field dropped its time of day.
- **Now:** the shipped `AuditRule`, `Department` and `Employee` layouts are regenerated with `FormLayoutGenerator` from
  their schemas: drop-downs for the audit modes, a check box for the sensitive flag, lookups for the department and the
  manager, and no system columns. `FormLayoutGenerator` and the `Auto` control type give a `DateTime` field the new
  `DateTimeEdit`. Materializing the defaults (`Defaults.MaterializeTo`, `dotnet polhem defines materialize`) skips
  files that exist, so a deployment that already has these layouts keeps the old ones, and layouts already saved keep
  `DateEdit` on their `DateTime` fields.
- **Migrate:**
  1. Overwrite the three layouts (see `dotnet polhem help defines`) or edit them, after carrying over any changes of
     your own.
  2. Change `DateTime` fields to `DateTimeEdit` where the time matters.
- **Background:** [#29](https://github.com/polhem-dev/polhem/pull/29), [#33](https://github.com/polhem-dev/polhem/pull/33)
