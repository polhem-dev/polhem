# Polhem 1.16.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.16.0.md)

This file holds the details behind the `[1.16.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

A form's list now takes query conditions: a form declares the fields it offers, and the Avalonia, MudBlazor and Fluent
UI lists show a query pane, the conditions in effect as chips, saved queries per user or shared with the company, and
"Me" for the signed-in user. Expressions gain business helper functions and conditional detail aggregates, an allowlist
checks expressions written by someone who cannot be trusted with the full engine, and `Polhem.Definition.Drafting`
writes form rules from plain language, which DefineEditor offers in a new rule dialog. A save that totals or rules read
now checks that the payload holds one record and only its own rows. The release also narrows the public surface of the
UI packages to what applications use, and replaces public members that ended in optional parameters with parameter
objects or overloads.

The wire adds the user query messages and two optional members on the EnterCompany response. A 1.15.0 client keeps
working against a 1.16.0 server, since unknown members are skipped; the TypeScript client needs the regenerated
contract for the new messages.

What each kind of application has to act on:

- **Every application on a database**: the first upgrade after updating changes the default of reference `Guid`
  columns, and on SQLite rebuilds those tables; afterwards the 1.15.0 tools refuse the database
  ([Reference `Guid` columns default to the empty GUID](#reference-guid-columns-default-to-the-empty-guid)).
- **Applications whose list filters type `_` in text**: [Only `%` is a wildcard in text
  operators](#only--is-a-wildcard-in-contains-startswith-and-endswith).
- **API callers that save forms with totals or rules over detail rows**: [Saves that totals or rules read check the
  record](#saves-that-totals-or-rules-read-check-the-record).
- **Code that calls the UI rule types, derives from the Blazor component bases or registers the Blazor client itself**:
  [UI types only the framework's UI packages use are no longer public](#ui-types-only-the-frameworks-ui-packages-use-are-no-longer-public).
- **Code that uses the object tree commands or drag and drop**: [The object tree command and drag-and-drop types move
  to `Polhem.UI.Core`](#the-object-tree-command-and-drag-and-drop-types-move-to-polhemuicore).
- **Code that calls `UpgradeTables`, `BuildSelect`, `BuildCount`, the expression sample methods or `ExpressionFunction`,
  and any assembly compiled against `CreateLocal` or `CreateRemote`**: [Members that ended in optional parameters take a
  parameter object or overloads](#members-that-ended-in-optional-parameters-take-a-parameter-object-or-overloads).
- **Hosts of `Polhem.AI.Claude`**: [Requests to Claude default to medium effort](#requests-to-claude-default-to-medium-effort).

## New features and changes

### Query conditions on a form's list

`FormSchema.QueryFields` names the master-table fields a list offers for query conditions, as a comma-separated list
like `ListFields`; empty offers the `ListFields`. `FormSchema.GetQueryFields` resolves it, leaving out `sys_rowid` and
the stored columns `ProtectedFields` lists, and analyzer `POLHEM1004` reports an entry that names no field. DefineEditor
and the form workbook edit the attribute; it is omitted from the file when empty, so existing definition files do not
change.

`Polhem.UI.Core.Criteria` holds the UI-neutral model: `CriteriaField` describes a field and the operators its kind
offers, `CriteriaRow` holds one condition with its value already converted, and `QueryCriteria` combines rows with AND,
with required and default rows for reports. `GetListFilterConverter` turns the criteria into the `FilterNode` that
`GetList` takes, resolving relative dates (this month, the last 30 days) against the user's today.
`CriteriaField.FromQueryFields` returns the fields a list offers, less those the user cannot read.

The Avalonia `ListView`, and the MudBlazor and Fluent UI `FormPage`, show a Query button when the form offers query
fields. The conditions open in a side pane, which docks beside the list, lies over it on a narrower window and covers
the page on a phone; the conditions in effect show as chips above the list, each removable. The Avalonia
`CriteriaPanel` can be hosted in a view of its own. On the Blazor pages a column header's filter is a row of the same
criteria, so the pane, its chips and saved queries include it.

A condition on a field related to employees, or on an owner column, can hold **Me**: the signed-in user, resolved
when the query runs. EnterCompany returns the user's and the linked employee's row ids for it, exposed as
`IUserContext.Identity`.

The guide is [List Query Conditions](../guides/list-query-conditions.md).

### Saved queries

A user can save the conditions under a name per form, keep the query personal or share it with the company, and make
one the default for the list. The queries live in `st_user_query` and `st_user_query_default` in the company database,
so the next upgrade creates both tables. `FormBusinessObject` gains `GetUserQueries`, `SaveUserQuery`, `DeleteUserQuery`
and `SetDefaultUserQuery`; each needs the form's Read permission, and only a query's creator may overwrite, rename or
delete it. The API client's `FormApiConnector` implements the new optional `IUserQueryConnector`, so an existing
`IFormApiConnector` implementation keeps compiling.

`UserQueryCodec` stores the criteria as versioned XML. A saved query that names a field or operator the form no longer
offers applies the rest and names what it left out. The Avalonia, MudBlazor and Fluent UI query panes show a bar of
saved queries with save, save as, rename, share, delete and default. See
[List Query Conditions §7](../guides/list-query-conditions.md#7-saved-queries).

### Business helper functions and conditional detail aggregates

Expressions gain `IsBlank`, `Between`, `In`, `DaysBetween`, `MonthEnd` and `RegexMatch`. They compute from their
arguments alone. `IsBlank` counts zero as blank, since text and number columns are never null; `RegexMatch` matches
without backtracking, so a pattern with a backreference or a lookaround is reported as unsupported.

A master expression can test detail rows one by one: `Count(Table, condition)`, `Any(Table, condition)` and
`All(Table, condition)`. Over no rows `Count` is 0, `Any` false and `All` true. `ValidateExpressions` checks the
condition against the detail table's fields.

Each helper function carries a summary and an example (`ExpressionFunction.Summary`, `ExpressionFunction.Example`),
which DefineEditor's expression editor shows beside each function and in completion. The editor now also checks detail
aggregates the way form validation does, through the new `FormExpressionCalculator.ValidateExpression`. The guide is
[Expressions and Rules](../definitions/expression-rules.md).

- **Background:** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md)

### An allowlist for expressions from untrusted authors

Parsing an expression is not a sandbox. `IExpressionAllowlist` (in `Polhem.Core`), implemented by
`DynamicExpressoEvaluator`, checks an expression before it runs: size limits, then only variables, the helper
functions, operators, literals and a fixed list of members. `FormExpressionCalculator.FindAllowlistViolations` checks a
schema or one expression, and `ValidateUntrustedExpression` rejects an expression that is too large, does not parse or
leaves the list. `RegexMatch` is outside the list whatever its pattern. A definition file's expressions are not
enforced: DefineEditor reports one outside the list as a warning, and it still runs.

The evaluator also reports some text it used to fail on with an `InvalidOperationException` (a helper function's name
used as a value) as the `ExpressionEvaluationException` its contract declares.

- **Background:** [ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### Form rules from plain language, and a rule dialog in DefineEditor

`RuleDrafting` (`Polhem.Definition.Drafting.Rules`) writes one `FormRule` from what a person says it should check,
revises it in the same conversation, and explains an existing rule. A submission is accepted only when its expressions
pass `ValidateUntrustedExpression`, its message has each requested language, and the expression engine computes the
outcome the model claimed for every sample row; the samples in the result are the engine's. `RuleDraftResult` reports
the calls, tokens and time a request took. `FormExpressionCalculator.EvaluateMasterRuleSample` evaluates a master rule
over sample detail rows.

In DefineEditor, **Add FormRule** and double-clicking a rule open a rule dialog that sets the table, When, Condition,
trigger, enabled flag and message, checks both expressions as they are typed, and tries a sample against When and then
Condition. Its AI assistant drafts or explains the rule and writes the message translations into the form's Language
files when the dialog is confirmed. The expression editor now edits field expressions only. See
[Expressions and Rules](../definitions/expression-rules.md#writing-a-rule-in-plain-words), which also says
[what a before-save rule can trust](../definitions/expression-rules.md#what-a-rule-can-trust).

- **Background:** [ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### UI packages upgraded

Avalonia moves to 12.1.6, MudBlazor to 9.14.0 and Fluent UI Blazor to 5.1.0. `Polhem.UI.Avalonia` keeps its 12.0.0
minimum. Fluent UI 5.1.0 fixes the disposed-module call that `PolhemDataGrid` worked around, so the Fluent grid uses
`FluentDataGrid` again.

### Dialogs and the keyboard on the Blazor heads

On both UI packages, Escape closes a lookup opened from the row edit dialog, and closes a dialog while the focus has
fallen back to the page body, while the row edit dialog stays open. A Fluent UI dialog gives the focus back to the
control that had it when it closes. `PolhemDialog` (Fluent) now implements `IAsyncDisposable` to release its script
module.

### MySQL gives each existing row its own id when `sys_rowid` is added

With binary logging on, MySQL refuses a `NOT NULL` column with a `UUID()` default on a table with rows, so the column
was added with the empty GUID and every existing row shared one row id. The upgrade now fills each row with its own
GUID before restoring the default. The schema format goes to 3.

## Breaking changes

### Reference `Guid` columns default to the empty GUID

- **Affects:** every application on a database, at its first upgrade after updating, and code that builds SQL from
  `IDialectFactory.GetDefaultValueExpression(FieldDbType.Guid)`.
- **Before:** every `NOT NULL` `Guid` column defaulted to a generated GUID (`newid()`, `gen_random_uuid()`, `UUID()`,
  `SYS_GUID()`, `hex(randomblob(16))`). A row written without a reference column, such as `st_employee.user_rowid`,
  linked to a row that does not exist, where the framework reads `Guid.Empty` as "no link".
- **Now:** only `sys_rowid` keeps the generated default; every other `Guid` column defaults to the empty GUID, and
  `GetDefaultValueExpression(FieldDbType.Guid)` returns the empty GUID literal. `SchemaFormat.Current` is 3. The next
  upgrade changes the default of existing columns, in place or, on SQLite, by rebuilding the table; stored values are
  kept. A database upgraded by 1.16.0 is refused by the 1.15.0 tools.
- **Migrate:** nothing is required. On a large SQLite database, run `db upgrade --dry-run` first to see which tables
  will be rebuilt, and upgrade every tool that changes the database at the same time. Rows that already hold a random
  id in a reference column keep it; clear them with your own update where it matters.
- **Background:** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### Only `%` is a wildcard in `Contains`, `StartsWith` and `EndsWith`

- **Affects:** filters that pass `_` in the value of a `Contains`, `StartsWith` or `EndsWith` condition, and on SQL
  Server a value with `[`.
- **Before:** the value went into the `LIKE` pattern unescaped, so `_` matched any one character (`A_01` also matched
  `AB01`), and on SQL Server `[A]` matched any value holding an `A`.
- **Now:** `_`, the escape character and, on SQL Server, `[` match themselves; a typed `%` stays a wildcard.
  `ComparisonOperator.Like` is unchanged, since its caller writes the whole pattern.
- **Migrate:** use `%` where a filter relied on `_` matching one character, or `ComparisonOperator.Like` for a full
  pattern. See [List Query Conditions §5](../guides/list-query-conditions.md#5-text-matching).

### Saves that totals or rules read check the record

- **Affects:** API callers that save a form whose master value expressions or enabled before-save rules aggregate a
  detail table, with a payload the framework's clients do not send.
- **Before:** stored detail rows a partial payload left out were added only for tables a master value expression read,
  so a rule such as `Count(Lines) > 0` saw only the rows the caller sent. Several records in one payload, unchanged rows
  with rewritten values, detail rows of another record and a changed row id were not checked on a form without a
  permission model.
- **Now:** the tables both totals and before-save rules aggregate get their stored rows back, and a save is refused
  when the payload changes such a table's rows without the master row, holds more than one live record
  (`PolhemMessages.SaveOneRecordRequired`), carries a row of another record (`SaveDetailRecordMismatch`) or changes a
  row's `sys_rowid` (`SaveRowKeyChanged`). An unchanged master row takes its stored values, and a master row that is not
  stored is refused as `SaveConcurrencyConflict`.
- **Migrate:** save one record per call, carry the master row with its detail changes, and keep the row ids the read
  returned. A check that must hold against a caller writing its own payload belongs in `DoBeforeSave`.
- **Background:** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md),
  [ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### UI types only the framework's UI packages use are no longer public

- **Affects:** applications that call the shared UI rules, derive from the Blazor component bases or register the
  Blazor client without a host package.
- **Before:** these types and members were public.
- **Now:** they are internal and reach the framework's UI packages through `InternalsVisibleTo`; some are removed.

  | Package | Type or member | Now |
  |---------|----------------|-----|
  | `Polhem.UI.Core` | `FieldValueChangeCoordinator` | Internal; use `FormDataObject.FieldValueChangeApplied` and `FieldValueChangeFailed` |
  | `Polhem.UI.Core` | `CardListState`, `DateTimeFieldFormat`, `NumericFieldFormat`, `FieldValueFormatter`, `GridCellFormatter`, `FieldCaptionRules`, `FieldEditRules`, `GridColumnRules`, `LookupDisplay`, `LookupFieldRules`, `RelationOpenRules`, `ListSelectFields`, `FormDataGuard`, `FormLiveComputationEngine`, `ListPagingState` | Internal |
  | `Polhem.UI.Core` | `ListFilterState` | Removed; column filters are rows of the list's `QueryCriteria` (`ColumnFilterCriteria`) |
  | `Polhem.Web.Blazor` | `FormPageBase.Filters`, `GridControlBase.Filters`, `GridColumnFilterBase.Filters` | Removed; the grids take `ColumnFilters` |
  | `Polhem.Web.Blazor` | `PolhemBlazorText`, `FormScopeContext`, `IGridEditorSlot`, `PolhemShellText` | Internal |
  | `Polhem.Web.Blazor` | The protected members of the component bases (`FormPageBase`, `GridControlBase`, `FormLayoutPresenterBase`, the dialog, panel, query pane, column filter and shell bases) and the public members of `LookupPanelBase` | Internal; `FieldEditorBase` and the typed editor bases keep theirs |
  | `Polhem.Web.Blazor` | `IBlazorDefinitionOptions`, `IShellLanguageSwitcher`, `PolhemBlazorClientServiceCollectionExtensions` | Internal; call the Server or Wasm host package's registration |
  | `Polhem.Web.Blazor.Mud`, `.Fluent` | `FieldEditorFactory` | Internal |
  | `Polhem.Web.Blazor.Fluent` | `PolhemDataGrid` | Removed; Fluent UI 5.1.0 fixed the issue it worked around |

- **Migrate:** remove the calls, or copy the rule into the application. A new field editor still derives from
  `FieldEditorBase`. Update `Polhem.UI.Core`, `Polhem.Web.Blazor` and its UI and host packages together: they share
  internals, so mixing versions can fail at run time.
- **Background:** [ADR-059](../../../maintainers/adr/adr-059-blazor-shared-layer.md),
  [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)

### The object tree command and drag-and-drop types move to `Polhem.UI.Core`

- **Affects:** code that uses `ITreeNodeCommandProvider`, `ITreeNodeDragDropHandler`, `TreeNodeCommand` or
  `TreeNodeDropPosition`, such as a command provider for the Avalonia `ObjectTreeView`.
- **Before:** they were in `Polhem.Definition.ObjectTree`, in `Polhem.Definition`.
- **Now:** they are in `Polhem.UI.Core.Trees`, in `Polhem.UI.Core`. `ObjectTreeBuilder`, `ObjectTreeNode` and the rest
  of the object tree stay in `Polhem.Definition.ObjectTree`.
- **Migrate:** add `using Polhem.UI.Core.Trees;` and a reference to `Polhem.UI.Core` where the project has none.

### Members that ended in optional parameters take a parameter object or overloads

- **Affects:** code that calls or implements the members below, and assemblies compiled against `CreateLocal` or
  `CreateRemote` (source compatible for calls without payload options, binary incompatible).
- **Before:** each ended in optional parameters, or, for `ExpressionFunction`, described parameters with
  `System.Reflection.ParameterInfo`.
- **Now:**

  | Before | Now |
  |--------|-----|
  | `IDatabaseInitializer.UpgradeTables(options, dryRun, tableCompleted, tableNames)` | `UpgradeTables(new TableUpgradeRequest { Options, DryRun, TableCompleted, TableNames })` |
  | `IFormCommandBuilder.BuildSelect(tableName, selectFields, filter, sortFields, skip, take)`, on the interface and each provider builder | `BuildSelect(tableName, new FormSelectQuery { SelectFields, Filter, SortFields, Skip, Take })` |
  | `IFormCommandBuilder.BuildCount(tableName, filter = null)` | `BuildCount(tableName, filter)`; the filter is required and may be `null` |
  | `FormExpressionCalculator.EvaluateRuleSample` / `EvaluateFieldSample(..., values, timeZoneId = "")` | `(..., new ExpressionSample { Values, TimeZoneId })`; a sample with `DetailRows` throws `ArgumentException` |
  | `ExpressionFunction(name, returnType, IReadOnlyList<ParameterInfo>)`, `ExpressionFunction.Parameters` | `ExpressionFunction(name, returnType, IReadOnlyList<ExpressionParameter>)`; `Parameters` is a list of `ExpressionParameter` (name and type) |
  | `PolhemApiClient.CreateLocal(services, payloadOptions = null)`, `CreateRemote(endpoint, apiKey, payloadOptions = null)` | An overload without payload options and one that takes them; the second refuses `null` |

- **Migrate:** rewrite the calls as in the table and rebuild. A `new TableUpgradeRequest()` or `new FormSelectQuery()`
  means what the omitted optional parameters meant.
- **Background:** [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)

### Requests to Claude default to medium effort

- **Affects:** hosts of `Polhem.AI.Claude` that do not set `ClaudeChatOptions.Effort`.
- **Before:** `Effort` defaulted to `ClaudeEffort.High`.
- **Now:** it defaults to `ClaudeEffort.Medium`, the model's own default on Claude Opus 5.5. Requests answer faster,
  and a hard request may get a shorter reasoning pass.
- **Migrate:** set `Effort = ClaudeEffort.High` to keep the previous behavior.
