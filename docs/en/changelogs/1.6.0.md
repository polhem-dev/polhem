# Polhem 1.6.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.6.0.md)

This file holds the details behind the `[1.6.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version gives `Polhem.Api.Client` one entry point, `PolhemApiClient`, which owns the connection and the
signed-in identity and hands out the connectors. It breaks the public API of `Polhem.Api.Client`, `Polhem.UI.Core` and
`Polhem.Web.Blazor.Server`. From this version on, a 1.x minor version may do that, with every break listed together
with its migration step; a patch version may not. Strict semantic versioning starts at 2.0. The policy and its reasons
are in [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md). Reference the packages with a
range that stays within one minor version, for example `[1.6,1.7)`. The wire format is the one of 1.5.0: a 1.5.0
client and a 1.6.0 server, or the other way round, talk to each other; only code that compiles against the client
packages has to change.

- **A console app, service or tool that creates connectors itself:**
  [Connectors come from `PolhemApiClient`](#connectors-come-from-polhemapiclient),
  [`ApiClientInfo` is removed](#apiclientinfo-is-removed) and
  [A connector calls with its client's current sign-in](#a-connector-calls-with-its-clients-current-sign-in).
- **A desktop head on `ClientInfo`:** keep your code, and replace `ApiClientInfo.SupportedConnectTypes` and
  `ApiClientInfo.ConnectType` with the members of the same name on `ClientInfo`
  ([`ApiClientInfo` is removed](#apiclientinfo-is-removed)); see also
  [`ClientInfo.ApplyLoginResult` always discards the cached definitions](#clientinfoapplyloginresult-always-discards-the-cached-definitions).
- **A Blazor Server host:** [Blazor Server injects a `PolhemApiClient` per circuit](#blazor-server-injects-a-polhemapiclient-per-circuit).

## New features and changes

### One client owns the connection and the identity

`PolhemApiClient` is created once, in process with `PolhemApiClient.CreateLocal(services)` or over HTTP with
`PolhemApiClient.CreateRemote(endpoint, apiKey)`, and hands out the connectors (`client.System`, `client.AuditLog`,
`client.Form(progId)`):

```csharp
var client = PolhemApiClient.CreateRemote("https://host/api", apiKey);
await client.System.LoginAsync(userId, password);
await client.System.EnterCompanyAsync(companyId);
var data = await client.Form("Employee").GetDataAsync(rowId);
```

The sign-in stores the access token, the transmission key and the user's time zone in the client's session as one
`ApiSessionCredentials`, replaced as a whole. Every connector then calls with the token, transmission key and time
zone of that sign-in, with no token to pass around. Each call reads the credentials once at its start, so a call cannot
send one sign-in's token with another's key.

- **Several servers in one process.** Each client has its own endpoint, API key and identity, so one process can call
  several servers, each through a client of its own.
- **`Form(progId)` returns a new connector each time.** Creating one is cheap and it holds no identity of its own.
- **The API key is read on every request.** Setting `PolhemApiClient.ApiKey` applies from the next call.
- **Desktop and Blazor.** `ClientInfo.ApiClient` is the desktop head's client. `PolhemBlazorOptions.ApiKey` and
  `PolhemBlazorOptions.DefaultLanguage` configure the client the Blazor Server package registers.
- **After `LoginAsync`, the same `ClientInfo.SystemApiConnector` can call `EnterCompanyAsync`;** it no longer has to
  be read again.

**Why.** Until 1.5.0 the state a .NET client called with had three owners: the static `ApiClientInfo` (endpoint, API
key, payload options, default language), an `ApiSessionContext` (transmission key, time zone), and each connector
(access token and transport, fixed when it was constructed). Callers chose between the in-process and the HTTP
constructor themselves and passed the token along. After a new sign-in, a connector still held by some caller sent its
old token sealed with the new key, and the server refused it. A multi-user host that forgot to give a connector its
own session fell back to a shared one and saw intermittent `ReplayRejected`. The design and the alternatives are in
[ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md).

**Performance.** A transport is now created for each call. A load test on 2026-10-10 (SQL Server, 20 virtual users,
Closed model) showed no measurable difference from 1.5.0: the gap between the two versions was smaller than the gap
between two runs of the same version. The figures and their conditions are in the pull request
([#104](https://github.com/polhem-dev/polhem/pull/104)).

## Breaking changes

### Connectors come from `PolhemApiClient`

- **Affects:** code that constructs connectors itself, reads `ApiConnector.AccessToken` or `ApiConnector.Provider`, or
  uses `LocalApiProvider` or `RemoteApiProvider`.
- **Before:** each connector had constructors that took an endpoint, or a service provider, with an access token, and
  the caller chose between the in-process and the HTTP one and passed the token along.
- **Now:** each connector has one constructor, which takes the client. The constructors that took an endpoint or a
  service provider with an access token are removed, `ApiConnector.AccessToken` and `ApiConnector.Provider` are
  removed, and `LocalApiProvider` and `RemoteApiProvider` are internal.
- **Migrate:** create one `PolhemApiClient` with `PolhemApiClient.CreateRemote(endpoint, apiKey)` or
  `PolhemApiClient.CreateLocal(services)`, sign in through `client.System.LoginAsync`, and take the connectors from
  it (`client.System`, `client.AuditLog`, `client.Form(progId)`), as in
  [One client owns the connection and the identity](#one-client-owns-the-connection-and-the-identity).
- **Background:** [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md)

### `ApiClientInfo` is removed

- **Affects:** code that reads or sets `ApiClientInfo`, including desktop heads that use
  `ApiClientInfo.SupportedConnectTypes` or `ApiClientInfo.ConnectType`, and callers of
  `ApiConnectValidator.ValidateAsync`.
- **Before:** the static `ApiClientInfo` held the endpoint, connection type, API key, payload options, supported
  connection types and default language for the whole process.
- **Now:** each setting lives on the client, or on the desktop's `ClientInfo`. `ApiConnectValidator.ValidateAsync`
  takes the allowed connection types as its second argument.
- **Migrate:**

  | Before | Now |
  |--------|-----|
  | `ApiClientInfo.Endpoint` | `PolhemApiClient.Endpoint` |
  | `ApiClientInfo.ConnectType` | `PolhemApiClient.IsLocal` (desktop: `ClientInfo.ConnectType`) |
  | `ApiClientInfo.ApiKey` | the argument of `CreateRemote`, or `PolhemApiClient.ApiKey` |
  | `ApiClientInfo.PayloadOptions` | `PolhemApiClient.PayloadOptions` |
  | `ApiClientInfo.SupportedConnectTypes` | `ClientInfo.SupportedConnectTypes` |
  | `ApiClientInfo.DefaultLanguage` | `PolhemApiClient.DefaultLanguage` (Blazor: `PolhemBlazorOptions.DefaultLanguage`) |

  Pass the allowed connection types to `ApiConnectValidator.ValidateAsync` as its second argument. Desktop heads keep
  `ClientInfo` with its signatures.
- **Background:** [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md)

### `ApiSessionContext` holds one `ApiSessionCredentials`

- **Affects:** code that uses `ApiSessionContext.Ambient` or sets `ApiSessionContext.ApiEncryptionKey` or
  `ApiSessionContext.UserTimeZoneId`.
- **Before:** an ambient session existed, and the transmission key and time zone were set one by one.
- **Now:** `ApiSessionContext.Ambient` and the setters of `ApiEncryptionKey` and `UserTimeZoneId` are removed. The
  session holds an `ApiSessionCredentials`, replaced as a whole by `SignIn` and `SignOut`.
- **Migrate:** sign in through the client's `System.LoginAsync`, which replaces the credentials; code that managed a
  session itself calls `SignIn` and `SignOut` with an `ApiSessionCredentials`.
- **Background:** [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md)

### Blazor Server injects a `PolhemApiClient` per circuit

- **Affects:** Blazor Server hosts on `Polhem.Web.Blazor.Server`.
- **Before:** components injected `PolhemApiConnectorFactory`, the API key was set through `ApiClientInfo.ApiKey`, and
  `FormPage` took an `AccessToken` parameter.
- **Now:** `PolhemApiConnectorFactory` is removed. `AddPolhemBlazor` registers a scoped `PolhemApiClient` per circuit.
  `UseRemoteProvider` takes the API key as its second argument. `FormPage` no longer has an `AccessToken` parameter: it
  calls as whoever signed in on the circuit's client.
- **Migrate:**
  1. Pass the API key to `UseRemoteProvider(endpoint, apiKey)` in place of setting `ApiClientInfo.ApiKey`.
  2. Inject `PolhemApiClient` where you injected `PolhemApiConnectorFactory`.
  3. Remove the `AccessToken` you passed to `FormPage`.
- **Background:** [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md)

### A connector calls with its client's current sign-in

- **Affects:** code that keeps a connector across a new sign-in, and hosts that serve several users.
- **Before:** a connector kept the access token it was constructed with.
- **Now:** a connector follows its client: one taken before a new sign-in calls with the new identity afterwards.
- **Migrate:** a host that serves several users gives each user a client of its own; the Blazor Server package
  registers one per circuit.
- **Background:** [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md)

### The reachability check no longer sends the API key

- **Affects:** applications that relied on `ApiConnectValidator` to report a wrong API key.
- **Before:** the reachability check sent the API key.
- **Now:** `ApiConnectValidator` pings without one, as the server answers `System.Ping` without a key. A wrong key now
  shows up on the configuration call that connecting makes.
- **Migrate:** handle a key error from the configuration call that connecting makes, not from the reachability check.

### `ClientInfo.ApplyLoginResult` always discards the cached definitions

- **Affects:** desktop heads that call `ClientInfo.ApplyLoginResult`.
- **Before:** it discarded the cached definitions and capabilities only when the token changed.
- **Now:** it always discards them.
- **Migrate:** nothing to change; expect the definitions and capabilities to load again after each sign-in.
