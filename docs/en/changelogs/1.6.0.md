# Polhem 1.6.0 — Detailed Release Notes

[繁體中文](../../zh-TW/changelogs/1.6.0.md)

This file is the detailed companion to the `[1.6.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). The changelog lists
each change in one line; this file keeps the reasons and the background.

## Why a minor version with breaking changes

This release breaks the public API of `Polhem.Api.Client`, `Polhem.UI.Core` and `Polhem.Web.Blazor.Server`. From this
version on, a 1.x minor version may do that, with every break listed in the changelog together with its migration step;
a patch version may not. Strict semantic versioning starts at 2.0. The policy and its reasons are in
[ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md). Reference the packages with a range that
stays within one minor version, for example `[1.6,1.7)`.

The wire format is the one of 1.5.0. A 1.5.0 client and a 1.6.0 server, or the other way round, talk to each other;
only code that compiles against the client packages has to change.

## How to upgrade

- **A console app, service or tool that creates connectors itself:** create one `PolhemApiClient` and take the
  connectors from it, as in the example below.
- **A desktop head on `ClientInfo`:** keep your code, and replace `ApiClientInfo.SupportedConnectTypes` and
  `ApiClientInfo.ConnectType` with the members of the same name on `ClientInfo`.
- **A Blazor Server host:** pass the API key to `UseRemoteProvider(endpoint, apiKey)` and inject `PolhemApiClient`
  where you injected `PolhemApiConnectorFactory`. Remove the `AccessToken` you passed to `FormPage`.

Each removed member and its replacement is listed in the changelog.

## One client owns the connection and the identity

Until 1.5.0 the state a .NET client called with had three owners: the static `ApiClientInfo` (endpoint, API key,
payload options, default language), an `ApiSessionContext` (transmission key, time zone), and each connector (access
token and transport, fixed when it was constructed). Callers chose between the in-process and the HTTP constructor
themselves and passed the token along. After a new sign-in, a connector still held by some caller sent its old token
sealed with the new key, and the server refused it. A multi-user host that forgot to give a connector its own session
fell back to a shared one and saw intermittent `ReplayRejected`.

`PolhemApiClient` replaces the three. It is created once, in process or over HTTP, and hands out the connectors:

```csharp
var client = PolhemApiClient.CreateRemote("https://host/api", apiKey);
await client.System.LoginAsync(userId, password);
await client.System.EnterCompanyAsync(companyId);
var data = await client.Form("Employee").GetDataAsync(rowId);
```

The sign-in stores the access token, the transmission key and the user's time zone in the client's session as one
`ApiSessionCredentials`, replaced as a whole. Each call reads it once at its start, so a call cannot send one sign-in's
token with another's key. One process can call several servers, each through a client of its own. The design and the
alternatives are in [ADR-053](../../../maintainers/adr/adr-053-api-client-composition-root.md).

### Behavior to know about

- **A connector follows its client.** A connector taken before a new sign-in calls with the new identity afterwards.
  A host that serves several users gives each user a client; the Blazor Server package registers one per circuit.
- **`Form(progId)` returns a new connector each time.** Creating one is cheap and it holds no identity of its own.
- **The API key is read on every request.** Setting `PolhemApiClient.ApiKey` applies from the next call.
- **The reachability check no longer sends the API key.** `ApiConnectValidator` pings without one, as the server
  answers `System.Ping` without a key. A wrong key now shows up on the configuration call that connecting makes.
- **`ClientInfo.ApplyLoginResult` always discards the cached definitions and capabilities.** Before, it did so only
  when the token changed.

## Performance

A transport is now created for each call. A load test on 2026-10-10 (SQL Server, 20 virtual users, Closed model)
showed no measurable difference from 1.5.0: the gap between the two versions was smaller than the gap between two runs
of the same version. The figures and their conditions are in the pull request
([#104](https://github.com/polhem-dev/polhem/pull/104)).
