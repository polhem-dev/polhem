# Polhem 1.4.0 — Detailed Release Notes

[繁體中文](../../zh-TW/changelogs/1.4.0.md)

This file is the detailed companion to the `[1.4.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). The changelog lists
each change in one line; this file keeps the reasons and the background.

> **The .NET SDK 10.0.400 or later is required.** The analyzers that ship inside the `Polhem.Definition` package are
> built against Microsoft.CodeAnalysis 5.9. An older compiler does not run them and reports `CS9057`, which fails the
> build of a project that sets `TreatWarningsAsErrors`. See "How to upgrade".

## Why a minor version

The release adds public API (object trees, the property grid) and removes three public types that the move to
Polhem.JsonRpc in 1.2.0 had left without a job: `Polhem.Api.Core.Messages.PayloadFormat`,
`Polhem.Core.Serialization.Gzip` and `Polhem.Api.Core.JsonRpc.JsonRpcException`.

The first two removals break source and binary compatibility. They are the fourth exception to semantic versioning
within 1.x, after 1.1.0, 1.2.0 and 1.3.0, and like those they have their own ADR,
[ADR-051](../../../maintainers/adr/adr-051-remove-jsonrpc-leftovers-in-1-x.md). Neither carries behavior an application
would lose: the format enum has the same members and values under another namespace, and `Gzip` was a thin wrapper of
`GZipStream` that nothing in the framework called.

`JsonRpcException` is removed under a rule added in this release: decision 4 of
[ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md) lets the framework's exception types
change in a minor version, provided the release notes list the change. The JSON-RPC error codes, and the code each
failure travels as, stay under semantic versioning, because clients compare against the numbers.

`TreeNodeAttribute` and `TreeNodeIgnoreAttribute` move from `Polhem.Core` to `Polhem.Definition`. That is a move of two
shipped types to another assembly, but nothing in the framework read them before this release, so applying them had no
effect; the move is listed under Changed rather than as a breaking change.

The wire is unchanged: a 1.4.0 client and a 1.3.x server, or the other way round, talk to each other.

## How to upgrade

1. **Build with the .NET SDK 10.0.400 or later.** Check with `dotnet --version`. A `global.json` that pins an older SDK
   band has to move as well. In CI, `actions/setup-dotnet` with `dotnet-version: 10.0.x` already resolves to a
   10.0.4xx SDK.
2. Update the Polhem packages to 1.4.0.
3. Where code names `PayloadFormat`, replace `using Polhem.Api.Core.Messages;` with `using Polhem.JsonRpc.Payload;`.
   The members and their values are the same.
4. Where code calls `Gzip`, use `System.IO.Compression.GZipStream` directly.
5. Where a business object throws `JsonRpcException` to show a message, throw `UserMessageException` instead. It
   travels under the same code (`-32099`), so clients see no difference.
6. Where a type of your own applies `[TreeNode]` or `[TreeNodeIgnore]`, replace `using Polhem.Core.Attributes;` with
   `using Polhem.Definition.Attributes;`.
7. Recompile everything that references the Polhem packages: assemblies built against an earlier 1.x that use the
   removed types fail at run time.

Servers and clients do not have to upgrade together.

## Object trees and the property grid

These are the building blocks DefineEditor now uses for its document trees and property panels. They are meant for
desktop tools.

- **`ObjectTreeBuilder`** (`Polhem.Definition.ObjectTree`) builds a UI-independent tree of `ObjectTreeNode` from an
  object graph, following the properties whose values carry `[TreeNode]`. It skips the properties that the collection
  base types declare, so the back references of collection items do not become nodes; `[Browsable(false)]` plays no
  part, because the definition types put it on their collection properties to keep them out of property grids. Each
  object becomes one node, which together with `ObjectTreeOptions.MaxDepth` stops cycles. `PropertyFilter`, `NodeBuilt`
  and `LabelTranslator` let the consumer narrow, extend and translate the tree. Commands
  (`ITreeNodeCommandProvider`) and drag-and-drop reordering (`ITreeNodeDragDropHandler`) are described UI-independently
  too, and `ObjectTreeView` in `Polhem.UI.Avalonia` shows the tree with both.
- **The `[TreeNode]` annotations of the definition types follow one rule for folders**: a collection is a folder when
  its owner has more than one annotated collection, and sits directly under the owner otherwise.
  `TreeNodeAnnotationGateTests` pins this rule, and that every annotated type labels itself the way its `ToString()`
  does.
- **`PropertyGridControl`** (`Polhem.UI.Avalonia`) edits an object through the ComponentModel annotations its
  properties carry: `[Category]`, `[Description]`, `[DisplayName]`, `[Browsable]`, `[DefaultValue]`,
  `[TypeConverter]` and `[PasswordPropertyText]`. A collection property opens in `CollectionEditDialog`, which edits
  copies of the items and replaces the collection's items only on OK. The control reads types through
  `TypeDescriptor`, which trimming does not preserve, so it is not for trimmed mobile heads.
- **Every browsable property of the definition types now declares `[Category]` and `[Description]`**, so a property
  grid groups and describes it; `EditorAnnotationGateTests` pins this. Collections that an editor shows as tree nodes
  are marked `[Browsable(false)]`. None of these attributes changes the XML or the wire.

## Fixed

- **The signed-in user's culture applies again under Avalonia 12.1.** Avalonia 12.1
  ([AvaloniaUI/Avalonia#21627](https://github.com/AvaloniaUI/Avalonia/pull/21627)) writes the UI thread's live culture
  back after every dispatcher operation. `ClientInfo` sets the user's culture inside the async sign-in handler, and
  the runtime reverted that change at the next `await`, so an en-US account on a Chinese operating system saw Chinese
  captions and date formats. `ClientInfo` now also posts the culture to the caller's synchronization context, where a
  plain callback sets it. `Polhem.UI.Avalonia` accepts Avalonia 12.0.0 and later, so an application that moved to 12.1
  on its own was affected with 1.3.x as well. ([#95](https://github.com/polhem-dev/polhem/pull/95))

## Dependencies

- MessagePack 3.1.11, DynamicExpresso.Core 2.19.6, and the 10.0.12 releases of the `Microsoft.Extensions` packages the
  framework references. These are the lowest versions NuGet resolves for an application.
- The analyzers move to Microsoft.CodeAnalysis 5.9, which is why the SDK requirement rises. The version an analyzer is
  built against is the lowest compiler that can load it, so this raises the SDK for every project that references
  `Polhem.Definition`. ([#96](https://github.com/polhem-dev/polhem/pull/96))

## Samples and tools

- DefineEditor builds its trees with `ObjectTreeBuilder` and edits properties in `PropertyGridControl`, in place of
  hand-written tree nodes and property panels. Its categories and descriptions are translated into Traditional
  Chinese.
- Avalonia.DemoCenter adds a Property Grid case.
- The Avalonia heads run Avalonia 12.1 with Semi.Avalonia 12.1. The Northwind iOS head requires iOS 15.0, the lowest
  that the iOS workload of the .NET SDK 10.0.400 accepts. Xamarin.AndroidX.Core.SplashScreen stays at 1.0.1.15 in the
  Northwind Android head: 1.2.0.3 brings AndroidX Lifecycle 2.11, outside the range Avalonia.Android depends on, and
  the Android build fails. ([#95](https://github.com/polhem-dev/polhem/pull/95),
  [#96](https://github.com/polhem-dev/polhem/pull/96))
