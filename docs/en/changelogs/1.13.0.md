# Polhem 1.13.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.13.0.md)

This file holds the details behind the `[Unreleased]` entry in [CHANGELOG.md](../../../CHANGELOG.md), which becomes
`[1.13.0]` when it is released.

This version is not released yet. Several companies can now share one company database, separated row by row; the
Avalonia and Blazor heads share one `FormDataObject`, in `Polhem.UI.Core`; and the framework's business objects read the
session's company once per request. Its wire format is the one of 1.12.1.

## New features and changes

### One over-long audit value no longer loses its batch

Audit entries are written to the log database in batches of up to 100, in one transaction. Several values come straight
from an unauthenticated caller, such as the user id of a failed sign-in or a JSON-RPC method name. One value longer than
its column made SQL Server, PostgreSQL, MySQL and Oracle refuse the whole batch, and every other entry in it was lost, so a
caller could erase other users' audit records; a NUL character did the same on PostgreSQL. SQLite enforces neither, so this
did not show there.

String values are now cut to the width their column declares in the log table's `TableSchema`, and a NUL character in one
is replaced with U+FFFD. A batch the database still
refuses is retried one entry at a time, so only the entries it refuses go to the file fallback; two failures in a row are
taken for an outage, and the rest of the batch goes to the file without further attempts. The file fallback escapes a
backslash, a tab, a carriage return and a line feed in a value, and writes every other control character and the Unicode
line and paragraph separators as `\uXXXX`, so a value read back with a line reader stays on its own line.

### A table with a Binary column reads back over JSON

Since 1.0.0, a `DataTable` with a `Binary` column did not read back over the JSON body codec or the Plain format: the
column's default value, an empty `byte[]` written as base64, was read back as the string `""`, which a `byte[]` column
rejects. The server answered with an internal error. A form with a Binary column could be opened for a new record, but
a JSON client, such as polhem-connector-js, could not save it, and a .NET client that declares the `json` codec could
not even read the new record. MessagePack was not affected.

A column's default value is now read back against the column's type, the way its cells are. The same change keeps a
date-shaped default of a text column as text; before, it came back as a reformatted date.

### The database initializer writes through repositories

The `db seed` and `db upgrade` commands no longer build SQL in `Polhem.Hosting`. The first administrator, company and
access are written by the new framework repository `IAdministratorSeedRepository`, and the rows an upgrade gives a
company are found and assigned by `ICompanyRowAssignmentRepository`; both are created through
`IRepositoryFactory.Create<T>`. `ICompanyRepository` gains `GetCompanyDatabases`, which lists every company of a common
database with its database item. With the framework's own repository factory and router, the commands behave as before.

Under [ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md) a repository contract may gain a
member in a minor version, and implementers derive from the framework's implementations:

- A host that implements `ICompanyRepository` itself adds `GetCompanyDatabases`.
- A host whose repository factory does not derive from `RepositoryFactory` creates `IAdministratorSeedRepository` and
  `ICompanyRowAssignmentRepository` in `Create<T>`; without them, `db seed-admin` and `db upgrade` fail and say which
  repository is missing.
- The seed now reaches the common database through the router's `Common` scope rather than the literal `common` item, so
  a replaced router decides where it goes.

## Breaking changes

### Companies can share a company database

- **Affects:** every deployment with company tables, and hosts with company table schemas of their own (`ft_*` and copies
  of the framework's `st_*` company tables).
- **Before:** each company was kept apart only by having a database of its own; companies that named the same
  `CompanyDatabaseId` saw, changed and deleted each other's rows.
- **Now:** every table of a `company` form schema carries `sys_company_id`, and its unique index starts with it. The form
  repository stamps the session's company on every row it inserts and confines every read, update and delete to it; a
  relation join between two company forms also matches the company. The framework's own company-database queries
  (departments, employees, roles and grants, audit rules) read only the company's rows. Single-company databases carry
  the column too, holding one value. A row whose `sys_company_id` is empty belongs to no company and no company sees it.
- **Migrate:**
  1. Add the column to your company table schemas: `db add-company-column` (or `--dry-run` first) adds it, and
     company-led unique indexes, to the schemas that lack it.
  2. Run `db upgrade`. It stops before changing anything while a schema still lacks the column or a company id is not in
     its stored form, upgrades the tables, then gives the rows with no company the one company whose database they are
     in. Rows in a database several companies share are reported and left for you to assign.
  3. Rows you insert with SQL of your own, such as role grants, carry `sys_company_id` (see
     [Permission and Authorization §3](../security/permission-authorization.md#3-grant-roles)).
- **Background:** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md),
  [Database Settings §5.5](../database/database-settings-guide.md#55-companies-sharing-a-company-database)

### Hand-written repository SQL is bound to the company

- **Affects:** custom repositories with SQL of their own, and code that builds a `DataFormRepository` itself.
- **Before:** a repository's `CreateDbAccess()` returned an access that ran any statement against the whole database.
- **Now:** in a company-bound repository, `CreateDbAccess()` is bound to the session's company
  (`DbAccess.BindCompany`). Every statement it runs must contain `{@CompanyId}` (`CommandTextVariable.CompanyId`), which
  becomes a parameter carrying the company; one without it is refused when it runs. The check sees only that the
  placeholder is present, not that each company table is compared with it. A bound access also refuses every stored
  procedure call, which cannot carry the placeholder, so a company-bound repository can no longer call a stored
  procedure on its company database. `CreateDbAccess(databaseId, companyId)` binds one explicitly for code with no
  session. The POLHEM3004 analyzer reports a repository that takes its access another way (the context's
  `DbAccessFactory`, an `IDbAccessFactory`, `new DbAccess(...)`), which would not be bound. `DataFormRepository` refuses
  to be built for a company form without a company.
- **Migrate:**
  1. In each statement on a company table, compare `sys_company_id = {@CompanyId}` (for every company table the
     statement reads, joins included), and write `{@CompanyId}` into the column of a row you insert.
  2. Replace a database access taken from `IDbAccessFactory` or `new DbAccess(...)` in a repository with
     `CreateDbAccess()`.
  3. Build a `DataFormRepository` for a company form with the constructor that takes a company id.
  4. Replace a stored procedure call on a company database with a statement that names `{@CompanyId}`.
- **Background:** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md),
  [Customising the Repository for a ProgId](../guides/development-cookbook.md#customising-the-repository-for-a-progid)

### Company-database methods take a company id, and company ids are lowercase

- **Affects:** callers and implementations of `IDepartmentRepository.GetDepartments`,
  `IEmployeeRepository.GetByUserRowId`, `IRolePermissionRepository.GetRoleGrants` / `GetUserRoles`,
  `IAuditRuleRepository.GetRules` and `IEmployeeContextResolver.Resolve`; deployments whose company ids hold uppercase
  letters or other characters.
- **Before:** these methods took a database id only, and a company id was stored as written.
- **Now:** each takes the company id as well, which its query filters on. Company ids are stored in lowercase, up to
  `CompanyInfo.CompanyIdMaxLength` ASCII letters and digits (`CompanyInfo.NormalizeId`, `CompanyInfo.IsValidId`).
  `EnterCompany` accepts any case and binds the session to the stored form.
- **Migrate:**
  1. Pass the company id to these methods, and add the parameter to your own implementations.
  2. Rename company ids that are not lowercase letters and digits in `st_company` and every place the id is stored
     before running `db upgrade`, which reports them and stops.
- **Background:** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md)

### `FormDataObject` moves to `Polhem.UI.Core`

- **Affects:** code that names `FormDataObject`, `FieldValueChangedEventArgs` or `RowChangedEventArgs`, in an Avalonia
  head or a Blazor head, code that constructs a `FormDataObject` itself, and a class derived from the Avalonia
  `FormDataObject`.
- **Before:** each head had its own copy: `Polhem.UI.Avalonia.DataObjects.FormDataObject` took an
  `IFormApiConnector`, and `Polhem.Web.Blazor.DataObjects.FormDataObject` took the API client's `FormApiConnector`.
  The Avalonia copy took the time zone of a new row's dates from the `IUserContext` in `UIServices.Provider`; the
  Blazor copy took it from its connector's client.
- **Now:** one type, `Polhem.UI.Core.DataObjects.FormDataObject`, takes an `IFormApiConnector` and, optionally, a
  function that returns the signed-in user's IANA time zone id. Without that function, a new row's dates default to
  today in UTC. `FormView`, `FormPage` and the related-record dialog pass the user's time zone, so a form opened
  through them behaves as before. The type is sealed, as the Blazor copy was; the Avalonia copy could be
  derived from. `FormLiveComputation` stays in each head.
- **Migrate:**
  1. Replace the namespaces:

     | Before | Now |
     |--------|-----|
     | `Polhem.UI.Avalonia.DataObjects.FormDataObject` | `Polhem.UI.Core.DataObjects.FormDataObject` |
     | `Polhem.Web.Blazor.DataObjects.FormDataObject` | `Polhem.UI.Core.DataObjects.FormDataObject` |
     | `Polhem.UI.Avalonia.DataObjects.FieldValueChangedEventArgs` | `Polhem.UI.Core.DataObjects.FieldValueChangedEventArgs` |
     | `Polhem.Web.Blazor.DataObjects.FieldValueChangedEventArgs` | `Polhem.UI.Core.DataObjects.FieldValueChangedEventArgs` |
     | `Polhem.UI.Avalonia.DataObjects.RowChangedEventArgs` | `Polhem.UI.Core.DataObjects.RowChangedEventArgs` |
     | `Polhem.Web.Blazor.DataObjects.RowChangedEventArgs` | `Polhem.UI.Core.DataObjects.RowChangedEventArgs` |

     Code that also uses `FormLiveComputation` keeps the head's `DataObjects` namespace as well.
  2. If you construct a `FormDataObject` with a connector and new rows should default to the user's date, pass the
     time zone. In an Avalonia head:

     ```csharp
     var dataObject = new FormDataObject(schema, connector,
         () => UIServices.Get<IUserContext>()?.User?.TimeZone ?? string.Empty);
     ```

     In a Blazor component, pass the circuit's own, never a process-wide one:

     ```csharp
     var dataObject = new FormDataObject(schema, Client.Form(progId),
         () => Client.Session.Credentials.UserTimeZoneId);
     ```
  3. A class derived from the Avalonia `FormDataObject` no longer compiles. Hold a `FormDataObject` instead and
     subscribe to its events.
- **Background:** [ADR-054](../../../maintainers/adr/adr-054-front-end-decoupled-from-api-client.md), under
  "Implementation evolution".

### One request reads the session's company once

- **Affects:** hosts that implement `ICompanyAuthorizationService`, `IScopeResolver`, `IRepositoryDatabaseRouter`,
  `IBusinessObjectFactory` or `IRepositoryTypeResolver`; hosts that override
  `RepositoryFactory.CreateFormRepositoryCore`; code that relied on a company-bound repository throwing
  `InvalidOperationException` when the session entered another company while it was being built; and host business
  objects and form plugins that read the session's company themselves, or keep a business object past its call.
- **Before:** within one request, the authorization check, the record scope, the database router, the company a
  repository stamps rows with and the customization each read the session's company through the access token. A user
  with access to two companies could switch the token between them while sending requests, and a request could be
  authorized with one company's roles and then read or write the other company's data.
- **Now:** the business object factory reads the session's company scope once per call and the business object keeps it
  as `CompanyScope`. Authorization, record scope, routing, repositories and business objects it calls all take that
  snapshot. These members are added:

  | Type | Added member |
  |------|--------------|
  | `ICompanyAuthorizationService` | `Can(SessionCompanyScope, string, PermissionActions)` |
  | `IScopeResolver` | `ResolveFilter(SessionCompanyScope, string, PermissionActions, FormSchema)` |
  | `IRepositoryDatabaseRouter` | `Resolve(DbScope, SessionCompanyScope)` |
  | `IBusinessObjectFactory` | `CreateBusinessObject(Guid, string, bool, SessionCompanyScope)` |
  | `IRepositoryTypeResolver` | `Resolve(string customizeId, string progId)` |
  | `IRepositoryFactory` | `CreateFormRepository<T>(Guid, string, SessionCompanyScope)` |
  | `IRepositoryContext`, `IBusinessObjectContext` | `CompanyScope` (default `null`) |
  | `RepositoryFactory` | `CreateFormRepositoryCore(Guid, string, SessionCompanyScope)` |
  | `BusinessObject`, `FormBusinessPlugin` | `CompanyScope` |
  | `BusinessObjectFactoryExtensions` | `CreateFormBO` and `CreateSystemBO` overloads that take a `SessionCompanyScope` |

  The access-token overloads remain and read the session once. A company-bound repository takes its database and its
  company from one read and no longer throws when the company changes during construction.
- **Migrate:**
  1. In an implementation of one of the interfaces above, add the new member. The access-token member can read the
     session once and call it, as the framework's implementations do.
  2. In a `RepositoryFactory` subclass that overrides `CreateFormRepositoryCore(Guid, string)`, override the overload
     that takes a `SessionCompanyScope` too; the framework's business objects create their repositories through it.
  3. In a business object of your own, read the current company from `CompanyScope` rather than from
     `SessionInfoService.Get(AccessToken)`, pass `CompanyScope` to `Can` and `ResolveFilter`, and pass it to
     `CreateFormBO` / `CreateSystemBO` when you call another business object. A form plugin does the same with its
     own `CompanyScope`.
  4. Create a new business object for each call. One kept past its call goes on acting for the company and roles it
     started with after the session leaves the company, signs out or expires.
- **Background:** [ADR-063](../../../maintainers/adr/adr-063-one-company-scope-per-request.md)
