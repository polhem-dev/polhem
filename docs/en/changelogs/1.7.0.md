# Polhem 1.7.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.7.0.md)

This file holds the details behind the `[1.7.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). This version is not
released yet; until it is, the changelog lists it under `[Unreleased]`.

This version separates the front ends and the API client from the server: a front end reaches its backend through
contracts and no longer carries the transport, and the API client no longer carries the server's dispatcher. The wire
format is the one of 1.6.0, so a 1.6.0 client and a 1.7.0 server, or the other way round, talk to each other.

## New features and changes

### Forms that run without a Polhem backend

`FormView` and `ListView` run on the schema, layout and connector the host sets, so an application can show forms
over its own data. The pieces are:

- `IFormApiConnector` and `IFormApiConnectorFactory` (`Polhem.Api.Contracts`): the form operations a front end calls.
  `FormApiConnector` implements them over a Polhem backend; an application can implement them over its own data.
- In `Polhem.UI.Core`: `UIServices`, which holds the services a front end resolves; `IUserContext`;
  `IFormDefinitionSource` with `StorageDefinitionSource`, which reads definitions from an `IDefineStorage`; and the
  response types `FormListResult`, `FormDataResult` and `FormDeleteResult`.

### New package `Polhem.UI.ApiBridge`

Joins a front end to a Polhem backend: `AddPolhemUIApiBridge` registers `FormApiConnectorFactory`,
`ApiFormDefinitionSource` and `ClientUserContext`. A head that talks to a backend references it; how to switch over is
under [Front ends no longer reference the API client](#front-ends-no-longer-reference-the-api-client).

### New package `Polhem.Api.Server`

The dispatcher setup, authorization and access control that only the server runs. `Polhem.Hosting` references it, so a
host built with `AddPolhemFramework` gets it without a change; see
[The server side of the API moves to Polhem.Api.Server](#the-server-side-of-the-api-moves-to-polhemapiserver).

### `Polhem.Web.Blazor.Server` references `Polhem.UI.Core`

The Blazor Server package shares the form binding and capability types with the desktop front ends.

## Breaking changes

### Front ends no longer reference the API client

- **Affects:** every desktop, mobile or browser head built on `Polhem.UI.Core` or `Polhem.UI.Avalonia`, and code that
  uses `FormValueBinding`, `FormDataGuard` or the capability resolver.
- **Before:** `Polhem.UI.Core` referenced `Polhem.Api.Client`, held `ClientInfo` and the endpoint storage, and the
  form views found their connector and definitions through `ClientInfo`.
- **Now:** `Polhem.UI.Core` and `Polhem.UI.Avalonia` depend only on the contracts in `Polhem.Api.Contracts`. The
  services they need come from `UIServices.Provider`, and the connection pieces live in `Polhem.UI.ApiBridge`.
- **Migrate:**
  1. In a head that talks to a Polhem backend, reference `Polhem.UI.ApiBridge`, and at startup set
     `UIServices.Provider = new ServiceCollection().AddPolhemUIApiBridge().BuildServiceProvider();`.
     Without it, `FormView`, `ListView` and the lookup dialog have no connector, definitions or user context.
  2. Update the namespaces of the types that moved:

     | Type | Before | Now |
     |------|--------|-----|
     | `ClientInfo`, `IEndpointStorage`, `IApiKeyStorage`, `FileEndpointStorage` | `Polhem.UI.Core` | `Polhem.UI.ApiBridge` |
     | `FormValueBinding`, `FormDataGuard` | `Polhem.Api.Client` | `Polhem.UI.Core` |
     | `ElementCapabilityResolver`, `IElementCapabilityResolver`, `FieldCapability` | `Polhem.Api.Client.Permissions` | `Polhem.UI.Core.Permissions` |

  3. `FormView.FormConnector`, `ListView.FormConnector`, `FormDataObject`, `LookupPanel.Bind` and
     `LookupDialog.ShowAsync` take `IFormApiConnector`. Code that passes a `FormApiConnector` keeps compiling.
     An override of `ResolveFormConnector` returns `IFormApiConnector?`. `FormDataGuard.RequireConnector` is generic.
  4. Replace `FormView.DefinitionLoader` and `ListView.DefinitionLoader` with `DefinitionSource`
     (`IFormDefinitionSource`). Remove overrides of `ResolveLang`: the definition source decides the language.
  5. Remove uses of `FormView.AccessToken`, `ListView.AccessToken` and `ResolveAccessToken`; nothing read them, since
     the client's session holds the token. Code in a view subclass that read `ClientInfo` uses `ResolveUserContext`.
  6. `IUIViewService` and `ClientInfo.UIViewService` are removed. Call
     `ClientInfo.InitializeAsync(SupportedConnectTypes)` in place of
     `ClientInfo.InitializeAsync(IUIViewService, SupportedConnectTypes)`; when it returns `false`, show the connection
     setup yourself and then call `ClientInfo.InitializeAsync(endpoint)`.
- **Background:** [ADR-054](../../../maintainers/adr/adr-054-front-end-decoupled-from-api-client.md)

### The server side of the API moves to Polhem.Api.Server

- **Affects:** servers with a custom `IApiAuthorizationValidator`, hosts that build the dispatcher without
  `AddPolhemFramework`, code that calls `PolhemApiClient.CreateLocal` on a service provider it builds itself, logging
  configuration keyed on `Polhem.Api.Core`, and applications that used the server packages through
  `Polhem.Api.Client`.
- **Before:** `Polhem.Api.Core` held the dispatch, authorization and access control, so every API client, and every
  front end through `Polhem.UI.ApiBridge`, carried the server packages.
- **Now:** these move to `Polhem.Api.Server`, which depends on `Polhem.Api.Core` at the exact same version. The wire
  does not change.
- **Migrate:**
  1. Change the namespaces: `Polhem.Api.Core.Dispatch`, `Polhem.Api.Core.Authorization` and
     `Polhem.Api.Core.Validator` become `Polhem.Api.Server.Dispatch`, `Polhem.Api.Server.Authorization` and
     `Polhem.Api.Server.Validator`. A custom `IApiAuthorizationValidator` changes its `using`.
  2. A host that builds the dispatcher without `AddPolhemFramework` references `Polhem.Api.Server`.
  3. `PolhemApiClient.CreateLocal` reaches the in-process dispatcher through `IInProcessTransportFactory`, which
     `AddPolhemFramework` registers. A service provider built without it registers `InProcessTransportFactory`
     (`Polhem.Api.Server.Dispatch`) as `IInProcessTransportFactory`.
  4. Log categories follow the namespace: masked failures log under
     `Polhem.Api.Server.Dispatch.PolhemExceptionMapper`, and API key lookup warnings under
     `Polhem.Api.Server.Dispatch.PolhemObjectFactory`. Update a `Logging:LogLevel` filter or sink route keyed on
     `Polhem.Api.Core`.
  5. `Polhem.Api.Client` (and so `Polhem.UI.ApiBridge`) no longer brings `Microsoft.Extensions.Logging.Abstractions`,
     `Polhem.JsonRpc.Server` or `Polhem.JsonRpc.Payload.Server`. An application that used them through it references
     them itself.
- **Background:** [ADR-055](../../../maintainers/adr/adr-055-api-core-split-from-server.md)

### `FileHashValidator` is removed

- **Affects:** code that calls `Polhem.Core.Security.FileHashValidator`.
- **Before:** `FileHashValidator` checked a file against a SHA-256 hash. Nothing in the framework used it.
- **Now:** the type is removed.
- **Migrate:** compute the hash with `SHA256.HashData(stream)` and compare it with
  `CryptographicOperations.FixedTimeEquals`.

### `IDisplayName` is removed

- **Affects:** types that implement `Polhem.Core.IDisplayName`.
- **Before:** `TreeNodeAttribute.GetDisplayText` used `IDisplayName` when the formatted text was empty.
- **Now:** `IDisplayName` is removed, and `TreeNodeAttribute.GetDisplayText` falls back to `ToString()`.
- **Migrate:** override `ToString()` in place of implementing `IDisplayName`.
