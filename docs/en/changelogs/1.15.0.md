# Polhem 1.15.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.15.0.md)

This file holds the details behind the `[1.15.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

The table upgrade now records each table's upgrade in `st_table_upgrade`, together with a schema format that versions
what the upgrade does. A tool of an older format no longer undoes a newer one, and a table whose record says it is
current is not compared with the database, which makes a start-up that changes nothing much cheaper. The wire format is
the one of 1.14.0.

## New features and changes

### Each table upgrade is recorded, and an older tool leaves a newer database alone

Every database the upgrade runs on gets a table `st_table_upgrade` with one row per table: the status of its last
upgrade (`Upgrading`, `Succeeded`, `Failed` or `Verified`), the error of a failed one, the definition last applied and
the schema format and framework version of the tool. `SchemaFormat.Current` is the format of this build, and
`TableUpgradeRecordStore` reads the records (`GetRecord`, `GetHighestFormatVersion`, `DescribeNewerFormat`).

Before it changes anything, the upgrade reads the highest format recorded in the database. When a newer format upgraded
the database, `db upgrade` and `IDatabaseInitializer.UpgradeTables` report it once and skip its tables, and
`IDatabaseRepository.UpgradeTableSchema`, `TableSchemaBuilder.Execute` and `TableUpgradeOrchestrator.Execute` throw.
Nothing in that database is changed; upgrade it with the newer tool. The guide is
[Database Schema Upgrade Guide §11](../database/database-schema-upgrade.md#11-upgrade-records-and-the-schema-format).

- **Background:** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### `db upgrade` reports what the records say

A table decided by its record shows `unchanged (upgrade record)`, a table whose previous upgrade failed or did not
finish says so on its line, and the summary counts the tables decided by their record. In code,
`TableUpgradeEntry.UnchangedByRecord` and `TableUpgradeEntry.PreviousStatus` carry the same. See
[Database Settings](../database/database-settings-guide.md).

## Breaking changes

### The upgrade trusts a table's record instead of comparing it

- **Affects:** deployments that change tables by hand and rely on the next upgrade to put them back, and code that
  calls `TableSchemaBuilder.Execute`, `IDatabaseRepository.UpgradeTableSchema` or `IDatabaseInitializer.UpgradeTables`
  with the default options.
- **Before:** every upgrade read each table's schema from the database's catalog and compared it with the definition.
- **Now:** `UpgradeOptions.CompareMode` defaults to `UpgradeCompareMode.Fast`. A table whose record says its last
  upgrade succeeded or found it matching, under the current schema format and with the definition as it is now, counts
  as unchanged without reading the catalog. A change made to such a table outside the framework is not found until the
  definition changes.
- **Migrate:** to compare every table with the database, run `db upgrade --full-compare`, or pass
  `new UpgradeOptions { CompareMode = UpgradeCompareMode.Full }`. The first upgrade after updating compares every table
  in full anyway, because no table has a record yet.
- **Background:** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)
