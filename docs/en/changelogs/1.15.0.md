# Polhem 1.15.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.15.0.md)

This file holds the details behind the `[1.15.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

The table upgrade now records each table's upgrade in `st_table_upgrade`, together with a schema format that versions
what the upgrade does. A tool of an older format no longer undoes a newer one, and a table whose record says it is
current is not compared with the database, which makes a start-up that changes nothing much cheaper. The upgrade also
follows four written principles: it keeps the data, takes the current definition as the target, never needs repeating,
and stops and reports when the data blocks it. A rebuild therefore keeps AutoIncrement numbers, and refuses what it
cannot recreate. A master field's expression can now add up its detail rows. The wire format is the
one of 1.14.0.

Applications on SQLite or Oracle should expect the first upgrade after updating to change their `Date` columns to the
new default, which on SQLite rebuilds those tables (see the breaking changes).

## New features and changes

### Each table upgrade is recorded, and an older tool leaves a newer database alone

Every database the upgrade runs on gets a table `st_table_upgrade` with one row per table: the status of its last
upgrade (`Upgrading`, `Succeeded`, `Failed` or `Verified`), the error of a failed one, the definition last applied and
the schema format and framework version of the tool. `SchemaFormat.Current` is the format of this build, and
`TableUpgradeRecordStore` reads the records (`GetRecord`, `GetHighestFormatVersion`, `DescribeNewerFormat`).

Before it changes anything, the upgrade reads the highest format recorded in the database. When a newer format upgraded
the database, `db upgrade` and `IDatabaseInitializer.UpgradeTables` report it once and skip its tables, and
`IDatabaseRepository.UpgradeTableSchema`, `TableSchemaBuilder.Execute` and `TableUpgradeOrchestrator.Execute` throw.
Nothing in that database is changed; upgrade it with the newer tool. The guide is
[Database Schema Upgrade Guide §11](../database/database-schema-upgrade.md#11-upgrade-records-and-the-schema-format).

- **Background:** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### `db upgrade` reports what the records say

A table decided by its record shows `unchanged (upgrade record)`, a table whose previous upgrade failed or did not
finish says so on its line, and the summary counts the tables decided by their record. In code,
`TableUpgradeEntry.UnchangedByRecord` and `TableUpgradeEntry.PreviousStatus` carry the same. See
[Database Settings](../database/database-settings-guide.md).

### A rebuild keeps the rows, their numbers and a renamed column

A rebuild copies every column, those the definition does not declare included, and now also the AutoIncrement
column: SQL Server, PostgreSQL, MySQL and Oracle used to number the rows again. Each dialect continues the sequence after
the old table's last number, except MySQL, which continues after the highest copied value, so a number freed at the end
of the table can be handed out again. A rebuild that also renames a column copies the old column into the new name,
where it used to be refused.

An undeclared column with an expression default has no literal form to restate; it gets the built-in default of its
type, and the plan lists it in its warnings. The principles are in the
[Database Schema Upgrade Guide §1](../database/database-schema-upgrade.md#upgrade-principles).

### An upgrade no longer repeats itself

After an upgrade, comparing the definition with the table again now finds no difference on every database, so the next
start-up plans nothing. Before, these were changed again on every upgrade: a default on a SQL Server `DECIMAL`,
`NUMERIC`, `SMALLINT`, `BIGINT` or `TINYINT` column; a decimal default on MySQL; and a `Currency` column on SQLite, which
on SQLite meant a rebuild every time. A rebuild on Oracle could not run at all and now does.

### SQLite adds a column that needs a default to a table with rows

SQLite refuses `ADD COLUMN` for a `NOT NULL` column whose default is an expression or missing once the table has rows,
so adding a `Date`, `DateTime`, `Guid` or `Binary` column to such a table failed. The upgrade now adds these columns by
rebuilding the table.

### A language file is found whatever case the request names it in

On a case-sensitive file system, a request for the `common` namespace missed `Common.Language.xml`, and the shared cache
then answered every spelling with the miss. Reading, saving and watching a language file now find the file, and the
language folder, that match ignoring case; a new namespace saved in another case goes into the existing folder.

### A master field adds up its detail rows

A master table's `ValueExpression`, and a `FormRule` on the master table, can call `Sum(Table.field)`, `Count(Table)`,
`Min(Table.field)` and `Max(Table.field)` over a detail table of the same form:

```xml
<FormField FieldName="total_amount" DbType="Currency" NumberKind="Amount" ReadOnly="true"
           ValueExpression="Sum(OrderDetail.amount)" />
<FormRule RuleId="detail_required" Condition="Count(OrderDetail) &gt; 0" Message="At least one line is required." />
```

Each detail value is rounded to its own field's decimals before the sum. On save, the server computes the detail rows
first and sums every row of the record, adding the stored rows a payload does not carry; a payload that changes rows of
such a detail table must carry the master row, or the save is refused (`PolhemMessages.SaveMasterRowMissing`). The
Avalonia and Blazor heads recompute the master as a line is edited, added, deleted or its edit is cancelled
(`FormLiveComputationEngine.RecomputeAggregates`, `FormDataObject.RowEditCanceled`). `ValidateExpressions` and
DefineEditor report an aggregate that cannot work. Document drafting and the form workbook's formula column describe
the aggregates, so a drafted form keeps its totals. The guide is
[Expressions and Rules](../definitions/expression-rules.md#totals-over-detail-rows).

- **Background:** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md)

## Breaking changes

### The upgrade trusts a table's record instead of comparing it

- **Affects:** deployments that change tables by hand and rely on the next upgrade to put them back, and code that
  calls `TableSchemaBuilder.Execute`, `IDatabaseRepository.UpgradeTableSchema` or `IDatabaseInitializer.UpgradeTables`
  with the default options.
- **Before:** every upgrade read each table's schema from the database's catalog and compared it with the definition.
- **Now:** `UpgradeOptions.CompareMode` defaults to `UpgradeCompareMode.Fast`. A table whose record says its last
  upgrade succeeded or found it matching, under the current schema format and with the definition as it is now, counts
  as unchanged without reading the catalog. A change made to such a table outside the framework is not found until the
  definition changes.
- **Migrate:** to compare every table with the database, run `db upgrade --full-compare`, or pass
  `new UpgradeOptions { CompareMode = UpgradeCompareMode.Full }`. The first upgrade after updating compares every table
  in full anyway, because no table has a record yet.
- **Background:** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### A rebuild that would lose part of the table is refused

- **Affects:** databases where a table that needs a rebuild has an index the definition does not declare, or a column
  of a type the framework does not map.
- **Before:** the rebuild ran; it dropped such an index or failed partway on such a column.
- **Now:** the plan is refused before any statement runs. The error names the index or column, and the table and its
  rows stay as they were. `db upgrade` reports it on the table's line and goes on with the other tables; the
  single-table APIs throw.
- **Migrate:** declare the index or column in the definition, or drop it by hand, and upgrade again. See
  [When the existing data blocks an upgrade](../database/database-schema-upgrade.md#when-the-existing-data-blocks-an-upgrade).

### A `Date` column defaults to midnight of the UTC day on SQLite and Oracle

- **Affects:** applications on SQLite or Oracle with `Date` columns.
- **Before:** the default stored the current instant: `CURRENT_TIMESTAMP` on SQLite, `SYS_EXTRACT_UTC(SYSTIMESTAMP)` on
  Oracle. A row that took the default did not match a filter on its own day.
- **Now:** the default is `(datetime('now', 'start of day'))` on SQLite and `TRUNC(SYS_EXTRACT_UTC(SYSTIMESTAMP))` on
  Oracle. A column with the old default reads back as a difference, so the first upgrade after updating changes it: in
  place on Oracle, and by rebuilding the table on SQLite. The rows keep their values, including a time of day the old
  default stored.
- **Migrate:** nothing is required. On a large SQLite database, run `db upgrade --dry-run` first to see which tables
  will be rebuilt. See [Database Dialect Differences](../database/database-dialect-differences.md).

### Language files that differ only in case are an error

- **Affects:** applications on a case-sensitive file system with two language files, or two language folders, whose
  names differ only in case.
- **Before:** one of them was read, depending on the spelling of the request.
- **Now:** reading or saving the language throws an `InvalidOperationException` that names the file or folder.
- **Migrate:** merge the two files or folders into one.
