# Polhem 1.12.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.12.0.md)

This file holds the details behind the `[1.12.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version is in progress. Its wire format is the one of 1.11.0.

## New features and changes

### Page buttons on lists

`ListView` used to read one server page without saying so, which left out every row beyond `PagingOptions.MaxPageSize`.
It now shows 50 rows at a time, with previous and next buttons, the current position and a choice of 50, 100 or 200 rows
per page. `ReloadAsync` stays on the page on screen, and returns to the last page that still has rows when the page came
back empty, such as after deleting its last row.

Blazor Server's `FormPage` behaves the same way.

The paging position lives in `ListPagingState` in `Polhem.UI.Core`, which both heads share. The new `PolhemUIText` keys
`PreviousPage`, `NextPage`, `PageNumber`, `PageNumberOfTotal` and `RowsPerPage` carry the text. A host that replaces
`UIText.Localizer` sees the English text for them until it declares them.

### Scrolling through the cards on a phone

On a narrow screen `ListView` shows cards without page buttons. It reads the next page when the user scrolls near the end
and appends it, keeping the scroll position and the selection. A row that an insert pushed onto the next page appears
once. The cards stop at 5000 rows with a notice, using the new `PolhemUIText` key `ListRowsLimited`.

`ReloadAsync` starts the cards over from the first page, so saving or deleting a record returns to the top. Crossing
between the narrow and wide widths also reads the first page again, in the same order.

### Sort a list by a column

Clicking a column header of `ListView` or `FormPage` moves that column through ascending, descending and back to the
default order, and reads the first page again in that order, so the sort covers every row and not only the page on
screen. The sorted header carries a mark. `Text` and `Binary` columns cannot be sorted. The compact card list on a phone
keeps the order but has no headers to click.

`GridControl` gains `OnSortRequested`, `SortFieldName` and `SortDirection`; without a handler its headers stay plain
text. `ListPagingState` gains `ToggleSort` and `CreateSort`.

### Lookups say when they show only some candidates

The `LookupPanel` of Avalonia and Blazor Server reads the first page of candidates, 100 rows by default, and left out the
rest without saying so. It now shows a notice with the number of rows shown and asks for a keyword, using the new
`PolhemUIText` key `LookupResultsTruncated`. A lookup does not page: the keyword search reaches the rows beyond the first
page. A slower answer to an earlier search no longer replaces the rows of a newer one.

### Stable paging and lookup order

`GetLookup` orders its candidates by the first lookup field that can be sorted, so a picker no longer lists them in
creation order. A `Text` or `Binary` field is passed over, and with no sortable field the order stays `sys_no`. The
caller cannot choose the order.

A paged `GetList` with an explicit sort now adds `sys_no`, or `sys_rowid` on a table without it, when the sort does not
name it. Rows that tie on a non-unique sort have a fixed order, so they no longer repeat or go missing across pages. An
empty sort is treated like no sort.

A page whose offset is too large to compute returns its columns and no rows, with `HasMore` false, on `GetList`,
`GetLookup` and the audit log queries. It used to fail or, at some page numbers, return rows from an earlier page.

### Open a relation field's record from a read-only form

On a record that Blazor Server's `FormPage` or Avalonia's `FormView` shows read-only, double-clicking a field that declares a `RelationProgId` opens the record
the field points at, read-only, in a dialog. For example, on a leave request the leave type opens that leave type.
Close returns to the leave request as it was. A relation field inside the dialog opens the next record in a dialog on
top.

The record opens only when the user holds `Read` on the related form's permission model: the page checks the
capability snapshot of the entered company before it asks the backend for anything, and otherwise names the form in
a notice. A related form without a permission model opens for everyone. The backend still decides: the dialog loads
the record through the related form's `GetData`, which checks the permission and the record scope.

Picking a value and viewing it are separate permissions. The lookup does not require `Read` on the related form, so a
user may hold a value they may not open.

A relation field with a value shows a hand cursor and the hint "Double-click to open this record" while the record is
read-only. While it is edited nothing changes: the field keeps its lookup button.

A relation column of a detail grid opens its record the same way: on a read-only record, double-click the cell, for
example an order line's product. While the record is edited a double-click on a row still opens the row's edit form.

On Avalonia the dialog is a native window under the desktop classic-window lifetime and an overlay on the browser,
iOS and Android heads, as the lookup dialog is. Inside it is a `FormView` over the related form, which fetches its
definitions from the same source as the view that opened it and says Close instead of Back. A `FormView` subclass can
replace both steps: `CreateRelatedView` builds the related view and `ShowRelatedViewAsync` presents it.

The pieces are public for a page of your own on Blazor Server:

- `RelatedRecordDialog` (`Polhem.Web.Blazor.Mud.Components`) shows one related record.
- `FormLayoutPresenter.OpenRelation` and `FormScope.OpenRelation` receive the record a field asks to open; without a
  handler the fields offer nothing.
- `RelationOpenRules` and `RelationTarget` (`Polhem.UI.Core.Fields`) hold the rules every front end shares: when a
  field offers it, which record it opens, and whether the user may read it.

`PolhemUIText` gains the keys `Close`, `OpenRelatedRecord` and `RelatedRecordDenied`, translated into Traditional
Chinese.

### Avalonia tints messages as warnings and failures as errors

`FormView`'s message bar used the error tint for everything it showed. It now tints a message the user can act on as a
warning: a missing required field, a validation message from the backend, a computed field that stopped computing, and
a related record the user may not open. Failures, such as a call that throws, keep the error tint. Blazor Server's `FormPage`
shows its notices with the warning tint.

### Deleting a record asks first

Delete on Avalonia's `ListView` and Blazor Server's `FormPage` used to delete the selected record at once. Both now ask
first, and the safe answer holds the focus. On Avalonia the question is a window on the desktop and an overlay in the
browser and on mobile.

An application that wants the old behavior sets `ConfirmDelete` to `false`: a parameter on `FormPage`, a styled
property on `ListView`, so a style setter also reaches the lists the shell creates. A `ListView` subclass can override
`ConfirmDeleteAsync` to ask its own way.

`PolhemUIText` gains the key `DeleteRecordPrompt`, translated into Traditional Chinese.

## Breaking changes

### The Blazor components move to MudBlazor, and the HTML controls are removed

The Blazor head's controls now come from a new package, `Polhem.Web.Blazor.Mud`, built on MudBlazor ([ADR-060](../../../maintainers/adr/adr-060-mudblazor-first-ui-package.md)). `Polhem.Web.Blazor.Server` is now only the host: the circuit client, the shell's registration and culture endpoint, and `PolhemAccessTokenProvider`.

**Who is affected:** every application that uses the Blazor components, and every site with styles of its own for them. The look changes too.

**What is removed:** from `Polhem.Web.Blazor.Server`, `FormPage`, `DynamicGrid`, `FormLayoutPresenter`, `GridControl`, the field editors, the lookup and row edit dialogs, `RelatedRecordDialog`, `PolhemLoginPanel`, `PolhemShellLayout`, `PolhemShellNavMenu`, `PolhemShellSignIn` and `polhem.css`, along with the `polhem-*` class names as a contract you can style against.

**How to migrate:**

1. Reference `Polhem.Web.Blazor.Mud` beside `Polhem.Web.Blazor.Server`, and call `builder.Services.AddPolhemMud()`.
2. In `App.razor`, replace the link to `polhem.css` with:

   ```html
   <link href="_content/MudBlazor/MudBlazor.min.css" rel="stylesheet" />
   <link href="_content/Polhem.Web.Blazor.Mud/polhem-mud.css" rel="stylesheet" />
   ```

   and add `<script src="_content/MudBlazor/MudBlazor.min.js"></script>` after `blazor.web.js`.
3. Change the `@using` lines:

   | Before | After |
   |--------|-------|
   | `Polhem.Web.Blazor.Server.Components` | `Polhem.Web.Blazor.Mud.Components` (`PolhemAccessTokenProvider` stays in the old namespace) |
   | `Polhem.Web.Blazor.Server.Controls` | `Polhem.Web.Blazor.Mud.Controls` |
   | `Polhem.Web.Blazor.Server.Controls.Editors` | `Polhem.Web.Blazor.Mud.Controls.Editors` |
   | `Polhem.Web.Blazor.Server.Shell` in `.razor` files | `Polhem.Web.Blazor.Mud.Shell` (`AddPolhemShell` and the other extensions stay in the old namespace) |

4. Without `PolhemShellLayout`, place one `PolhemMudProviders` in your layout.
5. Replace `DynamicGrid` with `GridControl`, setting `DataTable`, `FormTable` and `AllowEdit="false"`.
6. Replace rules that target `polhem-*` classes with a `MudTheme` passed to `PolhemMudProviders`.

Pages you write directly with MudBlazor components do not carry over to another UI package if you change later. Definition-driven pages do.

### The Blazor head splits into a shared layer and a host package

`Polhem.Web.Blazor.Server` now references a new package, `Polhem.Web.Blazor`, which holds what does not depend on a host or a UI framework ([ADR-059](../../../maintainers/adr/adr-059-blazor-shared-layer.md)). A host still references `Polhem.Web.Blazor.Server` alone, and behavior does not change.

**What breaks:** code that names the moved types. Update the `using` lines and the `@using` lines:

| Before | After |
|--------|-------|
| `Polhem.Web.Blazor.Server.DataObjects` | `Polhem.Web.Blazor.DataObjects` |
| `Polhem.Web.Blazor.Server.Controls.Editors.FieldEditorBase`, `IFieldEditor`, `FormScope`, `FormScopeContext` | `Polhem.Web.Blazor.Controls.Editors` |
| `Polhem.Web.Blazor.Server.Identity.CircuitUserContext` | `Polhem.Web.Blazor.Identity.BlazorUserContext` |
| `Polhem.Web.Blazor.Server.Components.CompactViewportObserver` | `Polhem.Web.Blazor.Components` |
| `Polhem.Web.Blazor.Server.Shell.PolhemShellHome`, `PolhemShellOptions`, `PolhemShellLanguage` | `Polhem.Web.Blazor.Shell` |

The other field editors derive from the value bases of the shared layer (`TextEditorBase`, `NumericEditorBase` and so on). `NumericEdit`, `TimeEdit` and `DateTimeEdit` no longer derive from `TextEdit`, and `TextEdit` loses its `InputMode`, `Pattern` and `Placeholder` overrides, so a subclass that overrode them renders its own input. `ButtonEdit` no longer derives from `TextEdit`, and `LookupPanel` and `LookupDialog` derive from new bases; their parameters are unchanged. `FormPage` now derives from `FormPageBase` in `Polhem.Web.Blazor.Components`; its parameters are unchanged. `GridControl` now derives from `GridControlBase`, and `GridEditMode` moves to `Polhem.Web.Blazor.Controls`, so code that names it adds that `using`. The constructor of `BlazorUserContext` takes the default language instead of `PolhemBlazorOptions`; `AddPolhemBlazor` registers it, so only code that constructs it itself changes.
