# Polhem 1.10.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/1.10.0.md)

This file holds the details behind the `[1.10.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version gives the Blazor Server head the field editors the Avalonia head has, with the same names, the same
contract and the same behavior, so a form is built and extended the same way in both. The rules the two heads share
move into `Polhem.UI.Core`. The wire format is the one of 1.9.0 plus the messages of the new `FieldValueChange` call,
so a 1.9.0 client and a 1.10.0 server, or the other way round, talk to each other; only the new call needs both sides
at 1.10.0.

## New features and changes

### Field editors for Blazor Server

`Polhem.Web.Blazor.Server.Controls.Editors` holds one component per `ControlType`: `TextEdit`, `MemoEdit`,
`NumericEdit`, `TimeEdit`, `DateTimeEdit`, `DateEdit`, `YearMonthEdit`, `CheckEdit`, `DropDownEdit` and `ButtonEdit`.
They carry the
names of the Avalonia field editors and implement the same `IFieldEditor` contract (`Bind`, `Unbind`,
`SetControlState`, `FieldName`, `FieldValue`), and they behave the same way:

- The value is committed when the user leaves the input or presses Enter, not per keystroke.
- The editor applies the schema field's metadata itself: `MaxLength`, `ListItems`, the number format.
- Whether it accepts input follows the form mode, the layout field's `ReadOnly` and its `AllowEditModes`.
- A value written by code, or a reload of the data object, refreshes the editor.
- `NumericEdit` shows the formatted value at rest and the full-precision value while focused, and keeps the last valid
  value when the input does not parse; `TimeEdit` stores `HH:mm`.

An editor binds through an explicit `Bind`, else its `DataObject` parameter, else an enclosing `FormScope`:

```razor
<FormScope DataObject="dataObject" FormMode="SingleFormMode.Edit">
    <TextEdit FieldName="emp_name" />
    <NumericEdit LayoutField="amountField" />
</FormScope>
```

A custom editor derives from `FieldEditorBase` and overrides `RefreshFromSource` and, when it needs schema metadata,
`ApplyMetadata`. `FieldEditorFactory.GetEditorType` maps a `ControlType` to its editor type.

The editors render the class `polhem-field-editor`, a modifier per editor (such as `polhem-field-editor--numeric`) and
`polhem-field-editor--readonly` when they do not accept input; the package ships no CSS. The read-only state of the
date, date-time and drop-down editors shows the value as text in the user's culture, as the Avalonia editors do.

`FormDataObject` gains what the editors need: `GetField` and `SetField` for a given row, `GetFormField` for a table
and field, and the events `FieldValueChanged`, `IsDirtyChanged` and `DataSetReplaced`. Writing the value a field
already holds no longer marks the object dirty.

### Lookup in Blazor Server

A `ButtonEdit` bound to a field with a `RelationProgId` runs the lookup flow of the Avalonia `ButtonEdit`: the input
shows the field's display fields (for example `D01 - Engineering`) and is read-only, the button opens `LookupDialog`,
the chosen row's `sys_rowid` and mapped fields are written through `FormDataObject.ApplyLookupSelection`, and Delete or
Backspace clears them through `ClearLookupSelection`. Without a `RelationProgId` the button raises `ButtonClick`.
`LookupFailed` reports a lookup that cannot load or a selection that cannot be written; without a handler the message
is shown as the input's tooltip.

`LookupDialog` is a modal overlay over `LookupPanel`, which has a search box, a list over the target form's lookup
layout and OK / Cancel; a double-click commits a row. The dialog takes the target schema and connector from its
`Schema` and `Connector` parameters, else from an `IFormDefinitionSource` and an `IFormApiConnectorFactory` registered
in the container, else from the circuit's `PolhemApiClient`, loading the schema the way `FormPage` loads its own. An
application with a Polhem backend registers nothing; one without registers its own source, scoped:

```csharp
builder.Services.AddScoped<IFormDefinitionSource, MyDefinitionSource>();
builder.Services.AddScoped<IFormApiConnectorFactory, MyConnectorFactory>();
```

`DynamicGrid` gains `OnRowActivated` (a double-click) and `SelectedRowId` (the row to highlight), which the panel uses.

### Live computation in Blazor Server

`FormPage` recomputes computed fields (`ValueExpression`) as the user edits and evaluates default-value expressions
for a new record, the way the Avalonia `FormView` does. The rules are the new `FormLiveComputationEngine` in
`Polhem.UI.Core`, which both heads now drive, so a value previewed in either head matches what the server writes on
save. It takes the expression evaluator and the user's time zone from its caller; the Avalonia `FormLiveComputation`
keeps its public shape over it.

The new `Polhem.Web.Blazor.Server.DataObjects.FormLiveComputation` brings that engine to a page of its own, with
the shared DynamicExpresso evaluator by default. Pass the circuit's time zone:

```csharp
var live = new FormLiveComputation(schema, timeZoneProvider: () => client.Session.Credentials.UserTimeZoneId);
dataObject.FieldValueChanged += (_, e) =>
{
    if (!live.IsRecomputing) live.Recompute(e.TableName, e.FieldName, e.Row);
};
```

`FormPage` rounds the preview with a rounding context like the Avalonia `FormView`'s: the entered company from its
definition loader's `CompanyAccessor`, and the currency and unit masters when they are deployed (a missing or refused
master falls back to framework-default decimals). The server rounds authoritatively on save.
`Polhem.Web.Blazor.Server` now references `Polhem.Expressions` for the default evaluator.

The Blazor `FormDataObject` gains the row lifecycle of the Avalonia one: a new row is seeded with the schema's
defaults (a fresh `sys_rowid`, the link to the master, non-null values by type), `RowAdded` and `RowDeleted` report
row changes, and `BeginRowEdit` / `CommitRowEdit` / `CancelRowEdit` buffer one row's edits, which raise
`RowEditFieldChanged` until the commit publishes them through `FieldValueChanged`.

### Live computation says when it stops

When an expression cannot be evaluated, for example `amount * 1.05` on a `Currency` field (a `decimal` does not
combine with the `double` literal; write `1.05m`), live computation still stops for that form, but no longer
silently. `FormLiveComputationEngine` records the cause in the new `Degradation` property, a
`LiveComputationDegradation` with the field, the expression and the exception, and raises `Degraded` once. Both
`FormLiveComputation` types pass them through. The Avalonia `FormView` shows a message that names the field and the
reason and raises the new `LiveComputationDegraded` event for the host to log; the Blazor `FormPage` keeps the same
message on screen and logs a warning with the expression through its `ILogger`. The message text is the new
`PolhemUIText.LiveComputationStopped` key.

### Detail grids in Blazor Server

`FormLayoutPresenter` and `FormPage` now render the layout's detail tables, each as the new `GridControl`, with the
editing rules of the Avalonia grid:

- The Add / Edit / Delete toolbar shows while the form mode is not View, the layout's `AllowEditModes` admits it, and
  its `AllowActions` grants the action. A grid over a caller-supplied table (list mode) never edits.
- `GridEditMode.InCell` shows each editable cell's field editor bound to its row, so a value commits when the user
  leaves the cell. `GridEditMode.EditForm` shows text and edits a row in `RowEditDialog`, a modal over `RowEditPanel`
  that buffers the edits (`BeginRowEdit`) until OK; Cancel restores the row, and a cancelled Add removes the blank row.
- `FormLayoutPresenter.DetailEditMode` picks the model; `IsCompact` forces the edit form for phone-sized screens
  (see "Compact layout in Blazor Server" below).
- A read-only column's header is parenthesised, and a required one carries `polhem-grid__header--required`.

The cell text follows the new `GridCellFormatter` in `Polhem.UI.Core`, which the Avalonia grid and the Blazor
`DynamicGrid` now use too, so a lookup column in a list shows its display fields rather than a row id in both heads.
`FieldEditorBase` also refreshes on `RowEditFieldChanged`, so an edit form shows a recomputed field at once.

### Compact layout in Blazor Server

On a phone-sized screen a Blazor form now takes the compact layout of the Avalonia `FormView`:

- `FormLayoutPresenter.IsCompact` lays the master fields out in one column, whatever the layout's `ColumnCount`, as
  well as editing the detail grids in the edit form. The root element then carries `polhem-form-layout--compact`.
- `FormPage` decides it from the browser's viewport: below `CompactWidthThreshold` (600 CSS pixels by default) the
  form is compact, and it switches only when the viewport crosses the threshold. Set `IsCompact` to fix the layout
  instead; the page then measures nothing. `DetailEditMode` picks the detail editing model outside the compact
  layout.
- The new `CompactViewportObserver` does the measuring and raises `CompactChanged`. A page that uses
  `FormLayoutPresenter` directly places one next to it:

  ```razor
  <CompactViewportObserver CompactChanged="compact => _isCompact = compact" />
  <FormLayoutPresenter Layout="_layout" DataObject="_data" IsCompact="_isCompact" />
  ```

The package ships its first script for this: a small JavaScript module, loaded through JavaScript isolation from
`_content/Polhem.Web.Blazor.Server/`, so the host page adds no `<script>`. The host must serve static web assets
(`UseStaticFiles` or `MapStaticAssets`), as the Blazor templates do. JavaScript cannot run while a page prerenders,
so a prerendered page starts wide and switches once the circuit connects. The package still ships no CSS.

A field whose `ColumnSpan` is wider than the grid now spans the whole grid instead of adding a column.

### FormPage follows the form mode

`FormPage` opens a record in View mode after **View** (or a double-click on its row), in Edit mode after **Edit** and
in Add mode after **New**, so a field limited to Add (a key, for example) is read-only when the saved record is edited
again. See [`FormPage` shows the list and the record one at a time](#formpage-shows-the-list-and-the-record-one-at-a-time).

### FormPage serves several programs and follows the user's permissions

`FormPage` loads again when its `ProgId` or `DefinitionLoader` changes. A host can route every program to one page,
such as `@page "/form/{ProgId}"`, which Blazor renders with the same component instance; before, the page kept showing
the first program. Its list now asks the server for `sys_rowid` ahead of the form's `ListFields`, as the Avalonia
`ListView` does; before, a list served by a real backend came back without the row id, and clicking a row opened
nothing. The rule is the new `Polhem.UI.Core.Connectors.ListSelectFields`, which both heads use.

The new `Polhem.Web.Blazor.Server.Identity.CircuitUserContext` holds one circuit's signed-in user, entered company and
capabilities. `AddPolhemBlazor` registers it scoped, and as the circuit's `IUserContext`, and `PolhemLoginPanel` records
the sign-in on it. Enter the company and sign out through it, so the context and the client stay in step:

```csharp
@inject CircuitUserContext UserContext

await UserContext.EnterCompanyAsync(companyId);   // after the sign-in
UserContext.SignOut();
```

With a capability snapshot, `FormPage` hides View when the user lacks `Read` on the form's permission model, New
without `Create`, Edit without `Update`, Delete without `Delete`, and Save on a record without both `Create` and
`Update`, as the Avalonia views do; sensitive
fields are hidden or read-only by their category, and numbers preview with the entered company's decimals. A host
that enters the company through the client directly leaves the context without a snapshot, and the page treats the
user as unrestricted. The backend still checks every call.

The layout half of this is `LayoutCapabilityApplier`, which moves from `Polhem.UI.Avalonia`, where it was internal,
to `Polhem.UI.Core.Permissions`, so both heads degrade layouts with one implementation.

### Field rules shared by both heads

`Polhem.UI.Core.Fields` holds the rules the field editors of both heads use, so they cannot drift apart:

- `FieldEditRules.AllowsEdit`: the form mode, the layout read-only flag and `AllowEditModes`.
- `FieldValueFormatter.Format`: the display of a value in the user's culture.
- `NumericFieldFormat`: number format resolution, including currency and unit decimals, display, input parsing and
  the value written back.
- `DateTimeFieldFormat`: the display, input and binding-string rules of a date-and-time field.
- `FormLiveComputationEngine`: the live recomputation of computed fields and new-row defaults.
- `GridCellFormatter` and `FieldCaptionRules`: the text of a grid cell, and the read-only and required caption cues.
- `LookupFieldRules` and `LookupDisplay`: whether a field looks up, which fields it shows and how they are joined,
  and how a selection is written back or cleared.

### Lookup-only relation mappings

A relation mapping marked `LookupOnly="true"` is written back when the user picks a row in the lookup, but the query
join does not read it. A selection can then carry more along than the join fills. On a leave request that stores both
the employee and the department, picking an employee also fills the request's own `dept_rowid` and the department's
display fields, while `dept_rowid` still joins its own `ref_dept_*`:

```xml
<FormField FieldName="emp_rowid" RelationProgId="Employee">
  <RelationFieldMappings>
    <FieldMapping SourceField="sys_name"      DestinationField="ref_emp_name" />
    <FieldMapping SourceField="dept_rowid"    DestinationField="dept_rowid"    LookupOnly="true" />
    <FieldMapping SourceField="ref_dept_name" DestinationField="ref_dept_name" LookupOnly="true" />
  </RelationFieldMappings>
</FormField>
```

Without the flag, the join would read `dept_rowid` from the employee row, so a filter or a sort on it would use the
employee's current department, and `ref_dept_name` would be claimed by two relations. The source fields must be in
the target form's `LookupFields`, unless the field calls back the server (next section). POLHEM1006 now reports a relation field that only lookup-only mappings fill, because
it is empty after every reload. In the form workbook, write ` (lookup)` after such a pair. The full explanation is in
[FormSchema-Driven Database Access](../definitions/formschema-data-access.md#34-lookup-only-mappings).

### Field changes that call back the server

A lookup window shows a few columns, while a selection often needs more, such as a product's price on an order line.
Mark the field with `ValueChangeCallback="true"`, and a change the user makes calls `FieldValueChange` on the BO of
the form being edited, with the table, the field, the new value and a copy of the row. The answer carries the values
to write into the row and the errors and warnings to show on its fields.

- A relation field needs no code. The server reads the related row under the related form's lookup rules and returns
  every `RelationFieldMappings` destination, the ones the lookup window does not show included. A mapping source of
  such a field no longer has to be in `LookupFields`: the pick skips it and the callback fills it.
- For anything else, the form's BO overrides `FormBusinessObject.FieldValueChange`, calls the base method and adds
  values by field name to the `FieldValueChangeResult`. The call requires `Create` or `Update` on the form.
- Only the user's own change calls back. Values a callback writes, the writes of a lookup pick and a committed row
  edit do not call back again, and a lookup pick calls back once, after all of its writes. An answer that arrives
  after the field changed again, or after the row was deleted, is discarded.
- Both heads do it the same way, through `FieldValueChangeCoordinator` in `Polhem.UI.Core`. The Avalonia and Blazor
  `FormDataObject`s stamp every write with a `FieldValueOrigin` and raise `FieldValueChangeApplied` and
  `FieldValueChangeFailed`; `FormView` and `FormPage` show the messages. The connector side is the new
  `IFieldValueChangeConnector`, which `FormApiConnector` implements; a connector without it makes no call.
- DefineEditor's relation dialog has a checkbox for the flag, ticked by default when a mapping source is missing from
  the related form's `LookupFields`.

The definition is described in
[FormSchema-Driven Database Access](../definitions/formschema-data-access.md#35-filling-the-row-from-the-server-on-change)
and the method in the [API method reference](../api/api-method-reference.md). The reasons for the design are in
[ADR-058](../../../maintainers/adr/adr-058-field-value-change-callback.md).

### Northwind on Blazor Server

`apps/Polhem.Northwind` gains `Polhem.Northwind.Blazor`, a Blazor Server head built on `Polhem.Web.Blazor.Server`:
sign-in with company entry, the menu from `MenuSettings.xml`, and one routed `FormPage` for every form. Its backend
moves into the class library `Polhem.Northwind.Backend`, which the JSON-RPC server and the Blazor head both run on the
same definitions and the same database, the Blazor head in process. The demo also shows two features of this version
on every head: the order line's product calls back the order's business object for the product's unit price, and the
Order form is bound to a permission model, with a `demo-ro` account that may only read orders. See
[its README](../../../apps/Polhem.Northwind/README.md#web-client-blazor-server).

### DefineEditor rejects expressions that do not parse

When DefineEditor validates a FormSchema, and before it saves one, it parses every field expression
(`DefaultValueExpression`, `ValueExpression`) and rule expression (`When`, `Condition`) the way the runtime does, and
lists each one that does not parse as an error on its field or rule. The typical case is a numeric literal: a literal
with a decimal point is a `double`, and there is no operator between `decimal` and `double`, so `amount * 1.05` on a
decimal field fails, while `amount * 1.05m` parses. Such an expression fails the server's save, and in a client's live
computation it only stops the computed field from updating, which is why it is caught here.

The check is public: `IExpressionEvaluator.Validate` parses one expression against variable types without evaluating
it, and `FormExpressionCalculator.ValidateExpressions` runs it over a whole FormSchema and returns a
`FormExpressionIssue` for each failure. A parse error's message now also names the operator and the operand types.

### DefineEditor sets up a field's relation

A stored field's `RelationProgId` has a button that opens a relation dialog. The related form is picked from the
solution's `ProgramSettings`, filtered by ProgId or display name as you type; only `ProgramSettings` is read to build
the list, and only the picked form's FormSchema is read to list its master fields. Each of those fields can be mapped
to a destination (`ref_<base>_<field>` by default) and marked `LookupOnly`, or marked `FormField.ValueChangeCallback`,
which is ticked by default while an included source is missing from the related form's `LookupFields`. A destination
the table lacks is added after the foreign key with the source's type, length and a caption that follows the form
workbook convention; unchecked mappings are removed, and the relation fields they leave unwritten can be removed with
them. Before applying, the dialog lists what the result would break: lookup-only sources the related form does not
return, and new validation issues such as POLHEM1006. The relation fields of a field that is not stored still open in
the tree.

### FormSchema rules are added and deleted in the tree

The FormSchema tree showed the Rules folder but offered no way to add a rule, so a rule had to be written into the XML
by hand. The Rules folder and each rule now offer **Add FormRule**, which adds a rule whose condition is `true`, so it
refuses nothing until it is written, and selects it for the property grid. A rule is deleted like a field.

### A sync gives every new field a caption to translate

Syncing a translated form only added `zh-TW` captions for new stored fields, whose newness it reads from the
TableSchema. A relation field has no column, so a `ref_*` field added in the editor never got a key and the translator
could not find it. A sync now gives every new field of a form that already has `zh-TW` texts a caption key holding the
form's own caption, ready to translate, and every relation field without one gets the foreign key's `zh-TW` caption
plus 代號 or 名稱 when a regular mapping fills it from `sys_id` or `sys_name`, as the form workbook import names them.
A translation already there is kept, a form without `zh-TW` texts gets no language file, and the sync preview lists
the keys each language file gains.

### Recent solutions, and the Table Schemas view

A DefinePath folder is usually called `Define`, so DefineEditor's recent lists name each entry after the folder above
it, add parent folders only where names collide, and show the location with the home directory as `~` and the middle
segments elided. An entry whose folder no longer exists stays listed, dimmed, with a tooltip saying so; each Welcome
page entry can be removed, and **File › Open Recent** rebuilds from the same change event.

The **Databases** view is renamed **Table Schemas**: it lists the tables of each `DbCategorySettings` category, not
the databases of `DatabaseSettings`, and in a multi-tenant setup one company category stands for many company
databases, so the title, the icon and the category nodes no longer suggest connections. On macOS the window extends
its client area into the title bar and draws a sidebar toggle right of the traffic lights; Windows and Linux keep the
native title bar.

### Form messages in a bar, and required captions from the schema

A refused save or a rule message was one line of small red text above the toolbar. The Avalonia form and list views
now show it in a danger-tinted bar with an icon, wrapped text and a dismiss button (`PolhemUIText.Dismiss`), and when
required fields are empty the cursor moves to the first one.

A required caption followed only the layout's `Required`, while the server enforces the schema's, so a field required
in the FormSchema alone was refused on save without the cue. The master fields and a bound detail grid now take
either. The required blue is lighter on the dark theme variant, where the old one read poorly.

### In-cell text editing replaces the value

Text cells use a template column, so entering edit left the caret where the click put it and typing went in front of
the value: `40` became `540`. `GridControl` now selects the text when a cell enters editing, keeps the caret at the
end on F2, and starts an edit from the typed character when a key is pressed on a selected cell. Escape no longer
writes the abandoned text when the editor loses focus.

### The shell's content stays above the on-screen keyboard

On a phone the keyboard overlays the view without resizing it, so it covered the sign-in button, and a field near the
bottom of a form could sit under it as well. `Polhem.UI.Avalonia.Shell`'s root now raises its bottom padding to the
height the keyboard covers and scrolls the focused editor back into view, the way the overlay dialogs already do.

### A property row can open its own value editor

`PropertyGridControl.ValueEditorProvider` gives a text or suggestion row a button that opens an editor the host
supplies, such as a dialog, in the same way `CollectionEditorProvider` does for a collection. The row keeps its text
box or drop-down; typed text is committed before the editor runs, and a reported change reloads the rows and raises
`PropertyValueChanged` with the values before and after. The addition is purely additive and binary compatible.

### A list item with no text shows its value

A list item added in DefineEditor's collection editor starts with an empty `Text`, so its drop-down showed blank
options, while the form workbook import used the value as the text. `ListItem.Text` now returns the value when no text
is set, which covers DefineEditor, hand-written XML and every head at once. The property keeps its type and its
setter.

### The template's Server + Browser launch starts the browser client

The `polhem-avalonia` template's Browser launch configuration used the `dotnet` type, which cannot start a WebAssembly
project: F5 on **Server + Browser** started the server and nothing else, with no error. The configuration now runs the
client's development server as a background task and opens its URL in Chrome through VS Code's built-in JavaScript
debugger once the server is ready; stopping the session ends the development server.

## Breaking changes

### `DynamicForm` is replaced by `FormLayoutPresenter`

- **Affects:** Blazor Server applications that render `DynamicForm` themselves. Applications that use `FormPage` only
  need nothing.
- **Before:** `Polhem.Web.Blazor.Server.Components.DynamicForm` rendered the master sections with plain inputs and the
  CSS classes `polhem-dynamic-form`, `polhem-dynamic-form__*` and `polhem-dynamic-form__input--*`. It followed only
  each field's `ReadOnly`.
- **Now:** `Polhem.Web.Blazor.Server.Controls.FormLayoutPresenter` renders the same sections through the field
  editors. It takes the same `Layout`, `DataObject` and `IdPrefix` parameters, plus `FormMode` and `RoundingContext`.
- **Migrate:**
  1. Replace `<DynamicForm ...>` with `<FormLayoutPresenter ...>` and add `@using Polhem.Web.Blazor.Server.Controls`.
  2. Pass `FormMode` when the page has a view or add state; it defaults to Edit, which matches the old behavior for
     fields that are not read-only.
  3. Rename the CSS selectors: `polhem-dynamic-form` → `polhem-form-layout` (and its `__section`,
     `__section-caption`, `__grid`, `__field` and `__label` parts); `polhem-dynamic-form__input` →
     `polhem-field-editor`; `polhem-dynamic-form__input--<kind>` → `polhem-field-editor--<kind>`.

### `FormPage` shows the list and the record one at a time

- **Affects:** Blazor Server applications that use `FormPage`, and tests or styles written against its toolbar.
- **Before:** the list sat above the record on the same page. A click on a row loaded it for editing, and the toolbar
  had New, Save and Delete.
- **Now:** the page shows the list or the record, as the Avalonia `ListView` and `FormView` do. The list's toolbar has
  View, New, Edit and Delete; a click selects a row (`DynamicGrid.SelectedRowId`) and a double-click opens it with
  View. A viewed record has Back; a new or edited one has Save and Cancel. A save that succeeds returns to the list,
  reloads it and keeps the saved row selected; Cancel and Back return without saving. Delete removes the selected row
  from the list. On a narrow viewport the list and the record no longer stack.
- **Migrate:** nothing to change in a page that only places `FormPage`. A test that clicked a row and then Save
  selects the row and clicks Edit first; one that clicked Delete on an open record selects the row in the list.

### `FormPage` shows a failed action as a notice

- **Affects:** Blazor Server applications that use `FormPage` and style or test the error it shows.
- **Before:** when loading a record, a save or a delete failed, `FormPage` replaced the toolbar and the form with the
  message in `div.polhem-form-page__error`, so a save the server rejected took the entered values off the screen.
- **Now:** the message is shown in `div.polhem-form-page__notice` above the form, which keeps the toolbar and what
  the user entered. `polhem-form-page__error` is left for a page that cannot load its definitions.
- **Migrate:** style `polhem-form-page__notice` for action failures; a test that waits for
  `polhem-form-page__error` after an action waits for the notice instead.

### `IExpressionEvaluator` gains `Validate`

- **Affects:** applications that implement `Polhem.Core.Expressions.IExpressionEvaluator` themselves. Applications that
  use `DynamicExpressoEvaluator`, directly or through `AddPolhemFramework`, need nothing.
- **Before:** the interface had `Evaluate`, `Evaluate<T>` and `GetReferencedVariables`.
- **Now:** it also has `Validate(string expression, IReadOnlyDictionary<string, Type> variableTypes, Type returnType)`,
  which throws `ExpressionEvaluationException` when the expression does not parse for those variable types.
- **Migrate:** implement `Validate` by parsing the expression with the configuration `Evaluate` uses, without
  evaluating it. An engine that cannot parse without evaluating can evaluate once with a default value of each
  variable type, but then a helper that reads the clock or other state runs during design-time checks.
- **Background:** [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md) (breaking changes in
  1.x minors); `IExpressionEvaluator` is not one of the interfaces
  [ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md) lets grow in a minor version.

### `FormField.LookupProgId` and `FormField.LookupFieldMappings` are removed

- **Affects:** FormSchema definitions or code that set `LookupProgId` or `LookupFieldMappings`, and form workbooks
  that fill the Lookup form or Lookup mappings columns. A definition that uses only `RelationProgId` and
  `RelationFieldMappings` needs nothing.
- **Before:** a lookup opened `LookupProgId` when it was set, and wrote back `LookupFieldMappings` instead of
  `RelationFieldMappings` when those were declared.
- **Now:** a lookup always opens `RelationProgId` and writes back every `RelationFieldMappings` entry. A definition
  file that still has the `LookupProgId` attribute or a `LookupFieldMappings` element loads without an error and
  without them, and a workbook's two Lookup columns are ignored.
- **Migrate:**
  1. Move each `LookupFieldMappings` entry the join should not read into `RelationFieldMappings` with
     `LookupOnly="true"`, and drop the entries that only repeated a relation mapping.
  2. For a `LookupProgId` that narrowed the candidates, override the target business object's `GetLookupFilter`, or,
