# Polhem 1.0.0 — Detailed Release Notes

[繁體中文](1.0.0.zh-TW.md) · [← CHANGELOG](../../CHANGELOG.md)

This file is the detailed companion to the `[1.0.0]` entry in [CHANGELOG.md](../../CHANGELOG.md). The changelog lists
each change in one line; this file keeps the reasons and the background. It is a draft until 1.0.0 is released.

> Polhem continues [Bee.NET](https://github.com/jeff377/bee-library) under a new name. Polhem 1.0.0 is Bee.NET 4.33.0,
> the last Bee.NET release, renamed, plus the changes of a pre-release review that are described below. How to move an
> application over is described in [Migrating from Bee.NET](../../README.md#migrating-from-beenet).

## Why a new name and a new repository

Polhem is the framework formerly published as Bee.NET, moved to the `polhem-dev` organization so that it can be
maintained by more than one person. It starts as a new repository, `polhem-dev/polhem`, without the git history; the
history before the move stays in `jeff377/bee-library`, which is frozen. The `Bee.*` packages are not developed further.

The new package IDs start their own version line at 1.0.0.

## How the renaming was checked

The renaming was done mechanically, and it was checked by changing every name back to `Bee` and comparing the result
with the Bee.NET source it started from (`jeff377/bee-library` at commit `7d6cc9d9`, whose `src/` and `tools/Bee.Cli`
are identical to the `v4.33.0` tag). What remained were the license, the package metadata and the icon. The full test
suite, including the database tests, ran with the same number of tests as on Bee.NET and passed.

Several kinds of name are strings the compiler does not check, such as type names in definition files, analyzer
lookups by metadata name and the assembly name in the trimming descriptor. Tests were added for kinds that had none, for
example `DefinitionFileTypeReferenceGateTests` for type names in definition files and `TrimmerDescriptorGateTests` for
the trimming descriptor.

This check covered the renaming step. The pre-release review that followed changed the code, and those changes are
described under [Changes from the pre-release review](#changes-from-the-pre-release-review).

## Renamed from Bee.NET

### Package IDs and namespaces

Every `Bee.<Name>` package is now `Polhem.<Name>`, and namespaces follow the same pattern. The split into packages is
unchanged, and every package still targets `net10.0`.

### Types and members named after Bee

`Bee` in a type or member name is now `Polhem`: `AddPolhemFramework`, `UsePolhemFramework`, `AddPolhemBlazor`,
`PolhemBlazorOptions`, `PolhemBlazorProviderMode`, `PolhemApiConnectorFactory`, `PolhemAccessTokenProvider`,
`PolhemLoginPanel`, and the extension classes `PolhemFrameworkServiceCollectionExtensions`,
`PolhemFrameworkApplicationBuilderExtensions` and `PolhemBlazorServiceCollectionExtensions`. The compiler reports every
use of the old names.

Two names were first renamed the same way and then renamed again by the review, because the framework's name said
nothing about what they are: `IBeeContext` / `BeeContext` are `IBusinessObjectContext` / `BusinessObjectContext`, and
`BeeStringLocalizer<T>` is `LanguageResourceStringLocalizer<T>`.

### No compatibility layer

Every name that contained `Bee` was renamed, including those the compiler does not check, and the old names are not
recognized. Applications built on Bee.NET are mostly kept in repositories their own developers control, so a one-time
search and replace is enough. The README lists these names and a command that finds them.

- **Type names**: payloads, the default settings and the `BusinessObject` / `Repository` bindings in definition files
  use `Polhem.*` type names. The server only accepts payload types from allowed namespaces, so a Bee.NET client and a
  Polhem server cannot talk to each other; clients and servers are upgraded together.
- **The master key**: the default environment variable is `POLHEM_MASTER_KEY`. A `SystemSettings.xml` that names the
  variable in `MasterKeySource` keeps using that name.
- **Session keys**: `DerivedApiEncryptionKeyProvider` derives each session's encryption key with the labels
  `polhem-api-session-key` and `polhem-api-encryption-root-key`, which were `bee-api-*`. The derived keys are never
  stored, so no stored data depends on the labels. Sessions created by Bee.NET end in any case, because the session
  table is now keyed differently (see *Security* below).
- **Build integration**: analyzer diagnostic IDs are `POLHEMnnnn` with the same numbers (`POLHEM4001`–`POLHEM4004` are
  reserved, because Bee.NET shipped and then retired `BEE4001`–`BEE4004`, and a suppression mapped by number must not
  silence a future rule), and the MSBuild properties for
  definition file checks are `PolhemDefinitionFilesGlob`, `PolhemRequireDefinitionFiles` and
  `PolhemAnalyzeDefinitionFiles`. Settings that use the old names are ignored without a warning.
- **The command-line tool** is `Polhem.Cli`, invoked as `dotnet polhem`.
- **Leftover names get no special error**: a type or assembly name left over from Bee.NET fails with the same message
  as any other name that cannot be resolved, and a missing `POLHEM_MASTER_KEY` is reported the same way whether or not
  `BEE_MASTER_KEY` is set.
- **The `ProgramSettings` format is not checked.** `ProgramSettings.xml` is read like every other definition file. A
  file still in the nested `<Categories>` layout of earlier Bee.NET versions, which carried the menu, loads as an empty
  registry, so every progId falls back to the framework's default business object. Bee.NET 4.33.0 refused such a file
  and named the conversion command, so a deployment that ran on it already has the flat layout; any other converts the
  file with Bee.NET's `dotnet bee defines split-menu` before moving over. `ProgramSettingsFormat` and the Polhem copy
  of the command were removed. ([#28](https://github.com/polhem-dev/polhem/pull/28))
- **Blazor components** use CSS classes that start with `polhem-`.
- **Data keys**: the `DataColumn` extended property that records a declared field type is `Polhem.FieldDbType`, and the
  `Exception.Data` key `SerializationErrorData.FilePath` is `Polhem.FilePath`. Audit records that Bee.NET wrote keep
  `Bee.FieldDbType` in their stored XML; their values read the same, and only the declared type of their columns is no
  longer known.

### Package metadata

The authors and the copyright holder are Polhem contributors, the project and repository URLs point to
`polhem-dev/polhem`, and the packages carry the Polhem icon. The license is still MIT. `Polhem.Cli` shares the same
metadata, and ships a README and a symbol package. ([#3](https://github.com/polhem-dev/polhem/pull/3))

## Changes from the pre-release review

Before 1.0.0 the framework went through a full review: security, the wire contract, concurrency, the public API,
tests, internationalization, performance and trimming. Its fixes landed before the first release, so the version
number did not have to wait for a 2.0.0 to correct the public API. Each group below gives the reason and links the pull
requests that made the change; the one-line list is in the [CHANGELOG](../../CHANGELOG.md), and what an upgrade has to
do is in the README.

### Security

- **Access tokens are not stored.** `st_session` keeps `AccessTokenHasher.ComputeStorageKey` of the token in its
  `access_token` column, and the session seed no longer contains the token, so read access to the table yields no
  usable bearer token. The log tables `st_log_access`, `st_log_anomaly_api`, `st_log_change` and `st_log_login` keep
  a short fingerprint in `token_fingerprint`, which still correlates the records of one session. Rows written before
  the switch match no token, so every existing session ends. ([#5](https://github.com/polhem-dev/polhem/pull/5))
- **Passwords.** New hashes use PBKDF2-SHA256 with 600,000 iterations (the OWASP recommendation at the time) in a
  format that records its own iteration count, and a hash with fewer iterations is replaced at the next successful
  sign-in (`PasswordHasher.NeedsRehash`). The unprefixed PBKDF2-SHA1 format inherited from Bee.NET no longer verifies,
  so accounts that still have such a hash need a password reset. An unknown user name runs a decoy hash, so the time a
  failed sign-in takes does not reveal whether the account exists. ([#5](https://github.com/polhem-dev/polhem/pull/5))
- **Record scope on writes and reads.** A save checks the master scope against the row an UPDATE or DELETE actually
  binds, refuses rows that change their row id, checks against the database that modified and deleted detail rows
  belong to an in-scope master of the same payload, and checks the values an added or modified master row leaves
  behind against the caller's Create or Update scope. `GetList` and `GetCount` accept only filter and sort fields the
  form declares and never protected fields, and `GetLookup` applies the Read scope unless a business object sets
  `LookupAppliesRecordScope` to `false`. The rules are described in
  [Permission and authorization](../en/permission-authorization.md). ([#4](https://github.com/polhem-dev/polhem/pull/4))
- **Definitions over the API.** Remote `GetDefine` serves only an explicit list of definition types (the ones a client
  renders with, listed in `SystemBusinessObject.GetDefine`); deployment settings such as `SystemSettings` and
  `DatabaseSettings` are read only in process. ([#4](https://github.com/polhem-dev/polhem/pull/4))
- **Audit rules and ProgId casing.** A progId resolves to its form whatever casing the caller uses, so the audit rule
  must too. Business objects for reserved and registered progIds are created with the casing `ProgramSettings`
  declares ([#4](https://github.com/polhem-dev/polhem/pull/4)). That left the forms the registry does not list: they
  keep the caller's casing, and an exact rule lookup let a caller reach such a form under another casing and fall back
  to the deployment default. `CompanyAuditRules` now looks rules up case-insensitively (of two rules that differ only
  in case, the first is kept), and the audit records of a form carry its FormSchema's ProgId spelling, so one form's
  records share one `prog_id` in `st_log_change` and `st_log_access`. Records written before keep the spelling they
  were written with; a query over them compares `prog_id` case-insensitively.
  ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Transport.** Encoded and Encrypted requests are decoded into the parameter type of the action the request resolves
  to; the type name the client declares is only a consistency check. Decoding enforces one depth limit on both codecs,
  nested filters included. Only public, non-generic, one-parameter instance methods that are not accessors can be
  called as actions, the same rule `POLHEM3001` applies at build time. BCL exception messages stay in the server log
  (`JsonRpcExecutor.Logger`); the caller gets a fixed message per error code, and framework messages meant for users
  are thrown as `UserMessageException`. ([#6](https://github.com/polhem-dev/polhem/pull/6))
- **Plain bodies.** A `Plain` body used to be deserialized straight into the argument type of the business object's
  method, so a caller could set any public member of that type, including ones the contract does not declare. It is
  now read into the action's request type first and copied into the arguments, as the Encoded path already did; a
  gate test keeps the framework's argument types free of members that are not in their contract. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Sessions and keys.** `CreateSession` accepts only local calls. The API key methods `CreateApiKey`,
  `SetApiKeyEnabled` and `SetApiKeyExpiry` are replay-protected like the other state-changing system methods. The
  database anomaly log is readable only by a deployment administrator. The master key file and the client's
  `apikey.txt` are created with owner-only permissions, and a warning is logged when `DatabaseSettings` holds passwords
  but no `ConfigEncryptionKey` protects them. ([#5](https://github.com/polhem-dev/polhem/pull/5))
- **Server paths in errors.** A missing definition file used to be reported with its full path. A debug-mode host
  passes the message of an unmapped exception to the remote caller, and a FormSchema is reached by the progId a request
  names, so any caller could learn the server's directory layout. `FileUtilities.EnsureFileExists` names only the file;
  the full path stays on `FileNotFoundException.FileName` for the server log, and `FileUtilitiesTests` pins the
  message. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Client.** A client refuses the "none" encryptor a server advertises unless the client itself runs in debug mode,
  and no longer adopts the server's debug flag or allowed type namespaces.
  ([#6](https://github.com/polhem-dev/polhem/pull/6))
- **DDL and connection strings.** SQL Server string defaults are escaped, other defaults must be literals of their
  column type, and connection string placeholders are filled through `DbConnectionStringBuilder`
  (`ConnectionStringTemplate`). ([#4](https://github.com/polhem-dev/polhem/pull/4))

### Changed behaviour

- **Anonymous calls.** The server used to keep a hand-written list of methods that could be called without a Bearer
  header, and rejected every other request without one with HTTP 401. Now a request without the header is simply
  anonymous and `[ApiAccessControl]` alone decides; a method that needs a session answers JSON-RPC `-32001`
  (`AuthenticationRequiredException`), which the .NET client turns into an `UnauthorizedAccessException`. `RemoteApiProvider` sends
  the header only once it has an access token, so a deployment that overrides `IsAuthorizationRequired` to refuse
  anonymous requests is not bypassed by a placeholder empty token.
  ([#6](https://github.com/polhem-dev/polhem/pull/6), [#18](https://github.com/polhem-dev/polhem/pull/18))
- **Paging.** `GetList` without paging options returns the first page, capped at `PagingOptions.MaxPageSize`, instead
  of every row. ([#4](https://github.com/polhem-dev/polhem/pull/4))
- **English base language.** The built-in definition files, the Avalonia and Blazor UI text and the framework messages
  use English as their base text, and the Chinese text moves to the shipped `zh-TW` resources. One fall-back chain
  (`LanguageFallback`) serves captions, enums, menus, rule messages and framework text: the requested culture, its
  parents, the deployment default, then the base text. The deployment default is `CommonConfiguration.DefaultLanguage`,
  which replaces `CommonConfiguration.DefaultLang` and `BackendConfiguration.DefaultLanguage`; its default stays
  `zh-TW`. The login response carries the user's culture (`st_user.culture` or the deployment default) and the client
  adopts it, so `UserInfo.Culture` is empty until sign-in instead of `zh-TW`.
  ([#15](https://github.com/polhem-dev/polhem/pull/15))
- **User-facing messages** carry a key and arguments and are resolved in the session culture; form rule messages
  resolve `{ProgId}.Rule.{RuleId}.Message`. Numbers and dates are displayed and parsed in the user's culture, while the
  wire stays culture-invariant. ([#15](https://github.com/polhem-dev/polhem/pull/15))
- **`CBool`** accepts language-neutral codes only (`1`, `T`, `TRUE`, `Y`, `YES`, ignoring case). The Chinese words for
  yes and true made one language special in a culture-neutral conversion; a value typed in a user's language is the
  UI's to convert. ([#15](https://github.com/polhem-dev/polhem/pull/15))
- **Configuration.** `BackendComponents` entries are blank by default and a blank entry selects the framework default,
  so a settings file no longer has to name internal framework types. A wrong `CacheProvider` or component type name
  fails at startup with the name of the setting instead of later with a null reference.
  ([#8](https://github.com/polhem-dev/polhem/pull/8), [#11](https://github.com/polhem-dev/polhem/pull/11))
- **Client storage.** The endpoint and the API key are kept in `endpoint.txt` and `apikey.txt` under the per-user
  local application data folder (`FileEndpointStorage`, now in `Polhem.UI.Core` and the default), because the folder
  beside the assembly is read-only on iOS and lost on WebAssembly. The previous `{ExeName}.Settings.xml` is not read.
  ([#12](https://github.com/polhem-dev/polhem/pull/12))
- **Wire.** Over MessagePack a `DataTable` is written as one column table plus positional rows instead of a name/value
  map per row. Members whose initializer is not the CLR default are always written, so an absent member means the CLR
  default on every codec, and Plain requests bind object-typed filter and parameter values by JSON kind, so Plain,
  JSON and MessagePack carry the same values. The TypeScript client `polhem-connector-js` follows the contract changes
  (`userId`, the removed `oneTime`, `culture`, the `AuditLog…` response names).
  ([#9](https://github.com/polhem-dev/polhem/pull/9), [#12](https://github.com/polhem-dev/polhem/pull/12))
- **Cached definitions** are no longer changed by serializing them. The per-object serialize state is gone; empty
  collections are omitted through get-only `XSpecified` properties, which the reflection-only `XmlSerializer` on iOS
  accepts. The built-in definition files re-serialize byte-identically.
  ([#8](https://github.com/polhem-dev/polhem/pull/8))
- **Default-value expressions.** When a new row is created, by `GetNewData` on the server or by a UI client, a
  field's `DefaultValueExpression` now wins over its literal `DefaultValue` and over the per-type seed (0, empty
  text, today, `Guid.Empty`). Before, the seed made most fields non-empty, so an expression such as `Today()` on a
  date field never ran. At save the expression still fills only fields that are empty, so a value the user entered
  is kept. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Definition loader.** `ClientInfo.UseDefinitionLoader` is on by default. The Avalonia views then show captions in
  the user's language, the tenant's customized layout and the company's number formats without any setup; set it to
  `false` to render definitions as stored and save the loader's extra round trips. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Startup check.** A host built with `AddPolhemFramework` calls `IDatabaseSettingsProvider.ValidateRequired`
  before any other hosted service starts, so a deployment without a `common` database item fails at startup instead
  of on the first request that reaches a framework table. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Protocol errors.** An action name that resolves to no method answers JSON-RPC `-32601` (`MethodNotFound`), and a
  `Plain` body that cannot be read into the method's type answers `-32602` (`InvalidParams`), each with a fixed
  message. Both used to surface as other codes, and the two codes had no producer. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Required fields.** `FormField.Required` used to be a caption cue only: the server saved an empty required field.
  A save now refuses an added or modified row, master or detail, whose required field is empty, and names the field by
  its caption in the caller's language (`PolhemMessages.SaveFieldRequired`, `SaveDetailFieldRequired`). The Avalonia
  `FormView` and the Blazor `FormPage` run the same rule, `RequiredFieldCheck`, before sending a save, name every
  empty required field and do not send it. Empty means `null`, text that is empty or white space, `Guid.Empty` and a
  zero-length binary value; a number, a boolean or a date is never empty, because those columns always hold a value.
  Only persisted fields are checked, so a `Required` flag on a relation or virtual field has no effect on saving:
  mark the stored key field instead. Before upgrading, review the `Required` flags of your FormSchemas. An existing
  record stored with an empty required field cannot be saved again until the field is filled, so fill the data or
  clear the flag.
  ([#26](https://github.com/polhem-dev/polhem/pull/26), [#27](https://github.com/polhem-dev/polhem/pull/27))
- **Unguarded forms.** The startup warning that lists forms without a permission model used to look only at
  `ProgramSettings`, but a progId the registry does not name is still served by `FormBusinessObject`. It now also
  lists the forms the definition storage holds (`IDefineStorage.GetFormSchemaIds`). That member has a default
  implementation that returns an empty list, so a custom storage still compiles; implement it to have its forms
  covered. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Custom definition components.** A `DefineAccess` or `DefineStorage` type named in `BackendComponents` had to
  declare one of a fixed set of constructors. It is now created by `ActivatorUtilities`, so its constructor can take
  any registered service; a `byte[]` parameter still receives the configuration encryption key, and a storage's
  `(IServiceProvider)` constructor is still preferred, because a database-backed storage resolves its dependencies
  lazily. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Blazor definition loader.** The Blazor `FormPage` now localizes its definitions through a definition loader by
  default, like the Avalonia views: captions in the circuit's culture, the tenant's layout and the framework's number
  formats. `PolhemBlazorOptions.UseDefinitionLoader` set to `false` renders definitions as stored, and the page's own
  parameter still overrides it per page. ([#27](https://github.com/polhem-dev/polhem/pull/27))
- **Shipped layouts.** The default `AuditRule`, `Department` and `Employee` layouts showed every field as a text box,
  including mode codes, a flag and row ids. They are regenerated with `FormLayoutGenerator` from their schemas:
  drop-downs for the audit modes, a check box for the sensitive flag, lookups for the department and the manager, and
  no system columns. `LayoutControlTypeGateTests` fails when a shipped layout shows a field as a text box while its
  schema implies another editor. Materializing the defaults (`Defaults.MaterializeTo`, `dotnet polhem defines
  materialize`) skips files that exist, so a deployment that already has these layouts keeps the old ones: overwrite
  them (see `dotnet polhem help defines`) or edit them, after carrying over any changes of your own.
  ([#29](https://github.com/polhem-dev/polhem/pull/29))
- **Date-and-time fields.** A `DateTime` field used to get `DateEdit`, a date picker that writes the date alone, so
  editing the field dropped its time of day. `FormLayoutGenerator` and the `Auto` control type now give it the new
  `DateTimeEdit`: a text box that shows and parses the date and time in the user's culture on Avalonia, and a
  `datetime-local` input in Blazor. `DateEdit` stays for `Date` fields. Layouts already saved keep `DateEdit` on their
  `DateTime` fields; change those fields to `DateTimeEdit` where the time matters.
  ([#33](https://github.com/polhem-dev/polhem/pull/33))

### Breaking API changes

The public API was settled once, before anything shipped as Polhem. The rules it now follows are recorded in
[ADR-046](../adr/adr-046-api-evolution-policies-for-1-0.md).

- **Sealing.** Classes that are not designed for inheritance are sealed, so later versions can change their internals
  without breaking a subclass nobody planned for. Extension goes through the interfaces and the documented base classes,
  which stay open: the business object, repository and collection bases, `TextEdit`, `DateEdit`, `ListView`,
  `FormView`, the connectors and `AuditRuleBusinessObject`. `KeyCollectionBase<T>` is abstract.
  ([#13](https://github.com/polhem-dev/polhem/pull/13))
- **Names.** Types are named after what they are rather than after the framework or an abbreviation:
  `IBusinessObjectContext`, `LanguageResourceStringLocalizer<T>`, the `AuditLog…` family, `PermissionActions` (a flags
  enum), `NullLogWriter`, `UserId`. Enums without a zero value gained `None = 0`.
  ([#10](https://github.com/polhem-dev/polhem/pull/10), [#11](https://github.com/polhem-dev/polhem/pull/11))
- **Placement.** Types moved to the assembly that owns their responsibility: `DeploymentAuthorizationService` and
  `EmployeeContextResolver` to `Polhem.Business`, the permission capability resolver to `Polhem.Api.Client` so both UI
  heads can use it, and `FileEndpointStorage` to `Polhem.UI.Core`. `Polhem.ObjectCaching` no longer references
  `Polhem.Repository.Abstractions`.
  ([#11](https://github.com/polhem-dev/polhem/pull/11), [#12](https://github.com/polhem-dev/polhem/pull/12))
- **Client surface.** Local providers and connectors take the `IServiceProvider` instead of reading it from a static
  property; per-session state lives on `ApiSessionContext`. Every public async member takes a trailing
  `CancellationToken` that reaches `HttpClient`, and the server answers 499 for a cancelled request. The UI packages
  follow: the public async members of `Polhem.UI.Core`, `Polhem.UI.Avalonia` and `Polhem.Web.Blazor.Server` take one
  too, and a cancelled call throws to its caller instead of being reported on the view. Implementations of
  `IUIViewService` and overrides of the protected `Resolve*Async` hooks of `FormView` and `ListView` change their
  signatures. `SystemApiConnector` and `AuditLogApiConnector` keep `ExecuteAsync<T>` protected, because every framework
  action on them has a typed method and a host that adds actions exposes them from a subclass; `FormApiConnector`
  keeps it public, because a form's business object can declare actions of its own.
  ([#10](https://github.com/polhem-dev/polhem/pull/10), [#11](https://github.com/polhem-dev/polhem/pull/11),
  [#12](https://github.com/polhem-dev/polhem/pull/12), [#26](https://github.com/polhem-dev/polhem/pull/26),
  [#27](https://github.com/polhem-dev/polhem/pull/27))
- **Constants.** A `const` is compiled into every caller, so changing its value later would not reach code built
  against the old one. Tunable limits and defaults are therefore `static readonly`, among them the lockout defaults of
  `LoginAttemptTracker`, the length limits of `ApiKeyFormat`, `CurrencySettings.FallbackRounding`,
  `UnitSettings.FallbackDecimals` and the compact-width thresholds of `FormView` and `RowEditPanel`; the root changelog
  lists the ones Bee.NET had as constants. Protocol names, identifiers and formats stay `const`. Code that uses one of
  them in a constant expression, such as an attribute argument or a `case` label, must change.
  ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Replay store.** `IReplayWindowStore` is one atomic `TryAcceptAsync`, which a store shared by several server nodes
  can implement correctly. ([#12](https://github.com/polhem-dev/polhem/pull/12))
- **Codecs.** A custom codec is added with `ApiServiceOptions.RegisterPayloadCodec`; the codec used when a request
  declares none stays MessagePack, because every existing client relies on it.
  ([#10](https://github.com/polhem-dev/polhem/pull/10))
- **Cached types** that come from the database have init-only properties, and the session's company scope is one
  immutable `SessionCompanyScope` replaced in a single write, so a reader never sees half of a change.
  ([#8](https://github.com/polhem-dev/polhem/pull/8), [#10](https://github.com/polhem-dev/polhem/pull/10))
- **Rule processor.** `IFormRuleProcessor` gains `ApplyNewRowDefaults`, which the default-value change above needs.
  ADR-046 allows host-replaceable interfaces to gain members; another implementation has to add it. ([#22](https://github.com/polhem-dev/polhem/pull/22))

### Removed

Compatibility leftovers that 1.0 does not need, dead code and public types without callers were removed, and
implementation types became internal, so that 1.0 does not commit to them. The largest pieces are the hand-rolled
tracing subsystem, the serialize state interfaces, the legacy schema comparison path with `DbUpgradeAction`, the
one-time session flag and the synchronous `JsonRpcExecutor.Execute`. The framework repository implementations are
internal; hosts use the `I*Repository` interfaces. The unused settings types `ClientSettings`, `EndpointItem` and
`EndpointItemCollection` went once `FileEndpointStorage` had replaced the settings file they described, and
`StringHashSet` and the public setter of `SysInfo.Version` after them. `ProgramSettingsFormat` and
`dotnet polhem defines split-menu` were removed because Bee.NET compatibility is not a goal of 1.0 (see
[No compatibility layer](#no-compatibility-layer)).
([#8](https://github.com/polhem-dev/polhem/pull/8), [#10](https://github.com/polhem-dev/polhem/pull/10),
[#11](https://github.com/polhem-dev/polhem/pull/11), [#12](https://github.com/polhem-dev/polhem/pull/12),
[#22](https://github.com/polhem-dev/polhem/pull/22), [#26](https://github.com/polhem-dev/polhem/pull/26),
[#28](https://github.com/polhem-dev/polhem/pull/28))

### Performance

Measured at the time of the change:

- A definition cache hit with a file token took 62 ns instead of 1,216 ns, because the source file is checked at most
  once per second per entry. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- Gzip at the fastest level compressed a 570 KB payload in 0.48 ms instead of 1.67 ms, with 110 KB of output instead
  of 80 KB. ([#14](https://github.com/polhem-dev/polhem/pull/14))
- `AesCbcHmacCryptor` allocated 174 KB instead of 694 KB to encrypt a 173 KB payload, with the same output format.
  ([#14](https://github.com/polhem-dev/polhem/pull/14))
- The access-control lookup took 20 ns instead of 506 ns once per-request reflection was cached.
  ([#14](https://github.com/polhem-dev/polhem/pull/14))
- For a 20-column `DataTable` of 10,000 rows over MessagePack: 57% fewer raw bytes, 10% fewer compressed bytes, 86%
  less serialization time and 83% fewer allocations. ([#12](https://github.com/polhem-dev/polhem/pull/12))
- The audit batch writer persists a batch in one transaction. ([#14](https://github.com/polhem-dev/polhem/pull/14))

### Platform support

- **Trimming.** Polhem supports untrimmed and partial-trim builds. `POLHEM9004` warns when a consuming project publishes
  with NativeAOT, trims with `TrimMode=full` or disables System.Text.Json reflection; set
  `PolhemSuppressTrimSupportWarning` to `true` to silence it. `Polhem.Expressions` ships an ILLink descriptor so that
  the default mobile trim keeps the members expressions reach by reflection.
  ([#7](https://github.com/polhem-dev/polhem/pull/7), [#17](https://github.com/polhem-dev/polhem/pull/17))
- **Mobile and browser.** `LookupDialog` and `RowEditDialog` open a native window only on desktop and use the overlay
  host everywhere else, so lookups work on iOS, Android and the browser. The MessagePack value formatter handles Polhem
  enums and nested `ParameterCollection`s without dynamic code, and the HTTP client uses the platform default handler
  on the browser, Android and Apple mobile heads.
  ([#7](https://github.com/polhem-dev/polhem/pull/7), [#17](https://github.com/polhem-dev/polhem/pull/17))
- **Expressions on iOS.** Where code cannot be generated at run time, `LambdaExpression.Compile()` falls back to an
  interpreter, but the interpreter still builds a delegate of the lambda's exact signature, and beyond two parameters
  that needs generated code. On iOS a computed field such as `quantity * unit_price * (1 - discount)` terminated the
  app with an `ExecutionEngineException`; Mac Catalyst failed the same way. `DynamicExpressoEvaluator` now compiles
  every expression to one delegate that takes its variables as an object array; caching, null handling and exceptions
  are unchanged. The earlier desktop check with `DynamicCodeSupport=false` could not see the failure, because CoreCLR
  still generates that delegate, so `InterpretedInvokerGateTests` forces interpretation on desktop and fails when a
  compiled expression delegate is built on a `DynamicMethod`. ([#30](https://github.com/polhem-dev/polhem/pull/30))
- **Local mode on macOS and Linux.** `FileUtilities.IsLocalPath` accepted only Windows drive and UNC paths, so a desktop
  head on macOS or Linux could not connect in Local mode ("Unrecognized connection type"). It accepts paths fully
  qualified on the current operating system, and the Windows forms everywhere.
  ([#29](https://github.com/polhem-dev/polhem/pull/29))
- **Overlays on phones.** A panel's minimum width beat the overlay card's maximum, so a phone cut the lookup dialog off
  on both sides, and on iOS the on-screen keyboard covered the row-edit buttons. Hosted panels no longer set a minimum
  width of their own, the overlay host keeps the card inside the safe areas and above the keyboard, and the lookup and
  row-edit panels keep their buttons outside the scrolled content. ([#33](https://github.com/polhem-dev/polhem/pull/33))

### Fixed

- **Narrowing on rebuild.** `UpgradeOptions.AllowColumnNarrowing` was checked only on the `ALTER` path, so a table
  rebuild (every column change on SQLite) could narrow a column and truncate data without the opt-in. The rebuild
  path now applies the same check. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Relation joins.** A form table without a `DbTableName` produced a join against a blank table name; the join now
  falls back to `TableName` like the rest of the SQL builder. ([#22](https://github.com/polhem-dev/polhem/pull/22))
- **Chinese script tags.** Language resources are named by region (`zh-TW`, `zh-CN`), while macOS and iOS report the
  script (`zh-Hant-TW`), so the `zh-TW` resources were never reached there. `LanguageFallback` follows `zh-Hant-TW` and
  `zh-Hant` with `zh-TW`, and `zh-Hans-CN` and `zh-Hans` with `zh-CN`; a resource named by the script itself is still
  tried first. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Detail rows out of scope.** A save refused a detail row that belongs to a record the save does not carry with an
  English-only message; it now has a message key (`PolhemMessages.PermissionDetailOutOfScope`) and a `zh-TW`
  translation. ([#26](https://github.com/polhem-dev/polhem/pull/26))
- **Host-supplied layouts.** `FormView` narrowed a `Layout` the host assigned in place when it applied permission
  capabilities, so the host's instance changed under it; it now works on a copy.
  ([#27](https://github.com/polhem-dev/polhem/pull/27))
- **Lists.** Grids, card lists, lookups and detail grids in Avalonia and Blazor showed a drop-down field's stored code;
  they show its list-item text in the user's language (`FormValueBinding.TryGetListItemText`). A boolean shows a
  disabled check box in the card list and a localized yes or no elsewhere. At phone width the Avalonia card list
  showed a time part on dates and ignored number formats; it formats values as the grid does.
  ([#29](https://github.com/polhem-dev/polhem/pull/29), [#33](https://github.com/polhem-dev/polhem/pull/33))
- **Row-edit overlay.** The Avalonia row-edit overlay recomputed computed fields only once the row was confirmed; it
  recomputes them while the row is edited (`FormDataObject.RowEditFieldChanged`), and Cancel restores them.
  ([#30](https://github.com/polhem-dev/polhem/pull/30))
- **Blazor dates.** The Blazor `DateEdit` showed a blank box for a value that has a time of day, because a date input
  accepts only a date; it shows the date part. ([#33](https://github.com/polhem-dev/polhem/pull/33))
- **Blazor Remote mode.** Following the Blazor Server README in Remote mode failed with `401 Unauthorized`, because the
  server requires the application's API key and nothing said to set it. The README, `platform-support` and the remarks
  of `UseRemoteProvider` say that `ApiClientInfo.ApiKey` must be set at startup.
  ([#29](https://github.com/polhem-dev/polhem/pull/29))

### Samples and tools

- The samples keep their business tables in the company scope, as the database rules require: the seeder builds the
  tables from `DbCategorySettings`, seeds a demo company and the user's access to it, and the Blazor and JavaScript
  demos enter the company after sign-in. ([#23](https://github.com/polhem-dev/polhem/pull/23))
- Northwind adds a zh-TW demo account (`demo-tw`), seeded on start if it is missing, and its README screenshots are
  kept in the repository. DefineEditor shows a File menu inside the window on Windows and Linux. ([#23](https://github.com/polhem-dev/polhem/pull/23))
- The samples named their own forms `Employee` and `Department`, which replaced the framework's reserved forms of
  those names. They are `Staff` (`ft_staff`, `ft_staff_phone`) and `Team` (`ft_team`), and `Project` follows. Northwind
  ships `zh-TW` messages for its order rules. ([#25](https://github.com/polhem-dev/polhem/pull/25))

## Unchanged

- The split into packages and the target framework, `net10.0`.
- The names of the framework tables, which keep their `st_` prefix. The only column change is `access_token` →
  `token_fingerprint` in the four `st_log_*` tables named under *Security*; the README says what to do with the old
  column.
