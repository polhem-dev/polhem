# Polhem 1.5.0 — 詳細發佈說明

[English](../../en/changelogs/1.5.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.5.0]` 條目的詳細說明。變更紀錄以一行列一項變更；本檔保留
理由與背景。

## 為什麼是次版號

本版新增一個公開成員 `DbCommandSpec.ColumnTypes`，`PublicAPI.Shipped.txt` 基準沒有任何移除。wire 格式與 1.4.0 相同：
伺服端現在送出的 cell 值，就是欄位型別原本宣告的型別，所以 1.4.0 的客戶端與 1.5.0 的伺服端（或反過來）可以互通。

## 如何升級

把 Polhem 套件更新到 1.5.0。伺服端與客戶端不必同時升級。

在 SQLite、MySQL 或 Oracle 上以 in-process 方式（業務物件、Local provider）讀取表單資料表，並且處理過 provider 原生型別的程式碼
——Boolean 或 AutoIncrement 的 cell 是 `long`、Oracle 的 AutoIncrement 是 `decimal`——現在會拿到宣告的型別。SQL Server 與
PostgreSQL 原本就回傳宣告的型別，所有遠端呼叫也是，因為兩種 codec 在接收端都依宣告型別重建欄位。

## 表單讀取回傳宣告的型別

`GetList`、`GetData` 與依 row id 的讀取，現在在所有 provider 上都以 FormSchema 欄位宣告的 CLR 型別回傳每個數值與布林欄。
（[#99](https://github.com/polhem-dev/polhem/issues/99)、[#100](https://github.com/polhem-dev/polhem/pull/100)）

**出了什麼問題。** SQLite 沒有欄位型別，只有每個值各自的 storage class，而 Microsoft.Data.Sqlite 以結果集第一列的型別作為整欄的型別。
第一列是整數值的 `NUMERIC` 欄會成為 `Int64` 欄，之後每個值都被轉進這個型別：`100.5` 讀成 `100`，任何地方都沒有錯誤。
Boolean、Short、Integer 與 AutoIncrement 欄讀成 `Int64`。MySQL 把 AutoIncrement 讀成 `long`，Oracle 讀成 `decimal`。

JSON codec 為了保住 JavaScript 的精度，把 `long` 或 `decimal` 的 cell 寫成字串，欄位型別則寫 FormSchema 宣告的型別。因此 Boolean 欄
送出時是 `"type":"Boolean"`，cell 卻是 `"1"` 與 `"0"`，依欄位型別解碼每個 cell 的 polhem-connector-js 就拒收整張表。`Save` 也受影響，
而且是在事後：資料列已經寫入，回傳的 data set 才解碼失敗，呼叫端若把錯誤當成存檔失敗而重試，就會寫入兩筆。

**為什麼讀完再轉不夠。** 表單 repository 本來就會置換「provider 型別只是宣告型別的儲存形式」的欄位（Oracle 的 `RAW(16)` Guid、
SQLite 以文字儲存的日期）。在那裡補一個 `Boolean ⇐ long` 就能修好回報的症狀，但到那個時候 decimal 的小數已經沒了。

**修正方式。** `DbCommandSpec.ColumnTypes` 指定結果欄位的 CLR 型別。設定之後，`DbAccess` 在讀取任何一列之前先建好這些欄位，
同步與非同步兩條路徑都是，每個值在載入時就轉成宣告的型別。表單 repository 以這個方式宣告每個 Boolean、Short、Integer、
AutoIncrement、Long、Decimal 與 Currency 欄位。

### 限制

- **AutoIncrement 維持 `int`。** SQL Server 與 PostgreSQL 把它建成 32 位元 identity，兩種 codec 也以 `int` 重建。MySQL（`BIGINT`）、
  Oracle（`NUMBER(19)`）與 SQLite 存的是 64 位元，所以超過 `int.MaxValue` 的值會讓表單讀取失敗；in-process 現在如此，經過 wire
  時原本就是如此。
- **SQLite 的 Guid 欄仍讀成 `string`。** 轉換會讓存放的文字經過 `Guid` 往返，SQLite 欄位預設值存的不含連字號的 GUID，寫回時就比對不到。
- **SQLite 儲存時就會對長 decimal 四捨五入。** 超過約 15 位有效數字的值，在 `NUMERIC` affinity 下儲存時就被四捨五入，讀取端無從修復。
- **自行撰寫的 SQL 不在範圍內。** 不經過表單 repository 的查詢，欄位型別由 provider 決定，除非自己宣告 `ColumnTypes`。

## `DbCommandSpec.ColumnTypes`

這個選項是公開的，自行撰寫的 SQL 也可以使用：

```csharp
var spec = new DbCommandSpec(DbCommandKind.DataTable, "SELECT seq, flag, amount FROM my_table");
spec.ColumnTypes["flag"] = typeof(bool);
spec.ColumnTypes["amount"] = typeof(decimal);
var table = dbAccess.Execute(spec).Table;
```

- 只適用於 `DataTable` 命令；設在其他種類的命令上，執行時會擲例外，與 `DateColumns` 相同。
- 欄名比對不分大小寫；結果集中沒有的欄名會被忽略，因為依 schema 宣告的呼叫端會宣告所有欄位，而查詢可能只選其中一部分。
- 欄位保持在結果集中的位置。
- 放不進宣告型別的值會擲例外。值保有 provider 讀取時那個型別的精度：SQLite 的 `REAL` 進來時是 `double`。
- 設定之後，資料表只依結果集建立：同一個欄名出現兩次會擲例外，而不是自動改名；也不會把 key、nullability 或長度資訊讀進欄位。
