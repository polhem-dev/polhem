# Polhem 1.15.0 — 發佈說明

[English](../../en/changelogs/1.15.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.15.0]` 條目的詳細內容。

資料表升級現在會把每張表的升級記錄在 `st_table_upgrade`，並帶上為升級行為編版的格式版本。舊格式的工具不再復原新格式做過的改動；紀錄顯示已是最新的資料表不再與資料庫比對，沒有任何變更的啟動因此快很多。升級也明文遵循四項原則：保存資料、以目前的定義為準、不需重複升級，以及資料擋住升級時停下並回報。因此 rebuild 會保留 AutoIncrement 編號，無法重建的部分則拒絕執行。主表欄位的運算式現在可以加總明細列，產生的版面讓多行欄位獨占一整列，DefineEditor 的草擬對話也會顯示進度，並以可點選的問題提問。wire 格式與 1.14.0 相同。

使用 SQLite 或 Oracle 的應用，更新後的第一次升級會把 `Date` 欄位改成新的預設值；在 SQLite 上這會重建那些資料表（見破壞性變更）。

## 新功能與變更

### 每次資料表升級都有紀錄，舊版工具不會改動新版升級過的資料庫

升級執行過的每個資料庫會有一張 `st_table_upgrade`，每張資料表一筆：最近一次升級的狀態（`Upgrading`、`Succeeded`、`Failed` 或 `Verified`）、失敗時的錯誤、最近套用的定義，以及工具的格式版本與框架版本。`SchemaFormat.Current` 是目前建置的格式版本，`TableUpgradeRecordStore` 用來讀取紀錄（`GetRecord`、`GetHighestFormatVersion`、`DescribeNewerFormat`）。

升級在改動任何東西之前，會先讀資料庫記錄的最高格式版本。資料庫被較新的格式升級過時，`db upgrade` 與 `IDatabaseInitializer.UpgradeTables` 回報一次並略過它的資料表；`IDatabaseRepository.UpgradeTableSchema`、`TableSchemaBuilder.Execute` 與 `TableUpgradeOrchestrator.Execute` 則丟出例外。該資料庫不會有任何改動，請用較新的工具升級。說明見[資料庫 Schema 升級指引 §11](../database/database-schema-upgrade.md#11-升級紀錄與格式版本)。

- **背景：** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### `db upgrade` 回報紀錄的狀態

依紀錄判定的資料表顯示 `unchanged (upgrade record)`；上一次升級失敗或沒有完成的資料表，會在該行註明；最後的統計會列出依紀錄判定的表數。程式中由 `TableUpgradeEntry.UnchangedByRecord` 與 `TableUpgradeEntry.PreviousStatus` 提供相同資訊。見[資料庫設定](../database/database-settings-guide.md)。

### rebuild 保留資料列、編號與改名的欄位

rebuild 會複製每個欄位，包括定義沒有宣告的欄位，現在也包括 AutoIncrement 欄位：SQL Server、PostgreSQL、MySQL 與 Oracle 以前會重新編號。各方言都會從舊表的最後編號接續，只有 MySQL 是從複製過來的最大值接續，所以資料表尾端被刪除而空出的編號可能再被使用。同時改名欄位的 rebuild，會把舊欄位複製到新名稱；以前這種情況會被拒絕。

定義沒有宣告、預設值是運算式的欄位，沒有可以重寫的字面值；它會改用該型別的內建預設值，計畫會在警告中列出。這些原則見[資料庫 Schema 升級指引 §1](../database/database-schema-upgrade.md#升級原則)。

### 升級不再重複發生

升級之後再拿定義與資料表比對，現在在每種資料庫上都沒有差異，下一次啟動不會再規劃任何變更。以前以下情況每次升級都會再改一次：SQL Server 的 `DECIMAL`、`NUMERIC`、`SMALLINT`、`BIGINT` 或 `TINYINT` 欄位的預設值；MySQL 的小數預設值；SQLite 的 `Currency` 欄位，在 SQLite 上等於每次都重建資料表。Oracle 的 rebuild 以前完全無法執行，現在可以了。

### SQLite 可以在有資料的表加入需要預設值的欄位

資料表已有資料列時，SQLite 拒絕以 `ADD COLUMN` 加入預設值是運算式或沒有預設值的 `NOT NULL` 欄位，所以在這種表加入 `Date`、`DateTime`、`Guid` 或 `Binary` 欄位會失敗。升級現在改以重建資料表的方式加入這些欄位。

### 不論請求用哪種大小寫，都找得到語系檔

在區分大小寫的檔案系統上，請求 `common` 命名空間時找不到 `Common.Language.xml`，而共用的快取之後會對每種拼法都回傳這個找不到的結果。現在讀取、儲存與監看語系檔時，會找出忽略大小寫後相符的檔案與語系資料夾；用另一種大小寫儲存新的命名空間，會放進既有的資料夾。

### 主表欄位加總明細列

主表的 `ValueExpression`，以及目標為主表的 `FormRule`，可以對同一表單的明細表呼叫 `Sum(Table.field)`、`Count(Table)`、`Min(Table.field)` 與 `Max(Table.field)`：

```xml
<FormField FieldName="total_amount" DbType="Currency" NumberKind="Amount" ReadOnly="true"
           ValueExpression="Sum(OrderDetail.amount)" />
<FormRule RuleId="detail_required" Condition="Count(OrderDetail) &gt; 0" Message="At least one line is required." />
```

每筆明細值先依該欄位自己的小數位數捨入再加總。存檔時伺服端先算明細列，再加總整筆記錄的每一列，payload 沒帶的已存列會先補上；更動這類明細表的 payload 必須帶著主表列，否則存檔會被拒絕（`PolhemMessages.SaveMasterRowMissing`）。Avalonia 與 Blazor head 在明細列被編輯、新增、刪除或取消編輯時重算主表（`FormLiveComputationEngine.RecomputeAggregates`、`FormDataObject.RowEditCanceled`）。`ValidateExpressions` 與 DefineEditor 會指出無法運作的彙總。文件草擬與表單活頁簿的公式欄都會說明彙總，草擬出的表單因此保有合計。說明見[運算式與規則](../definitions/expression-rules.md#明細加總)。

- **背景：** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md)

### 多行欄位在產生的版面中獨占一整列

`FormLayoutGenerator.Generate` 會讓編輯器為 `MemoEdit` 的主表欄位（明確指定 `MemoEdit`，或 `Text` 欄位的 `Auto`）的 `ColumnSpan` 等於版面的欄數；`FormLayoutGenerator.Merge` 新增 memo 欄位時也一樣。文件草擬、草擬預覽與 Excel 匯入都經由它產生版面。既有 FormLayout 檔中的欄位維持原本的跨欄；重新產生該檔時，memo 欄位會獨占一列。草擬時要求某欄位跨整列，該欄位就會設為 `MemoEdit`。

### 草擬對話顯示步驟，並以問題卡提問

`FormDraftSession.Activity` 回報一輪中的每個步驟（思考、模型的推理摘要，以及每次工具呼叫與其對象），新的 `ask_user` 工具讓模型提出結構化問題，每題附選項與建議答案，透過 `FormDraftSession.QuestionsAsked` 發出。提問之後的回覆會先說明這輪改了草稿的哪些地方。`FormDraftingOptions.MarkdownReplies` 告訴模型宿主是否會呈現 Markdown。

在 DefineEditor 的「從文件草擬表單」視窗中，進度卡會跟著目前的步驟，該輪結束時收合成步驟數；問題卡列出選項並標示建議答案，可輸入自由回答，也有「**全部採用建議**」與「**送出回答**」。直接打字回覆仍然可以。見[從文件草擬表單 §3](../guides/document-form-drafting.md#3-草擬表單)。

## 破壞性變更

### 升級改為相信資料表的紀錄，不再逐一比對

- **影響：** 手動改過資料表、並靠下一次升級把它改回來的部署；以及用預設選項呼叫 `TableSchemaBuilder.Execute`、`IDatabaseRepository.UpgradeTableSchema` 或 `IDatabaseInitializer.UpgradeTables` 的程式。
- **之前：** 每次升級都從資料庫的系統目錄讀出每張表的結構，與定義比對。
- **現在：** `UpgradeOptions.CompareMode` 預設為 `UpgradeCompareMode.Fast`。資料表的紀錄顯示上次升級成功或比對一致，而且格式版本是目前的版本、定義與現在相同時，不讀系統目錄就視為沒有變更。在框架之外對這種資料表做的改動，要等定義改變才會被發現。
- **遷移：** 要讓每張表都與資料庫比對，執行 `db upgrade --full-compare`，或傳入 `new UpgradeOptions { CompareMode = UpgradeCompareMode.Full }`。更新後的第一次升級本來就會完整比對每張表，因為還沒有任何紀錄。
- **背景：** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### 會遺失資料表一部分的 rebuild 會被拒絕

- **影響：** 需要 rebuild 的資料表上，有定義沒有宣告的索引，或有框架無法對應型別的欄位的資料庫。
- **之前：** rebuild 照樣執行；會丟掉這種索引，或在這種欄位上中途失敗。
- **現在：** 在執行任何語句之前就拒絕這個計畫。錯誤訊息會指出索引或欄位，資料表與資料列維持原狀。`db upgrade` 在該表那一行回報並繼續處理其他資料表；單表 API 丟出例外。
- **遷移：** 在定義中宣告該索引或欄位，或手動刪除它，再升級一次。見[既有資料擋住升級時](../database/database-schema-upgrade.md#既有資料擋住升級時)。

### SQLite 與 Oracle 的 `Date` 欄位預設為 UTC 當天零點

- **影響：** 在 SQLite 或 Oracle 上有 `Date` 欄位的應用。
- **之前：** 預設值存的是當下的時間點：SQLite 是 `CURRENT_TIMESTAMP`，Oracle 是 `SYS_EXTRACT_UTC(SYSTIMESTAMP)`。採用預設值的資料列，用它自己的日期篩選時比對不到。
- **現在：** SQLite 的預設值是 `(datetime('now', 'start of day'))`，Oracle 是 `TRUNC(SYS_EXTRACT_UTC(SYSTIMESTAMP))`。帶舊預設值的欄位讀回時會被視為差異，所以更新後的第一次升級會改掉它：Oracle 直接修改，SQLite 以重建資料表的方式修改。資料列保留原值，包括舊預設值存下的時間。
- **遷移：** 不需要任何動作。SQLite 資料庫較大時，先執行 `db upgrade --dry-run`，看哪些資料表會被重建。見[資料庫方言差異](../database/database-dialect-differences.md)。

### 名稱只差大小寫的語系檔會被視為錯誤

- **影響：** 在區分大小寫的檔案系統上，有兩個名稱只差大小寫的語系檔或語系資料夾的應用。
- **之前：** 依請求的拼法讀到其中一個。
- **現在：** 讀取或儲存該語系時丟出 `InvalidOperationException`，訊息會指出是哪個檔案或資料夾。
- **遷移：** 把兩個檔案或資料夾合併成一個。
