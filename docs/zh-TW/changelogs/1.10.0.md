# Polhem 1.10.0 — 發佈說明

[English](../../en/changelogs/1.10.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.10.0]` 條目的詳細內容。

本版讓 Blazor Server 端擁有和 Avalonia 端相同的欄位編輯器：名稱相同、契約相同、行為相同，兩端建立與擴充表單的方式因此一致。
兩端共用的規則移到 `Polhem.UI.Core`。wire 格式是 1.9.0 的格式加上新呼叫 `FieldValueChange` 的訊息，1.9.0 的用戶端與 1.10.0 的伺服器（或反過來）可以互通；
只有這個新呼叫需要兩端都是 1.10.0。

## 新功能與變更

### Blazor Server 的欄位編輯器

`Polhem.Web.Blazor.Server.Controls.Editors` 為每種 `ControlType` 提供一個元件：`TextEdit`、`MemoEdit`、`NumericEdit`、
`TimeEdit`、`DateTimeEdit`、`DateEdit`、`YearMonthEdit`、`CheckEdit`、`DropDownEdit`、`ButtonEdit`。名稱與 Avalonia 的欄位編輯器相同，
實作同樣的 `IFieldEditor` 契約（`Bind`、`Unbind`、`SetControlState`、`FieldName`、`FieldValue`），行為也一致：

- 使用者離開輸入框或按 Enter 時才提交值，不是每次按鍵都提交。
- 編輯器自行套用 schema 欄位的中繼資料：`MaxLength`、`ListItems`、數值格式。
- 可否輸入依表單模式、版面欄位的 `ReadOnly` 與 `AllowEditModes` 決定。
- 程式寫入的值，或資料物件重新載入，都會更新編輯器。
- `NumericEdit` 平時顯示格式化後的值，取得焦點時顯示完整精度；輸入無法解析時保留上一個有效值。`TimeEdit` 以 `HH:mm` 儲存。

編輯器的綁定以明確呼叫的 `Bind` 優先，其次是 `DataObject` 參數，最後才是外層的 `FormScope`：

```razor
<FormScope DataObject="dataObject" FormMode="SingleFormMode.Edit">
    <TextEdit FieldName="emp_name" />
    <NumericEdit LayoutField="amountField" />
</FormScope>
```

自訂編輯器繼承 `FieldEditorBase`，覆寫 `RefreshFromSource`；需要 schema 中繼資料時再覆寫 `ApplyMetadata`。
`FieldEditorFactory.GetEditorType` 由 `ControlType` 對應到編輯器型別。

編輯器輸出 `polhem-field-editor` class、各編輯器的修飾 class（例如 `polhem-field-editor--numeric`），不可輸入時再加上
`polhem-field-editor--readonly`；套件本身不附 CSS。日期、日期時間與下拉編輯器的唯讀狀態，以使用者 culture 的文字顯示值，
和 Avalonia 編輯器相同。

`FormDataObject` 補上編輯器需要的功能：指定資料列的 `GetField` 與 `SetField`、指定資料表與欄位的 `GetFormField`，以及
`FieldValueChanged`、`IsDirtyChanged`、`DataSetReplaced` 事件。寫入與欄位現值相同的值，不再把物件標記為已修改。

### Blazor Server 的查詢

綁定到有 `RelationProgId` 欄位的 `ButtonEdit`，執行和 Avalonia `ButtonEdit` 相同的查詢流程：輸入框顯示該欄位的顯示欄位
（例如 `D01 - Engineering`）且為唯讀，按鈕開啟 `LookupDialog`，選中資料列的 `sys_rowid` 與對應欄位透過
`FormDataObject.ApplyLookupSelection` 寫回，按 Delete 或 Backspace 則透過 `ClearLookupSelection` 清除。沒有
`RelationProgId` 時，按鈕觸發 `ButtonClick`。查詢無法載入或選取結果無法寫回時觸發 `LookupFailed`；沒有處理常式時，
訊息顯示為輸入框的提示文字。

`LookupDialog` 是包著 `LookupPanel` 的強制回應覆蓋層；`LookupPanel` 有搜尋框、依目標表單查詢版面呈現的清單與
OK / Cancel，雙擊資料列即可確認。對話框依序從 `Schema` 與 `Connector` 參數、容器中註冊的 `IFormDefinitionSource` 與
`IFormApiConnectorFactory`、circuit 的 `PolhemApiClient` 取得目標 schema 與連接器；最後一種會以 `FormPage` 載入自身
schema 的方式載入。有 Polhem 後端的應用程式不需註冊任何東西；沒有後端的應用程式則以 scoped 註冊自己的來源：

```csharp
builder.Services.AddScoped<IFormDefinitionSource, MyDefinitionSource>();
builder.Services.AddScoped<IFormApiConnectorFactory, MyConnectorFactory>();
```

`DynamicGrid` 新增 `OnRowActivated`（雙擊）與 `SelectedRowId`（要高亮的資料列），供查詢清單使用。

### Blazor Server 的即時計算

`FormPage` 會在使用者編輯時即時重算計算欄位（`ValueExpression`），新增記錄時也會評估預設值運算式，做法與 Avalonia 的
`FormView` 相同。規則是 `Polhem.UI.Core` 新的 `FormLiveComputationEngine`，現在兩端都用它，所以任一端預覽的值都與伺服器
存檔時寫入的值一致。運算引擎與使用者時區由呼叫端提供；Avalonia 的 `FormLiveComputation` 改為套在它之上，公開介面不變。

新的 `Polhem.Web.Blazor.Server.DataObjects.FormLiveComputation` 讓自訂頁面也能使用這個引擎，預設使用共用的
DynamicExpresso 運算引擎。時區要傳 circuit 自己的：

```csharp
var live = new FormLiveComputation(schema, timeZoneProvider: () => client.Session.Credentials.UserTimeZoneId);
dataObject.FieldValueChanged += (_, e) =>
{
    if (!live.IsRecomputing) live.Recompute(e.TableName, e.FieldName, e.Row);
};
```

`FormPage` 的預覽依與 Avalonia `FormView` 相同的 rounding context 四捨五入：登入公司取自定義載入器的
`CompanyAccessor`，有部署幣別與單位主檔時也一併使用（主檔不存在或被拒絕時改用框架預設的小數位數）。儲存時由伺服器做權威的
四捨五入。`Polhem.Web.Blazor.Server` 為了預設運算引擎，現在引用 `Polhem.Expressions`。

Blazor 的 `FormDataObject` 補上與 Avalonia 相同的資料列生命週期：新資料列依 schema 填入預設值（新的 `sys_rowid`、
與主檔的連結、依型別的非 null 值），`RowAdded` 與 `RowDeleted` 回報資料列變更，`BeginRowEdit` / `CommitRowEdit` /
`CancelRowEdit` 暫存單一資料列的編輯，提交前只觸發 `RowEditFieldChanged`，提交時才透過 `FieldValueChanged` 發布。

### 即時計算停止時會告知

運算式無法評估時（例如 `Currency` 欄位上的 `amount * 1.05`：`decimal` 不能與 `double` 字面值一起運算，應寫成 `1.05m`），
該表單仍會停止即時計算，但不再毫無訊號。`FormLiveComputationEngine` 會把原因記在新的 `Degradation` 屬性
（`LiveComputationDegradation`，含欄位、運算式與例外），並觸發一次 `Degraded`；兩個 `FormLiveComputation` 都會轉出這兩者。
Avalonia 的 `FormView` 會顯示一則指出欄位與原因的訊息，並觸發新的 `LiveComputationDegraded` 事件供 host 記錄；
Blazor 的 `FormPage` 會把同樣的訊息留在畫面上，並透過它的 `ILogger` 記一筆帶運算式的 warning。訊息文字是新的
`PolhemUIText.LiveComputationStopped` 鍵。

### Blazor Server 的明細 grid

`FormLayoutPresenter` 與 `FormPage` 現在會呈現版面的明細資料表，每個都是新的 `GridControl`，編輯規則與 Avalonia 的
grid 相同：

- 表單模式不是 View、版面的 `AllowEditModes` 允許、且 `AllowActions` 開放該動作時，才顯示 Add / Edit / Delete 工具列。
  以呼叫端提供的資料表呈現的 grid（list 模式）永遠不可編輯。
- `GridEditMode.InCell` 在每個可編輯的儲存格顯示綁定該列的欄位編輯器，離開儲存格時提交。`GridEditMode.EditForm` 顯示文字，
  在 `RowEditDialog` 編輯資料列；它是包著 `RowEditPanel` 的強制回應視窗，按 OK 前都只暫存編輯（`BeginRowEdit`），按取消會
  還原，新增後取消則移除該空白列。
- `FormLayoutPresenter.DetailEditMode` 決定編輯模式；`IsCompact` 會為手機寬度強制使用編輯表單（見下方「Blazor Server 的
  精簡版面」）。
- 唯讀欄位的表頭加括號，必填欄位的表頭帶有 `polhem-grid__header--required`。

儲存格文字依 `Polhem.UI.Core` 新的 `GridCellFormatter`，Avalonia 的 grid 與 Blazor 的 `DynamicGrid` 現在也都用它，所以兩端
清單中的查詢欄位都會顯示其顯示欄位，而不是 row id。`FieldEditorBase` 也會在 `RowEditFieldChanged` 時更新，編輯表單裡重算
的欄位因此立即顯示。

### Blazor Server 的精簡版面

在手機寬度的螢幕上，Blazor 表單現在會採用與 Avalonia `FormView` 相同的精簡版面：

- `FormLayoutPresenter.IsCompact` 除了讓明細 grid 改用編輯表單，也會讓主檔欄位不論版面的 `ColumnCount` 都排成一欄。
  此時根元素帶有 `polhem-form-layout--compact`。
- `FormPage` 依瀏覽器 viewport 決定：寬度小於 `CompactWidthThreshold`（預設 600 CSS 像素）時為精簡版面，只在 viewport
  跨過門檻時切換。設定 `IsCompact` 則固定版面，頁面不再量測。`DetailEditMode` 決定非精簡版面時的明細編輯模式。
- 新的 `CompactViewportObserver` 負責量測並觸發 `CompactChanged`。直接使用 `FormLayoutPresenter` 的頁面在旁邊放一個：

  ```razor
  <CompactViewportObserver CompactChanged="compact => _isCompact = compact" />
  <FormLayoutPresenter Layout="_layout" DataObject="_data" IsCompact="_isCompact" />
  ```

套件因此首次附帶腳本：一支小型 JavaScript module，以 JavaScript isolation 從 `_content/Polhem.Web.Blazor.Server/` 載入，
host 頁面不必加 `<script>`。host 必須提供 static web assets（`UseStaticFiles` 或 `MapStaticAssets`），Blazor 範本都已具備。
頁面 prerender 時無法執行 JavaScript，所以 prerender 的頁面先以寬版呈現，circuit 連上後才切換。套件仍然不附 CSS。

`ColumnSpan` 比 grid 欄數還寬的欄位，現在會橫跨整個 grid，而不是多長出一欄。

### FormPage 依表單模式運作

`FormPage` 按 **View**（或雙擊資料列）以檢視模式開啟記錄，按 **Edit** 以編輯模式開啟，按 **New** 以新增模式開啟；因此只允許
新增時編輯的欄位（例如鍵值），在已儲存的記錄再次編輯時是唯讀的。見[`FormPage` 一次顯示清單或單筆](#formpage-一次顯示清單或單筆)。

### FormPage 服務多個程式並依使用者權限呈現

`FormPage` 在 `ProgId` 或 `DefinitionLoader` 變更時會重新載入。host 可以把所有程式路由到同一個頁面，例如
`@page "/form/{ProgId}"`，Blazor 會以同一個元件實例呈現；之前頁面會一直停在第一個程式。清單現在會向伺服器要求
`sys_rowid`，放在表單的 `ListFields` 之前，與 Avalonia 的 `ListView` 相同；之前由真實後端提供的清單不含資料列 id，
點選資料列什麼也打不開。這條規則是新的 `Polhem.UI.Core.Connectors.ListSelectFields`，兩端共用。

新的 `Polhem.Web.Blazor.Server.Identity.CircuitUserContext` 保存單一 circuit 的登入使用者、進入的公司與能力。
`AddPolhemBlazor` 以 scoped 註冊它，同時註冊為該 circuit 的 `IUserContext`；`PolhemLoginPanel` 會把登入記錄在它上面。
請透過它進入公司與登出，讓 context 與 client 保持一致：

```csharp
@inject CircuitUserContext UserContext

await UserContext.EnterCompanyAsync(companyId);   // 登入之後
UserContext.SignOut();
```

有能力快照時，`FormPage` 的行為與 Avalonia 的 view 相同：使用者缺少表單權限模型的 `Read` 時隱藏 View，缺少 `Create` 時隱藏 New，
缺少 `Update` 時隱藏 Edit，缺少 `Delete` 時隱藏 Delete，`Create` 與 `Update` 都沒有時隱藏記錄上的 Save；敏感欄位依其類別隱藏或唯讀，數值預覽採用登入公司的小數位數。
host 若直接透過 client 進入公司，context 沒有快照，頁面會把使用者視為不受限。後端仍會檢查每一個呼叫。

版面那一半是 `LayoutCapabilityApplier`，它從 `Polhem.UI.Avalonia`（原本是 internal）移到 `Polhem.UI.Core.Permissions`，
兩端以同一份實作降級版面。

### 兩端共用的欄位規則

`Polhem.UI.Core.Fields` 收納兩端欄位編輯器共用的規則，讓它們不會各自分歧：

- `FieldEditRules.AllowsEdit`：表單模式、版面唯讀旗標與 `AllowEditModes`。
- `FieldValueFormatter.Format`：依使用者 culture 顯示值。
- `NumericFieldFormat`：數值格式解析（含幣別與單位的小數位數）、顯示、輸入剖析，以及寫回的值。
- `DateTimeFieldFormat`：日期時間欄位的顯示、輸入與綁定字串規則。
- `FormLiveComputationEngine`：計算欄位與新資料列預設值的即時計算。
- `GridCellFormatter` 與 `FieldCaptionRules`：grid 儲存格的文字，以及唯讀與必填的標題提示。
- `LookupFieldRules` 與 `LookupDisplay`：欄位是否為查詢欄位、顯示哪些欄位及如何串接，以及選取結果如何寫回或清除。

### 只在查詢選取時套用的關聯對應

標記 `LookupOnly="true"` 的關聯對應，會在使用者於查詢視窗選取資料時回寫，但查詢的 JOIN 不讀它。這樣選取時就能帶回 JOIN
以外的值。以同時存放員工與部門的請假單為例，選員工時一併填入請假單自己的 `dept_rowid` 與部門的顯示欄位，而
`dept_rowid` 仍由自己的關聯 JOIN 出 `ref_dept_*`：

```xml
<FormField FieldName="emp_rowid" RelationProgId="Employee">
  <RelationFieldMappings>
    <FieldMapping SourceField="sys_name"      DestinationField="ref_emp_name" />
    <FieldMapping SourceField="dept_rowid"    DestinationField="dept_rowid"    LookupOnly="true" />
    <FieldMapping SourceField="ref_dept_name" DestinationField="ref_dept_name" LookupOnly="true" />
  </RelationFieldMappings>
</FormField>
```

不加這個旗標的話，JOIN 會從員工那筆讀 `dept_rowid`，對它下的篩選或排序就會用到員工目前的部門，而且 `ref_dept_name`
會同時屬於兩個關聯。來源欄位必須列在目標表單的 `LookupFields`，除非該欄位會回呼伺服器（見下一節）。POLHEM1006 現在會回報只被 LookupOnly 對應填入的關聯欄位，
因為它每次重新載入都是空的。在表單試算表中，於這類對應後面加上 ` (lookup)`。完整說明見
[FormSchema 驅動的資料庫存取](../definitions/formschema-data-access.md#34-只在查詢選取時套用的對應lookuponly)。

### 欄位異動時回呼伺服器

查詢視窗只顯示幾個欄位，選取時卻常需要更多，例如訂單明細要帶回產品的單價。在欄位標上 `ValueChangeCallback="true"`，
使用者變更它時就會呼叫**正在編輯的表單**的 BO 的 `FieldValueChange`，傳入資料表、欄位、新值與該列的複本。
回應帶著要寫回該列的值，以及要顯示在各欄位上的錯誤與警告。

- 關聯欄位不需要寫程式。伺服器依關聯表單的查詢規則讀取關聯列，回傳每個 `RelationFieldMappings` 目的欄位的值，
  包括查詢視窗沒有顯示的。這類欄位的對應來源不必再列在 `LookupFields`：選取時略過它，由回呼填入。
- 其他情形由表單的 BO 覆寫 `FormBusinessObject.FieldValueChange`，先呼叫基底方法，再依欄位名稱把值加進
  `FieldValueChangeResult`。呼叫需要該表單的 `Create` 或 `Update` 權限。
- 只有使用者自己的變更會回呼。回呼寫入的值、查詢選取的寫入、已確認的資料列編輯都不會再回呼；查詢選取在全部寫入後
  只回呼一次。欄位又被改過、或該列已刪除之後才到的回應會被捨棄。
- 兩端做法相同，都經過 `Polhem.UI.Core` 的 `FieldValueChangeCoordinator`。Avalonia 與 Blazor 的 `FormDataObject`
  會為每次寫入標上 `FieldValueOrigin`，並觸發 `FieldValueChangeApplied` 與 `FieldValueChangeFailed`；`FormView` 與
  `FormPage` 顯示訊息。connector 端是新的 `IFieldValueChangeConnector`，由 `FormApiConnector` 實作；沒有實作它的
  connector 不會發出呼叫。
- DefineEditor 的關聯設定視窗有這個旗標的核取方塊；對應來源不在關聯表單的 `LookupFields` 時預設勾選。

定義寫法見 [FormSchema 驅動的資料庫存取](../definitions/formschema-data-access.md#35-欄位異動時由後端帶回整列的值)，
方法說明見 [API 方法參考](../api/api-method-reference.md)，設計理由見
[ADR-058](../../../maintainers/adr/adr-058-field-value-change-callback.md)。

### Northwind 的 Blazor Server 版本

`apps/Polhem.Northwind` 新增 `Polhem.Northwind.Blazor`，一個以 `Polhem.Web.Blazor.Server` 建成的 Blazor Server head：
登入並進入公司、由 `MenuSettings.xml` 產生的選單，以及所有表單共用的一個路由 `FormPage`。它的後端移到類別庫
`Polhem.Northwind.Backend`，JSON-RPC server 與 Blazor head 都執行它，使用同一份定義與同一個資料庫，Blazor head 則在同一個行程內執行。
這個示範也在每個 head 上展示本版的兩項功能：訂單明細的商品會回呼訂單的業務物件、帶回商品單價；訂單表單綁定一個權限模型，
並有只能讀取訂單的 `demo-ro` 帳號。見[它的 README](../../../apps/Polhem.Northwind/README.zh-TW.md#網頁前端blazor-server)。

### DefineEditor 擋下無法解析的運算式

DefineEditor 驗證 FormSchema 時（以及存檔前），會以執行期相同的方式解析每個欄位運算式（`DefaultValueExpression`、
`ValueExpression`）與規則運算式（`When`、`Condition`），把無法解析的列為該欄位或規則的錯誤。典型的情況是數值常值：
帶小數點的常值是 `double`，而 `decimal` 與 `double` 之間沒有運算子，所以 decimal 欄位寫成 `amount * 1.05` 會失敗，
`amount * 1.05m` 則可以解析。這樣的運算式會讓伺服器端存檔失敗，在用戶端的即時計算中則只會讓計算欄位不再更新，
因此在這裡先擋下來。

這項檢查是公開的：`IExpressionEvaluator.Validate` 依變數型別解析單一運算式而不執行，
`FormExpressionCalculator.ValidateExpressions` 對整份 FormSchema 執行它，並為每個失敗回傳一個 `FormExpressionIssue`。
解析錯誤的訊息現在也會指出運算子與運算元型別。

### DefineEditor 設定欄位的關聯

存檔欄位的 `RelationProgId` 現在有一個按鈕可以開啟關聯對話框。關聯表單從方案的 `ProgramSettings` 挑選，輸入時依
ProgId 或顯示名稱篩選；建立清單只讀 `ProgramSettings`，列出主檔欄位只讀選定表單的 FormSchema。每個主檔欄位都可以
對應到一個目的欄位（預設 `ref_<base>_<field>`）並標記 `LookupOnly`，或標記 `FormField.ValueChangeCallback` ——
當被納入的來源欄位不在關聯表單的 `LookupFields` 內時，它預設是勾選的。資料表缺少的目的欄位會接在外來鍵之後新增，
型別與長度取自來源欄位，標題沿用表單工作簿的命名慣例；未勾選的對應會被移除，連帶不再被寫入的關聯欄位也可以一起移除。
套用前，對話框會列出結果會破壞什麼：關聯表單不會回傳的 lookup-only 來源，以及新產生的驗證問題（例如 POLHEM1006）。
非存檔欄位的關聯欄位仍可在樹狀結構中開啟。

### 在樹狀結構中新增與刪除 FormSchema 規則

FormSchema 的樹狀結構只顯示 Rules 資料夾，沒有新增規則的入口，規則因此得手寫進 XML。現在 Rules 資料夾與每一條規則
都提供 **Add FormRule**，新增的規則條件是 `true`（寫好之前不會擋掉任何東西），並選取它以便在屬性清單編輯。
規則的刪除方式與欄位相同。

### 同步時為每個新欄位補上可翻譯的標題

同步已翻譯的表單時，只會為新的存檔欄位補 `zh-TW` 標題，而「是不是新的」是從 TableSchema 判讀的。關聯欄位沒有對應的
資料表欄位，因此在編輯器裡新增的 `ref_*` 欄位從來拿不到 key，翻譯者找不到它。現在只要表單已經有 `zh-TW` 文字，
同步就會為每個新欄位補一個以表單自身標題為內容的標題 key 供翻譯；而每個還沒有 `zh-TW` 標題的關聯欄位，則取外來鍵的
`zh-TW` 標題，若由一般對應從 `sys_id` 或 `sys_name` 帶入，則依表單工作簿匯入的命名再加上「代號」或「名稱」。
既有的翻譯會保留，沒有 `zh-TW` 文字的表單不會產生語言檔，同步預覽會列出各語言檔新增的 key。

### 最近使用的方案，以及 Table Schemas 檢視

DefinePath 資料夾通常就叫 `Define`，所以 DefineEditor 的最近清單改以上一層資料夾命名，只在名稱重複時才加上父資料夾，
並以 `~` 表示家目錄、省略中間路徑來顯示位置。資料夾已不存在的項目仍會列出，但會變暗，並以提示說明資料夾已消失；
Welcome 頁的每個項目都可以移除，**File › Open Recent** 也依同一個變更事件重建。

**Databases** 檢視更名為 **Table Schemas**：它列出的是各 `DbCategorySettings` 分類的資料表，不是 `DatabaseSettings`
裡的資料庫；在多租戶配置下，一個 company 分類代表許多公司資料庫，因此標題、圖示與分類節點都不再讓人聯想到連線。
在 macOS 上，視窗把工作區延伸進標題列，並在紅綠燈右側畫出側邊欄切換按鈕；Windows 與 Linux 維持原生標題列。

### 表單訊息改用訊息列，必填標題改依 schema

被拒絕的存檔或規則訊息原本只是工具列上方一行紅色小字。Avalonia 的表單與清單檢視現在改以帶圖示、會折行、可關閉
（`PolhemUIText.Dismiss`）的警示色訊息列顯示；必填欄位為空時，游標會移到第一個未填的欄位。

必填標題原本只看 layout 的 `Required`，但伺服器檢查的是 schema 的，所以只在 FormSchema 標記必填的欄位會在存檔時
被拒絕卻沒有任何提示。現在主檔欄位與繫結的明細表格兩邊都採用。必填的藍色在深色主題變體上改淺，原本的在深色下很難讀。

### 儲存格內編輯改為取代原值

文字儲存格使用 template column，進入編輯時游標停在點擊的位置，打字會插在原值前面（`40` 變成 `540`）。
`GridControl` 現在在儲存格進入編輯時選取整段文字，按 F2 時把游標留在尾端，而在已選取的儲存格上按鍵時，直接以該字元
開始編輯。按 Escape 之後，編輯器失去焦點時不再把放棄的文字寫回。

### Shell 的內容保持在螢幕鍵盤上方

在手機上，鍵盤是覆蓋在畫面上而不會縮小畫面，因此它蓋住了登入按鈕，表單底部的欄位也可能被蓋住。
`Polhem.UI.Avalonia.Shell` 的根容器現在會把底部留白加高到鍵盤覆蓋的高度，並把取得焦點的編輯器捲回可見範圍，
做法與既有的覆蓋式對話框相同。

### 屬性列可以開啟自己的值編輯器

`PropertyGridControl.ValueEditorProvider` 讓文字或建議輸入的屬性列帶一個按鈕，開啟由宿主提供的編輯器（例如對話框），
方式與 `CollectionEditorProvider` 之於集合相同。該列仍保有文字框或下拉；編輯器執行前會先提交已輸入的文字，
回報有變更時會重新載入屬性列，並以變更前後的值引發 `PropertyValueChanged`。這是純新增，二進位相容。

### 沒有文字的清單項目顯示其值

在 DefineEditor 的集合編輯器新增的清單項目，`Text` 一開始是空的，下拉因此顯示空白選項，而表單工作簿匯入則是以值
當作文字。`ListItem.Text` 現在在沒有設定文字時回傳值，一次涵蓋 DefineEditor、手寫 XML 與所有前端。
該屬性的型別與 setter 都沒有變。

### 範本的 Server + Browser 啟動設定會帶起瀏覽器用戶端

`polhem-avalonia` 範本的 Browser 啟動設定用的是 `dotnet` 類型，而它無法啟動 WebAssembly 專案：對
**Server + Browser** 按 F5 只會起伺服器，其他什麼都沒有，也沒有錯誤。該設定現在改為以背景工作執行用戶端的開發
伺服器，待伺服器就緒後，透過 VS Code 內建的 JavaScript 除錯器在 Chrome 開啟它的網址；結束工作階段時會一併停掉
開發伺服器。

## 破壞性變更

### `DynamicForm` 改由 `FormLayoutPresenter` 取代

- **影響：** 自行呈現 `DynamicForm` 的 Blazor Server 應用程式。只使用 `FormPage` 的應用程式不需處理。
- **之前：** `Polhem.Web.Blazor.Server.Components.DynamicForm` 以一般輸入元素呈現主檔 section，CSS class 為
  `polhem-dynamic-form`、`polhem-dynamic-form__*` 與 `polhem-dynamic-form__input--*`，只依各欄位的 `ReadOnly`。
- **現在：** `Polhem.Web.Blazor.Server.Controls.FormLayoutPresenter` 透過欄位編輯器呈現相同的 section，參數同樣有
  `Layout`、`DataObject`、`IdPrefix`，另外新增 `FormMode` 與 `RoundingContext`。
- **遷移：**
  1. 把 `<DynamicForm ...>` 改為 `<FormLayoutPresenter ...>`，並加上 `@using Polhem.Web.Blazor.Server.Controls`。
  2. 頁面有檢視或新增狀態時傳入 `FormMode`；預設為 Edit，對非唯讀欄位而言與舊行為相同。
  3. 改名 CSS selector：`polhem-dynamic-form` → `polhem-form-layout`（以及 `__section`、`__section-caption`、
     `__grid`、`__field`、`__label` 各部分）；`polhem-dynamic-form__input` → `polhem-field-editor`；
     `polhem-dynamic-form__input--<kind>` → `polhem-field-editor--<kind>`。

### `FormPage` 一次顯示清單或單筆

- **影響：** 使用 `FormPage` 的 Blazor Server 應用程式，以及針對它的工具列撰寫的測試或樣式。
- **之前：** 清單與記錄在同一頁上下排列。點選資料列就以編輯模式載入它，工具列有 New、Save、Delete。
- **現在：** 頁面一次顯示清單或記錄，與 Avalonia 的 `ListView`、`FormView` 相同。清單的工具列有 View、New、Edit、Delete；
  點選資料列只會選取它（`DynamicGrid.SelectedRowId`），雙擊則以 View 開啟。檢視中的記錄有 Back；新增或編輯中的記錄有 Save 與 Cancel。
  儲存成功後回到清單、重新載入並維持選取剛存的資料列；Cancel 與 Back 不儲存直接回到清單。Delete 刪除清單中選取的資料列。
  窄 viewport 上清單與記錄不再上下堆疊。
- **遷移：** 只放置 `FormPage` 的頁面不需修改。原本點資料列後按 Save 的測試，要先選取資料列再按 Edit；原本在開啟的記錄上按 Delete
  的測試，改為在清單選取資料列。

### `FormPage` 以提示顯示失敗的動作

- **影響：** 使用 `FormPage`，並對它顯示的錯誤設定樣式或撰寫測試的 Blazor Server 應用程式。
- **之前：** 載入記錄、儲存或刪除失敗時，`FormPage` 以 `div.polhem-form-page__error` 裡的訊息取代工具列與表單，
  所以伺服器拒絕儲存時，使用者輸入的值會從畫面上消失。
- **現在：** 訊息顯示在表單上方的 `div.polhem-form-page__notice`，工具列與使用者輸入的內容都保留。
  `polhem-form-page__error` 只留給無法載入定義的頁面。
- **遷移：** 為 `polhem-form-page__notice` 設定動作失敗的樣式；在動作之後等待 `polhem-form-page__error` 的測試改為等待提示。

### `IExpressionEvaluator` 新增 `Validate`

- **影響：** 自行實作 `Polhem.Core.Expressions.IExpressionEvaluator` 的應用程式。直接使用或透過 `AddPolhemFramework`
  使用 `DynamicExpressoEvaluator` 的應用程式不需處理。
- **之前：** 介面有 `Evaluate`、`Evaluate<T>` 與 `GetReferencedVariables`。
- **現在：** 另有 `Validate(string expression, IReadOnlyDictionary<string, Type> variableTypes, Type returnType)`，
  運算式無法依這些變數型別解析時丟出 `ExpressionEvaluationException`。
- **遷移：** 以 `Evaluate` 使用的設定解析運算式、不執行，以此實作 `Validate`。無法只解析不執行的引擎，可以用各變數型別的
  預設值執行一次，但這樣讀取時鐘或其他狀態的 helper 會在設計期檢查時執行。
- **背景：** [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)（1.x minor 版的破壞性變更）；
  `IExpressionEvaluator` 不在 [ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md)
  允許於 minor 版增加成員的介面之列。

### 移除 `FormField.LookupProgId` 與 `FormField.LookupFieldMappings`

- **影響：** 設定了 `LookupProgId` 或 `LookupFieldMappings` 的 FormSchema 定義或程式碼，以及填了「查詢表單」或
  「查詢帶回欄位」欄的表單試算表。只使用 `RelationProgId` 與 `RelationFieldMappings` 的定義不需處理。
- **之前：** 設了 `LookupProgId` 時查詢視窗開啟它；宣告了 `LookupFieldMappings` 時以它取代 `RelationFieldMappings` 回寫。
- **現在：** 查詢視窗一律開啟 `RelationProgId`，並回寫 `RelationFieldMappings` 的每一筆。仍帶有 `LookupProgId` 屬性或
  `LookupFieldMappings` 元素的定義檔可以正常載入，只是會略過它們；試算表的兩個查詢欄也會被略過。
- **遷移：**
  1. 把 `LookupFieldMappings` 中不該被 JOIN 讀取的項目移到 `RelationFieldMappings`，並加上 `LookupOnly="true"`；
     只是重複關聯對應的項目直接刪除。
  2. 原本用 `LookupProgId` 縮小候選資料的，改為覆寫目標 BO 的 `GetLookupFilter`；若只有這個欄位需要縮小，且那支表單讀的是同一張表，
     就讓 `RelationProgId` 直接指向它。
  3. 程式碼中的 `LookupFieldRules.ResolveProgId(field)`（本版新增）改為 `field.RelationProgId`。
- **背景：** [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)（1.x minor 版的破壞性變更）。
