# Polhem 1.16.0 — 發佈說明

[English](../../en/changelogs/1.16.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.16.0]` 條目的詳細內容。

表單清單現在可以下查詢條件：表單宣告可查詢的欄位，Avalonia、MudBlazor 與 Fluent UI 的清單就會顯示查詢窗格，以標籤（chip）列出生效中的條件，可依使用者儲存查詢或分享給全公司，並可用「我」代表登入的使用者。運算式新增業務函式與帶條件的明細彙總；允許清單（allowlist）會檢查不能完全信任的作者所寫的運算式；`Polhem.Definition.Drafting` 可依白話描述撰寫表單規則，DefineEditor 在新的規則對話框中提供這項功能。總計或規則會讀取的存檔，現在會檢查 payload 只含一筆記錄、且只含該記錄自己的資料列。本版也把 UI 套件的公開介面縮小到應用程式實際使用的部分，並把以選用參數結尾的公開成員改為參數物件或多載。

wire 新增了使用者查詢的訊息，以及 EnterCompany 回應的兩個選用成員。1.15.0 的 client 連 1.16.0 的 server 仍可運作，因為未知的成員會被略過；TypeScript client 需要重新產生的契約才能使用新訊息。

各類應用需要處理的項目：

- **所有使用資料庫的應用**：更新後的第一次升級會改變參照用 `Guid` 欄位的預設值，在 SQLite 上會重建這些資料表；之後 1.15.0 的工具會拒絕這個資料庫（[參照用的 `Guid` 欄位預設為空 GUID](#參照用的-guid-欄位預設為空-guid)）。
- **清單篩選會在文字中輸入 `_` 的應用**：[`Contains`、`StartsWith`、`EndsWith` 只把 `%` 當萬用字元](#containsstartswithendswith-只把--當萬用字元)。
- **對有明細總計或規則的表單直接呼叫 API 存檔的呼叫端**：[總計或規則會讀取的存檔會檢查記錄](#總計或規則會讀取的存檔會檢查記錄)。
- **呼叫 UI 規則型別、繼承 Blazor 元件基底類別，或自行註冊 Blazor client 的程式碼**：[只有框架 UI 套件使用的 UI 型別不再公開](#只有框架-ui-套件使用的-ui-型別不再公開)。
- **使用物件樹命令或拖放的程式碼**：[物件樹的命令與拖放型別移到 `Polhem.UI.Core`](#物件樹的命令與拖放型別移到-polhemuicore)。
- **呼叫 `UpgradeTables`、`BuildSelect`、`BuildCount`、運算式樣本方法或 `ExpressionFunction` 的程式碼，以及以 `CreateLocal`、`CreateRemote` 編譯的組件**：[以選用參數結尾的成員改用參數物件或多載](#以選用參數結尾的成員改用參數物件或多載)。
- **使用 `Polhem.AI.Claude` 的宿主**：[對 Claude 的請求預設為中等 effort](#對-claude-的請求預設為中等-effort)。

## 新功能與變更

### 表單清單的查詢條件

`FormSchema.QueryFields` 列出清單可供查詢的主表欄位，與 `ListFields` 一樣以逗號分隔；留空時提供 `ListFields`。`FormSchema.GetQueryFields` 負責解析，會排除 `sys_rowid` 與 `ProtectedFields` 列出的儲存欄位；analyzer `POLHEM1004` 會回報不對應任何欄位的項目。DefineEditor 與表單活頁簿都能編輯這個屬性；留空時不寫入檔案，所以既有的定義檔不會改變。

`Polhem.UI.Core.Criteria` 是與 UI 無關的模型：`CriteriaField` 描述欄位，以及依欄位種類提供的運算子；`CriteriaRow` 存放一個條件，值已轉成欄位的型別；`QueryCriteria` 以 AND 組合各列，並支援報表用的必填列與預設列。`GetListFilterConverter` 把條件轉成 `GetList` 接受的 `FilterNode`，相對日期（本月、最近 30 天）以使用者的今天計算。`CriteriaField.FromQueryFields` 傳回清單提供的欄位，並排除使用者無權讀取的欄位。

表單提供查詢欄位時，Avalonia 的 `ListView`，以及 MudBlazor 與 Fluent UI 的 `FormPage`，會顯示「查詢」按鈕。條件在側邊窗格開啟：寬視窗時停靠在清單旁，較窄時覆蓋在清單上，手機上則蓋住整頁；生效中的條件以標籤顯示在清單上方，每個都可以移除。Avalonia 的 `CriteriaPanel` 也可以放在自己的畫面中。在 Blazor 頁面上，欄位標題的篩選是同一組條件中的一列，所以窗格、標籤與儲存的查詢都會包含它。

與員工相關的欄位或擁有者欄位上的條件，可以填入「**我**」：查詢執行時解析成登入的使用者。EnterCompany 為此回傳使用者與其對應員工的列 id，透過 `IUserContext.Identity` 提供給畫面。

說明見[清單查詢條件](../guides/list-query-conditions.md)。

### 儲存的查詢

使用者可以依表單以名稱儲存條件，設為個人或分享給全公司，並指定一個作為清單的預設查詢。查詢存放在公司資料庫的 `st_user_query` 與 `st_user_query_default`，下一次升級會建立這兩張表。`FormBusinessObject` 新增 `GetUserQueries`、`SaveUserQuery`、`DeleteUserQuery` 與 `SetDefaultUserQuery`；每個方法都需要表單的讀取權限，且只有查詢的建立者可以覆寫、改名或刪除。API client 的 `FormApiConnector` 實作新的選用介面 `IUserQueryConnector`，既有的 `IFormApiConnector` 實作仍可編譯。

`UserQueryCodec` 以有版本的 XML 儲存條件。儲存的查詢若用到表單已不再提供的欄位或運算子，會套用其餘條件，並指出略過了哪些。Avalonia、MudBlazor 與 Fluent UI 的查詢窗格會顯示儲存查詢列，提供儲存、另存、改名、分享、刪除與設為預設。見[清單查詢條件 §7](../guides/list-query-conditions.md#7-儲存的查詢)。

### 業務函式與帶條件的明細彙總

運算式新增 `IsBlank`、`Between`、`In`、`DaysBetween`、`MonthEnd` 與 `RegexMatch`，只依引數計算。因為文字與數值欄位不會是 null，`IsBlank` 把零也視為空白；`RegexMatch` 以不回溯的方式比對，所以含反向參照或環視的樣式會被回報為不支援。

主表運算式可以逐列檢查明細：`Count(Table, condition)`、`Any(Table, condition)` 與 `All(Table, condition)`。沒有資料列時，`Count` 為 0、`Any` 為 false、`All` 為 true。`ValidateExpressions` 會依明細表的欄位檢查條件。

每個業務函式都帶有摘要與範例（`ExpressionFunction.Summary`、`ExpressionFunction.Example`），DefineEditor 的運算式編輯器會在函式旁與自動完成中顯示。編輯器現在也透過新的 `FormExpressionCalculator.ValidateExpression`，以與表單驗證相同的方式檢查明細彙總。說明見[運算式與規則](../definitions/expression-rules.md)。

- **背景：** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md)

### 不受信任作者的運算式允許清單

剖析運算式並不是沙箱。`IExpressionAllowlist`（位於 `Polhem.Core`，由 `DynamicExpressoEvaluator` 實作）在運算式執行前檢查：先檢查大小限制，再只接受變數、業務函式、運算子、字面值與一份固定的成員清單。`FormExpressionCalculator.FindAllowlistViolations` 可檢查整份 schema 或單一運算式，`ValidateUntrustedExpression` 會拒絕過大、無法剖析或超出清單的運算式。`RegexMatch` 不論樣式為何都不在清單內。定義檔中的運算式不強制套用：DefineEditor 會把超出清單的項目列為警告，運算式照常執行。

運算引擎過去對某些文字（例如把業務函式名稱當成值使用）擲出 `InvalidOperationException`，現在改為契約宣告的 `ExpressionEvaluationException`。

- **背景：** [ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### 以白話撰寫表單規則，以及 DefineEditor 的規則對話框

`RuleDrafting`（`Polhem.Definition.Drafting.Rules`）依使用者描述要檢查的內容撰寫一條 `FormRule`，可在同一段對話中修改，也能解釋既有的規則。送出的規則必須通過 `ValidateUntrustedExpression`、訊息具備要求的每種語言，且運算引擎對每列樣本算出的結果與模型宣稱的相符，才會被接受；結果中的樣本是引擎算出的。`RuleDraftResult` 會回報一次請求花費的呼叫次數、token 與時間。`FormExpressionCalculator.EvaluateMasterRuleSample` 以樣本明細列評估主表規則。

在 DefineEditor 中，「**Add FormRule**」與雙擊規則會開啟規則對話框，可設定規則檢查的資料表、When、Condition、觸發時機、是否啟用與訊息；兩個運算式都會邊輸入邊檢查，並可依序以 When、Condition 試算樣本。對話框中的 AI 助理可以草擬或解釋規則，並在確認對話框時把訊息翻譯寫入表單的語系檔。運算式編輯器現在只編輯欄位運算式。見[運算式與規則](../definitions/expression-rules.md#用白話撰寫規則)，其中也說明了[存檔前規則可以信任什麼](../definitions/expression-rules.md#規則可以信任什麼)。

- **背景：** [ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### UI 套件升級

Avalonia 升到 12.1.6、MudBlazor 升到 9.14.0、Fluent UI Blazor 升到 5.1.0。`Polhem.UI.Avalonia` 的最低需求維持 12.0.0。Fluent UI 5.1.0 修正了 `PolhemDataGrid` 所迴避的已釋放模組呼叫，所以 Fluent 的格線改回使用 `FluentDataGrid`。

### Blazor head 的對話框與鍵盤操作

在兩個 UI 套件上，Esc 可以關閉從列編輯對話框開啟的查詢對話框；焦點落回頁面本體時，Esc 也能關閉對話框，而列編輯對話框維持開啟。Fluent UI 的對話框關閉後，會把焦點還給原本持有焦點的控制項。`PolhemDialog`（Fluent）現在實作 `IAsyncDisposable`，以釋放它的腳本模組。

### MySQL 新增 `sys_rowid` 時為每列既有資料產生各自的 id

開啟 binary logging 時，MySQL 不允許在已有資料的表上新增預設為 `UUID()` 的 `NOT NULL` 欄位，所以過去新增欄位時填入空 GUID，所有既有資料列共用同一個列 id。升級現在會先為每一列填入各自的 GUID，再還原預設值。schema 格式升到 3。

## 破壞性變更

### 參照用的 `Guid` 欄位預設為空 GUID

- **影響：** 所有使用資料庫的應用（更新後的第一次升級），以及以 `IDialectFactory.GetDefaultValueExpression(FieldDbType.Guid)` 組 SQL 的程式碼。
- **之前：** 所有 `NOT NULL` 的 `Guid` 欄位預設為產生的 GUID（`newid()`、`gen_random_uuid()`、`UUID()`、`SYS_GUID()`、`hex(randomblob(16))`）。寫入時沒給參照欄位（例如 `st_employee.user_rowid`）的資料列，會連到一筆不存在的資料，而框架把 `Guid.Empty` 視為「沒有連結」。
- **現在：** 只有 `sys_rowid` 保留產生的預設值，其他 `Guid` 欄位都預設為空 GUID，`GetDefaultValueExpression(FieldDbType.Guid)` 也改為傳回空 GUID 的字面值。`SchemaFormat.Current` 為 3。下一次升級會改變既有欄位的預設值，就地修改，或在 SQLite 上重建資料表；已存的值會保留。由 1.16.0 升級過的資料庫，1.15.0 的工具會拒絕處理。
- **遷移：** 不需要做任何事。SQLite 資料庫較大時，先執行 `db upgrade --dry-run` 看哪些資料表會重建，並同時更新所有會改動資料庫的工具。參照欄位中已經存有隨機 id 的資料列會保留原值，必要時請自行以 update 清除。
- **背景：** [ADR-065](../../../maintainers/adr/adr-065-table-upgrade-records-and-schema-format.md)

### `Contains`、`StartsWith`、`EndsWith` 只把 `%` 當萬用字元

- **影響：** 在 `Contains`、`StartsWith` 或 `EndsWith` 條件的值中使用 `_` 的篩選，以及 SQL Server 上含 `[` 的值。
- **之前：** 值未經跳脫直接放進 `LIKE` 樣式，所以 `_` 比對任一字元（`A_01` 也會比對到 `AB01`），在 SQL Server 上 `[A]` 會比對任何含 `A` 的值。
- **現在：** `_`、跳脫字元，以及 SQL Server 上的 `[` 都只比對自己；輸入的 `%` 仍是萬用字元。`ComparisonOperator.Like` 不變，因為呼叫端自己寫完整的樣式。
- **遷移：** 原本依賴 `_` 比對單一字元的篩選改用 `%`，需要完整樣式時改用 `ComparisonOperator.Like`。見[清單查詢條件 §5](../guides/list-query-conditions.md#5-文字比對)。

### 總計或規則會讀取的存檔會檢查記錄

- **影響：** 對主表運算式或啟用中的存檔前規則會彙總明細表的表單直接呼叫 API 存檔，且送出框架 client 不會送的 payload 的呼叫端。
- **之前：** 只有主表運算式讀取的明細表，才會補上部分 payload 未帶的已存資料列，所以像 `Count(Lines) > 0` 這樣的規則只看到呼叫端送來的列。沒有權限模型的表單，不檢查一個 payload 含多筆記錄、未變更但改寫了值的資料列、其他記錄的明細列，以及被改掉的列 id。
- **現在：** 總計與存檔前規則彙總的明細表都會補回已存的資料列；payload 若變更這些表的資料列卻沒帶主表列、含一筆以上的有效記錄（`PolhemMessages.SaveOneRecordRequired`）、帶有其他記錄的資料列（`SaveDetailRecordMismatch`），或改了某列的 `sys_rowid`（`SaveRowKeyChanged`），存檔會被拒絕。未變更的主表列改用已存的值；不存在於資料庫的主表列以 `SaveConcurrencyConflict` 拒絕。
- **遷移：** 每次呼叫只存一筆記錄，明細變更時一併帶上主表列，並保留讀取時取得的列 id。必須對自行組 payload 的呼叫端成立的檢查，請寫在 `DoBeforeSave`。
- **背景：** [ADR-066](../../../maintainers/adr/adr-066-detail-aggregates-in-expressions.md)、[ADR-067](../../../maintainers/adr/adr-067-form-rules-from-plain-language.md)

### 只有框架 UI 套件使用的 UI 型別不再公開

- **影響：** 呼叫共用 UI 規則、繼承 Blazor 元件基底類別，或不透過宿主套件自行註冊 Blazor client 的應用。
- **之前：** 這些型別與成員都是公開的。
- **現在：** 改為 internal，透過 `InternalsVisibleTo` 提供給框架的 UI 套件；部分已移除。

  | 套件 | 型別或成員 | 現在 |
  |------|-----------|------|
  | `Polhem.UI.Core` | `FieldValueChangeCoordinator` | internal；改用 `FormDataObject.FieldValueChangeApplied` 與 `FieldValueChangeFailed` |
  | `Polhem.UI.Core` | `CardListState`、`DateTimeFieldFormat`、`NumericFieldFormat`、`FieldValueFormatter`、`GridCellFormatter`、`FieldCaptionRules`、`FieldEditRules`、`GridColumnRules`、`LookupDisplay`、`LookupFieldRules`、`RelationOpenRules`、`ListSelectFields`、`FormDataGuard`、`FormLiveComputationEngine`、`ListPagingState` | internal |
  | `Polhem.UI.Core` | `ListFilterState` | 移除；欄位篩選改為清單 `QueryCriteria` 中的列（`ColumnFilterCriteria`） |
  | `Polhem.Web.Blazor` | `FormPageBase.Filters`、`GridControlBase.Filters`、`GridColumnFilterBase.Filters` | 移除；格線改用 `ColumnFilters` |
  | `Polhem.Web.Blazor` | `PolhemBlazorText`、`FormScopeContext`、`IGridEditorSlot`、`PolhemShellText` | internal |
  | `Polhem.Web.Blazor` | 元件基底類別（`FormPageBase`、`GridControlBase`、`FormLayoutPresenterBase`、對話框、面板、查詢窗格、欄位篩選與 shell 的基底類別）的 protected 成員，以及 `LookupPanelBase` 的 public 成員 | internal；`FieldEditorBase` 與各型別編輯器基底類別維持不變 |
  | `Polhem.Web.Blazor` | `IBlazorDefinitionOptions`、`IShellLanguageSwitcher`、`PolhemBlazorClientServiceCollectionExtensions` | internal；改呼叫 Server 或 Wasm 宿主套件的註冊方法 |
  | `Polhem.Web.Blazor.Mud`、`.Fluent` | `FieldEditorFactory` | internal |
  | `Polhem.Web.Blazor.Fluent` | `PolhemDataGrid` | 移除；Fluent UI 5.1.0 已修正它所迴避的問題 |

- **遷移：** 移除這些呼叫，或把規則複製到應用程式中。新的欄位編輯器仍然繼承 `FieldEditorBase`。`Polhem.UI.Core`、`Polhem.Web.Blazor` 與其 UI、宿主套件請一起更新：它們共用 internal 成員，混用版本可能在執行期失敗。
- **背景：** [ADR-059](../../../maintainers/adr/adr-059-blazor-shared-layer.md)、[ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)

### 物件樹的命令與拖放型別移到 `Polhem.UI.Core`

- **影響：** 使用 `ITreeNodeCommandProvider`、`ITreeNodeDragDropHandler`、`TreeNodeCommand` 或 `TreeNodeDropPosition` 的程式碼，例如為 Avalonia `ObjectTreeView` 提供命令的類別。
- **之前：** 位於 `Polhem.Definition` 的 `Polhem.Definition.ObjectTree`。
- **現在：** 位於 `Polhem.UI.Core` 的 `Polhem.UI.Core.Trees`。`ObjectTreeBuilder`、`ObjectTreeNode` 與物件樹的其他型別仍在 `Polhem.Definition.ObjectTree`。
- **遷移：** 加上 `using Polhem.UI.Core.Trees;`，專案尚未參考 `Polhem.UI.Core` 時加上參考。

### 以選用參數結尾的成員改用參數物件或多載

- **影響：** 呼叫或實作下列成員的程式碼，以及以 `CreateLocal`、`CreateRemote` 編譯的組件（不帶 payload options 的呼叫原始碼相容，二進位不相容）。
- **之前：** 各成員以選用參數結尾；`ExpressionFunction` 則以 `System.Reflection.ParameterInfo` 描述參數。
- **現在：**

  | 之前 | 現在 |
  |------|------|
  | `IDatabaseInitializer.UpgradeTables(options, dryRun, tableCompleted, tableNames)` | `UpgradeTables(new TableUpgradeRequest { Options, DryRun, TableCompleted, TableNames })` |
  | `IFormCommandBuilder.BuildSelect(tableName, selectFields, filter, sortFields, skip, take)`，介面與各 provider 的 builder | `BuildSelect(tableName, new FormSelectQuery { SelectFields, Filter, SortFields, Skip, Take })` |
  | `IFormCommandBuilder.BuildCount(tableName, filter = null)` | `BuildCount(tableName, filter)`；filter 為必填，可傳 `null` |
  | `FormExpressionCalculator.EvaluateRuleSample` / `EvaluateFieldSample(..., values, timeZoneId = "")` | `(..., new ExpressionSample { Values, TimeZoneId })`；樣本帶有 `DetailRows` 時擲出 `ArgumentException` |
  | `ExpressionFunction(name, returnType, IReadOnlyList<ParameterInfo>)`、`ExpressionFunction.Parameters` | `ExpressionFunction(name, returnType, IReadOnlyList<ExpressionParameter>)`；`Parameters` 是 `ExpressionParameter`（名稱與型別）的清單 |
  | `PolhemApiClient.CreateLocal(services, payloadOptions = null)`、`CreateRemote(endpoint, apiKey, payloadOptions = null)` | 不帶 payload options 的多載，以及帶 payload options 的多載；後者拒絕 `null` |

- **遷移：** 依上表改寫呼叫並重新建置。`new TableUpgradeRequest()` 或 `new FormSelectQuery()` 的意義等同於原本省略選用參數。
- **背景：** [ADR-052](../../../maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)

### 對 Claude 的請求預設為中等 effort

- **影響：** 使用 `Polhem.AI.Claude` 且沒有設定 `ClaudeChatOptions.Effort` 的宿主。
- **之前：** `Effort` 預設為 `ClaudeEffort.High`。
- **現在：** 預設為 `ClaudeEffort.Medium`，與 Claude Opus 5.5 模型本身的預設相同。請求回應較快，困難的請求推理可能較短。
- **遷移：** 設定 `Effort = ClaudeEffort.High` 即可維持原本的行為。
