# Polhem 1.13.0 — 發佈說明

[English](../../en/changelogs/1.13.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[Unreleased]` 條目的詳細內容，發佈時會成為 `[1.13.0]`。

本版尚未發佈。多家公司現在可以共用一個公司資料庫，以資料列區隔；Avalonia 與 Blazor head 共用同一個位於 `Polhem.UI.Core` 的 `FormDataObject`；框架的 business object 每個請求也只讀一次 session 的公司。MessagePack 的 wire 格式與 1.12.1 相同；經由 JSON body codec 時，`DateTime` 改以帶 `Z` 的 UTC 時間點送達（見破壞性變更中的「經由 JSON body codec 傳遞的 `DateTime` 以 UTC 時間點送達」）。

## 新功能與變更

### 一筆過長的稽核值不再讓整批遺失

稽核紀錄以最多 100 筆為一批，在一個交易中寫入 log 資料庫。有幾個值直接來自未登入的呼叫端，例如登入失敗時的帳號，或 JSON-RPC
的方法名稱。只要一個值超過欄寬，SQL Server、PostgreSQL、MySQL 與 Oracle 就會拒絕整批寫入，同批的其他紀錄全部遺失，呼叫端因此
可以抹掉其他使用者的稽核紀錄；PostgreSQL 上的 NUL 字元也會造成同樣結果，孤立的 UTF-16 surrogate 則讓 PostgreSQL 的驅動程式無法編碼該敘述。SQLite 這幾項都不檢查，所以在 SQLite 上看不出來。

現在字串值會截斷到 log 資料表 `TableSchema` 宣告的欄寬，值中的 NUL 字元與孤立的 UTF-16 surrogate 也會換成 U+FFFD。資料庫仍拒絕、或驅動程式無法編碼的批次會改為逐筆重試，只有失敗的紀錄才寫入備援檔；連續兩筆
失敗視為資料庫中斷，批次其餘的紀錄不再嘗試，直接寫入備援檔。備援檔會跳脫值中的反斜線、tab、CR 與 LF，其他控制字元與 Unicode
的行、段落分隔字元則寫成 `\uXXXX`，以逐行讀取時，值不會跑到另一行。

### 含 Binary 欄位的資料表可經由 JSON 讀回

自 1.0.0 起，含 `Binary` 欄位的 `DataTable` 無法經由 JSON body codec 或 Plain 格式讀回：欄位的預設值是空的 `byte[]`，
以 base64 寫出後被讀回成字串 `""`，而 `byte[]` 欄位不接受這個值，伺服器因此回應內部錯誤。含 Binary 欄位的表單可以開啟新紀錄，
但 JSON 用戶端（例如 polhem-connector-js）無法儲存；宣告 `json` codec 的 .NET 用戶端甚至無法讀到新紀錄。MessagePack 不受影響。

現在欄位的預設值會依欄位型別讀回，與該欄的儲存格相同。同一個修正也讓文字欄位中像日期的預設值維持為文字；原本會被讀回成重新格式化的日期。

### 含唯讀欄位與已變更列的資料表可經由 JSON 讀回

JSON body codec 與 Plain 格式會先把欄位設為唯讀，再還原各列。還原 `Modified` 列時，會把目前值寫進已經加入資料表的列，
唯讀欄位會拒絕這個寫入，整個 payload 因此以 `ReadOnlyException` 失敗。以 `DataTable.Load` 讀出的資料表（包括框架未指定
欄位型別時的非同步查詢），會把 provider 回報為唯讀的欄位（例如 identity 或計算欄位）設為唯讀；這類資料表帶著修改過的列
送回時就會觸發。唯讀旗標現在改在還原各列之後才套用，與 MessagePack 自 1.0.0 起的做法相同。

### 字串型別的過濾值會依其欄位型別讀取

`Plain` body 沒有指名 CLR 型別，因此以日期、`Guid` 或加了引號的數字寫出的過濾值，會以字串進入查詢、以文字繫結。
PostgreSQL 拒絕拿它與有型別的欄位比較（`operator does not exist: date >= text`），Oracle 轉換失敗；SQL Server
則把加了引號的小數轉成欄位本身的精度，`'10.5'` 對整數精度的欄位會以 11 比較，不報錯就查無資料。表單的清單、筆數與刪除，現在會在組查詢之前，把過濾條件中的字串值轉成所比對欄位的型別：
`DateTime` 欄位讀成 UTC 時間點（沒帶時差的文字視為 UTC），`Date` 欄位讀取寫出的日期，`Guid`、數值與 `Boolean`
欄位讀取與文化無關的文字形式；日期只接受 ISO 8601 形式。`String`、`Text` 與 `Time` 欄位以及 `LIKE` 系列運算子
保留字串。不符合欄位型別的字串，會在查詢送到資料庫之前以 `-32602 InvalidParams` 拒絕，訊息會指出欄位（直接呼叫 business object 或
repository 的程式碼捕捉的是 `InvalidRequestValueException`，它是 `ArgumentException`），包括資料庫過去會自行轉換的文字，例如數字欄位的
`""`、布林欄位的 `1`。

這個轉換適用於任何 codec 送來的字串值；其他型別的值不受影響。relation 欄位依其宣告的 `DbType` 轉換。見
[Plain body 裡的值](../api/jsonrpc-frontend-integration.md#plain-body-裡的值)。

### 各 head 共用的 UI 規則移到 `Polhem.UI.Core`

綁在單一列上的 Avalonia 編輯器（例如編輯表單中的明細列），每當表單替換資料集就會重讀該列。替換之後 data object
已不擁有那一列，因此重讀會在替換過程中擲出 `ArgumentException`，這類編輯器開著時 `NewAsync` 就會失敗。現在改為
保持不動，與 Blazor 編輯器原本的做法相同。

這項判斷背後的規則，以及時間欄寫回、lookup 顯示欄位解析、選單展平、勾選欄判讀與排序標記的規則，原本在兩個 head
各寫一份，現在只在 `Polhem.UI.Core` 寫一次：`FieldValueChangeFilter`、`TimeFieldFormat`、`MenuRows`，以及
`GridCellFormatter` 的 `IsChecked` 與 `SortMark`。這些都是新增，沒有移除任何公開成員。

### Blazor grid 提交一格、選取一張卡片時，只重繪有變動的部分

在儲存格內編輯的 grid 提交一個值時，整個 grid 的每一格都會重繪；在手機上選取一張卡片時，每一張卡片都會重繪。Blazor Server
上每一次重繪都要經由 circuit 傳送：200 列 15 欄的 grid 提交一格要送 45 到 58 KB，而移到下一格只要 3 到 6 KB；1000 張
卡片選取一張要送 44 KB。現在儲存格只在顯示內容改變、或正持有編輯器時重繪，編輯器的參數也只在那時建立。每張卡片是一個
`ListCard`，只在它的資料列、版面或選取狀態改變時重繪。提交一格現在送 9 到 22 KB，大部分是 UI 框架自己的表格重繪；選取
卡片送出的量則與清單有幾張卡片無關。`GridEditorCell` 的參數因此改變，見下方的破壞性變更。

### `PolhemAccessTokenProvider` 標為過時

框架與範例都沒有放置 `PolhemAccessTokenProvider`。頁面從 circuit 的 client（`Client.Session.Credentials`）讀取登入狀態，
應用程式的 `PolhemShellLayout` 則持有登入狀態。這個元件已標上 `[Obsolete]`，預計在 2.0 移除。`PolhemDataGrid`（Fluent UI）與
`FocusedButton`（MudBlazor）維持公開，因為 Razor 只能以標記放置公開型別的元件，但已從 IntelliSense 隱藏：它們分別屬於所在套件的
grid 與對話框。

### Blazor grid 會取消訂閱，UI 套件共用規則

MudBlazor 與 Fluent UI 的 grid 在共用 base 的 `IDisposable` 之外又實作了 `IAsyncDisposable`。renderer 對這種元件只呼叫
`DisposeAsync`，它釋放了 grid 的編輯器腳本，卻從未取消 base 對 data object 的訂閱，因此 data object 會一直留著頁面
顯示過的每個 grid，並持續對它們觸發事件。共用的 `GridControlBase` 現在兩者都實作，`DisposeAsync` 也會取消訂閱（框架以外衍生的 grid 見下方的破壞性變更）。

兩個 Blazor UI 套件各自寫出的規則，現在放在 `Polhem.Web.Blazor`，各套件只保留標記：欄位篩選（`GridColumnFilterBase`）、
選單抽屜的開合（`ShellLayoutBase`）、卡片點擊與捲回第一張卡片（`FormPageBase`）、數值或時間輸入是否被拒的判斷
（`TextEditorBase.TryCommitText`）、grid 的編輯器腳本、列與表頭的 CSS 類別（`GridControlBase`），以及列編輯與確認
對話框的參數（`RowEditDialogBase`、`ConfirmDialogBase`）。原本只有瀏覽器測試的欄位篩選，新增了 bUnit 行為測試，MudBlazor 與 Fluent UI 套件各自以自己的篩選元件執行。

從套件元件搬到新 base 的成員，在公開 API 基準中列為自元件移除。以參數設定或呼叫它們的程式碼，經由 base 照常編譯與
執行。`GridControlBase` 新增的成員（`OpenPopupSelector`、`ReplayDelayMilliseconds`、`RefreshRowList`）都是 virtual，
沒有設定 `OpenPopupSelector` 的 grid 不會載入編輯器腳本，因此既有的衍生 grid 行為不變。`FormPageBase.ScrollCardsToTopAsync` 的預設行為改為把視窗捲到頂端，不再什麼都不做；卡片在自己的元素內捲動的
UI 套件請覆寫它。

### `DbAccess` 的每個入口都會記錄資料庫異常

資料庫異常紀錄（`st_log_anomaly_db`）原本只記錄 `Execute`。現在 `ExecuteAsync`、`ExecuteBatch`、`ExecuteBatchAsync`、`Query`、
`QueryAsync`、`UpdateDataTable` 與 `UpdateDataTables` 也記錄同樣的異常：指令失敗時記 Error 或 Timeout，Warning 等級時記 Slow、
LargeAffected 或 LargeResult。批次中的每道指令各自記錄，開連線、開交易與 commit 也會記錄，分別以 `OPEN`、`BEGIN TRANSACTION` 與 `COMMIT` 這幾段文字記錄；`DataTable` 寫入的這些步驟也一樣。`DataTable` 寫入會把 insert、
update 與 delete 的範本一起記下，因為 data adapter 不會指出是哪一道失敗；是否逾時只依 provider 的訊息判斷。非同步呼叫端取消的
指令不記為 Error。寫入異常的 writer 丟出例外時，不再改變指令的結果。log 資料庫本身的存取仍不記錄，異常寫入不會遞迴。

### 前端比對共用語系 namespace 時不分大小寫

伺服端的語系快取以不分大小寫的方式存放 namespace，但前端的 `SnapshotLanguageService` 比對鍵時區分大小寫。表單欄位以兩種大小寫寫同一個共用
namespace 時（例如 `LangEnumName="common.Gender"` 與 `LangEnumName="Common.Status"`），前端只會以先遇到的大小寫抓一次該
namespace，寫成另一種大小寫的欄位在 Avalonia 與 Blazor 前端顯示未翻譯的選項值，也沒有任何錯誤。前端現在比對 namespace 與語系時
不分大小寫。傳給 `SnapshotLanguageService` 建構函式的快照不論原本用哪種比較方式，都會以這種方式複製；兩個鍵只差在大小寫時保留其中一個。

### Avalonia 明細表格自己捲動列

明細表格放在表單會捲動的本體裡，沒有高度上限，所以每一筆明細都會建出一列，而改到計算欄位的編輯會把全部列重建一次。2026-11-12
量測時，每次這類編輯在 50 列約 0.2 秒、200 列約 0.8 秒。`FormLayoutPresenter` 現在給每個明細表格 480 像素的最大高度（約十二列），
表格自己捲動列；每次編輯的成本與明細列數無關。由於表格會自己捲動，表格重建列時（這類編輯之後、在檢視與編輯之間切換時，或存檔、重新載入換掉
DataSet 時），會依物件參考或 `sys_rowid` 找回原本在畫面內的列與選取的列，捲回那裡並重新選取。表單重畫時（`FormView` 在載入、新增或存檔之後會重畫，
包括被伺服器拒絕的存檔），`FormLayoutPresenter` 也會對新建的表格這樣做。列高改變時（例如檢視與編輯之間），或畫面內有列被刪除時，位置可能偏移約一列。
`GridControl.AddRow` 會選取新列並捲到那裡。

### `Polhem.JsonRpc` 套件釘在單一版本

框架套件改為相依 `Polhem.JsonRpc` 套件的單一確切版本，不再用版本範圍。存取判定有一半在這些套件裡（action 名稱能呼叫到哪些方法、
payload filter、重放保護），新版本會改變框架的安全行為；用版本範圍時，還原會在 Polhem 沒有發版的情況下帶進新版。

參考 `Polhem.JsonRpc.AspNetCore` 的應用程式要用同一個版本，專案範本與入門指南都已改用：
`dotnet add package Polhem.JsonRpc.AspNetCore --version 1.2.0`。這些套件的修正要隨 Polhem 發版才會到達應用程式；直接參考較新的
版本會覆寫釘選，NuGet 會發出 NU1608 警告。`Polhem.Hosting`、`Polhem.Api.Server` 與 `Polhem.Web.Blazor.Server` 也補上了原本只
經由其他參考取得的套件宣告。

### 健檢的小型修正

- 初始化程式讀取設定、以及 repository 把自己的資料庫綁定到公司時，database id 的比對不分大小寫；設定中沒有的 id 會報錯，
  不再預設成 SQL Server。
- 在非 Development 環境開著 debug 模式時，啟動會記錄錯誤。
- 行程內的 client 初始化時不再改寫伺服器的 payload 設定。
- 存檔與欄位變更回應裡以欄位或資料表名稱為鍵的對照表，經過任一種 body codec 之後仍不分大小寫。
- ExecFunc 只會選中符合處理常式簽章的方法。
- Oracle 重建資料表時會跳脫表名中的引號。
- `SystemApiConnector.LogoutAsync` 遇到伺服器已結束的 session 視為已登出，不再丟出例外。

## 破壞性變更

### 多家公司可以共用公司資料庫

- **影響對象：** 有公司資料表的每個部署，以及擁有自己公司資料表 schema 的 host（`ft_*`，以及框架 `st_*` 公司資料表的副本）。
- **原本：** 公司之間只靠各自擁有一個資料庫來區隔；`CompanyDatabaseId` 相同的公司會看到、修改、刪除彼此的資料列。
- **現在：** `company` 表單 schema 的每張資料表都有 `sys_company_id`，唯一索引也以它開頭。表單 repository 會在新增的每一列
  蓋上 session 的公司，並把每次讀取、更新、刪除都限定在該公司；兩個公司表單之間的關聯 JOIN 也會比對公司。框架自己對公司
  資料庫的查詢（部門、員工、角色與授權、稽核規則）只讀取該公司的資料列。單一公司的資料庫也有這個欄位，只放一個值。
  `sys_company_id` 為空的資料列不屬於任何公司，任何公司都看不到。
- **遷移：**
  1. 在公司資料表的 schema 加上這個欄位：`db add-company-column`（可先加 `--dry-run`）會替缺少它的 schema 加上欄位與以它
     開頭的唯一索引。
  2. 執行 `db upgrade`。在 schema 仍缺少欄位、或公司代號不是儲存形式時，它會在任何變更之前停下；接著升級資料表，再把沒有
     公司的資料列指派給其資料庫所屬的唯一一家公司。多家公司共用的資料庫中的這類資料列會被列出，留給你自行指派。
  3. 以自己的 SQL 新增的資料列（例如角色授權）要帶 `sys_company_id`（見
     [權限與授權 §3](../security/permission-authorization.md#3-授權角色)）。
- **背景：** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md)、
  [資料庫設定 §5.5](../database/database-settings-guide.md#55-多家公司共用公司資料庫)

### repository 的手寫 SQL 綁定公司

- **影響對象：** 有自己 SQL 的客製 repository，以及自行建構 `DataFormRepository` 的程式。
- **原本：** repository 的 `CreateDbAccess()` 取得的存取可以對整個資料庫執行任何 statement。
- **現在：** 在綁定公司的 repository 中，`CreateDbAccess()` 綁定 session 的公司（`DbAccess.BindCompany`）。它執行的每個
  statement 都必須含有 `{@CompanyId}`（`CommandTextVariable.CompanyId`），執行時會變成帶著公司的參數；沒有它的 statement
  會在執行時被拒絕。這項檢查只看佔位符在不在，不檢查每張公司資料表是否都拿它比對。綁定的存取也會拒絕所有預存程序呼叫，
  因為預存程序無法帶這個佔位符，所以綁定公司的 repository 不再能在公司資料庫上呼叫預存程序。沒有 session 的程式以
  `CreateDbAccess(databaseId, companyId)` 明確綁定。POLHEM3004 analyzer 會報出以其他方式（context 的 `DbAccessFactory`、
  `IDbAccessFactory`、`new DbAccess(...)`）取得存取的 repository，因為那樣取得的存取不會綁定。`DataFormRepository`
  不接受在沒有公司的情況下為公司表單建構。
- **遷移：**
  1. 每個針對公司資料表的 statement，都要比對 `sys_company_id = {@CompanyId}`（statement 讀取的每張公司資料表都要，JOIN
     也算），新增資料列時把 `{@CompanyId}` 寫進該欄位。
  2. repository 中從 `IDbAccessFactory` 或 `new DbAccess(...)` 取得的存取，改用 `CreateDbAccess()`。
  3. 為公司表單建構 `DataFormRepository` 時，使用接受公司代號的建構子。
  4. 把對公司資料庫的預存程序呼叫，改成以 `{@CompanyId}` 指明公司的 statement。
- **背景：** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md)、
  [為 ProgId 客製 Repository](../guides/development-cookbook.md#為-progid-客製-repository)

### 公司資料庫的方法需要公司代號，公司代號改為小寫

- **影響對象：** `IDepartmentRepository.GetDepartments`、`IEmployeeRepository.GetByUserRowId`、
  `IRolePermissionRepository.GetRoleGrants` / `GetUserRoles`、`IAuditRuleRepository.GetRules` 與
  `IEmployeeContextResolver.Resolve` 的呼叫端與實作；公司代號含大寫字母或其他字元的部署。
- **原本：** 這些方法只接受資料庫代號，公司代號照輸入的樣子儲存。
- **現在：** 每個方法都另外接受公司代號，並依它過濾查詢。公司代號以小寫儲存，最多 `CompanyInfo.CompanyIdMaxLength` 個
  ASCII 英數字元（`CompanyInfo.NormalizeId`、`CompanyInfo.IsValidId`）。`EnterCompany` 接受任何大小寫，並把 session 綁定到
  儲存形式。
- **遷移：**
  1. 呼叫這些方法時傳入公司代號，自行實作的類別也加上這個參數。
  2. 執行 `db upgrade` 之前，把 `st_company` 與其他存放公司代號之處中、不是小寫英數字元的公司代號改名；`db upgrade` 會列出
     它們並停下。
- **背景：** [ADR-062](../../../maintainers/adr/adr-062-row-level-tenancy.md)

### `FormDataObject` 移至 `Polhem.UI.Core`

- **影響對象：** 在 Avalonia head 或 Blazor head 中指名 `FormDataObject`、`FieldValueChangedEventArgs` 或
  `RowChangedEventArgs` 的程式、自行建構 `FormDataObject` 的程式，以及繼承 Avalonia `FormDataObject` 的類別。
- **原本：** 兩個 head 各有一份：`Polhem.UI.Avalonia.DataObjects.FormDataObject` 接受 `IFormApiConnector`，
  `Polhem.Web.Blazor.DataObjects.FormDataObject` 接受 API client 的 `FormApiConnector`。新資料列日期所用的時區，
  Avalonia 那份取自 `UIServices.Provider` 中的 `IUserContext`，Blazor 那份取自其連接器的 client。
- **現在：** 只有一個型別 `Polhem.UI.Core.DataObjects.FormDataObject`，接受 `IFormApiConnector`，並可選擇傳入一個回傳
  登入使用者 IANA 時區 id 的函式。未傳入時，新資料列的日期預設為 UTC 的今天。`FormView`、`FormPage` 與關聯紀錄對話框
  都會傳入使用者時區，透過它們開啟的表單行為不變。這個型別是 sealed，與原本 Blazor 那份相同；原本 Avalonia 那份可被繼承。
  `FormLiveComputation` 仍留在各 head。
- **遷移：**
  1. 替換命名空間：

     | 原本 | 現在 |
     |------|------|
     | `Polhem.UI.Avalonia.DataObjects.FormDataObject` | `Polhem.UI.Core.DataObjects.FormDataObject` |
     | `Polhem.Web.Blazor.DataObjects.FormDataObject` | `Polhem.UI.Core.DataObjects.FormDataObject` |
     | `Polhem.UI.Avalonia.DataObjects.FieldValueChangedEventArgs` | `Polhem.UI.Core.DataObjects.FieldValueChangedEventArgs` |
     | `Polhem.Web.Blazor.DataObjects.FieldValueChangedEventArgs` | `Polhem.UI.Core.DataObjects.FieldValueChangedEventArgs` |
     | `Polhem.UI.Avalonia.DataObjects.RowChangedEventArgs` | `Polhem.UI.Core.DataObjects.RowChangedEventArgs` |
     | `Polhem.Web.Blazor.DataObjects.RowChangedEventArgs` | `Polhem.UI.Core.DataObjects.RowChangedEventArgs` |

     同時使用 `FormLiveComputation` 的程式，也要保留該 head 的 `DataObjects` 命名空間。
  2. 自行以連接器建構 `FormDataObject`、且新資料列應依使用者的日期預設時，傳入時區。在 Avalonia head：

     ```csharp
     var dataObject = new FormDataObject(schema, connector,
         () => UIServices.Get<IUserContext>()?.User?.TimeZone ?? string.Empty);
     ```

     在 Blazor 元件中，傳入 circuit 自己的時區，不可用整個 process 共用的：

     ```csharp
     var dataObject = new FormDataObject(schema, Client.Form(progId),
         () => Client.Session.Credentials.UserTimeZoneId);
     ```
  3. 繼承 Avalonia `FormDataObject` 的類別不再能編譯。改為持有一個 `FormDataObject` 並訂閱它的事件。
- **背景：** [ADR-054](../../../maintainers/adr/adr-054-front-end-decoupled-from-api-client.md) 的「Implementation evolution」。

### `IFieldEditor` 與 `GridEditMode` 移至 `Polhem.UI.Core`

- **影響對象：** 在 Avalonia 或 Blazor 應用中用到 `IFieldEditor` 或 `GridEditMode` 的程式：自訂的欄位編輯器、
  `where T : Control, IFieldEditor` 這類泛型限制，或在程式碼中設定 grid 的 `EditMode`。
- **之前：** 兩個 head 各宣告一份，除了命名空間完全相同：`Polhem.UI.Avalonia.Controls.Editors.IFieldEditor` 與
  `Polhem.UI.Avalonia.Controls.GridEditMode`，以及 `Polhem.Web.Blazor.Controls.Editors.IFieldEditor` 與
  `Polhem.Web.Blazor.Controls.GridEditMode`。
- **現在：** 各只有一份，位於 `Polhem.UI.Core.Editing`，兩個 head 都使用它。成員與列舉值都不變。
- **遷移方式：** 在用到這兩個型別的地方加上 `using Polhem.UI.Core.Editing;`（Razor 檔或 `_Imports.razor` 用
  `@using Polhem.UI.Core.Editing`）。只為這兩個型別而加的舊命名空間 `using` 可以移除。

### 一個請求只讀一次 session 的公司

- **影響對象：** 自行實作 `ICompanyAuthorizationService`、`IScopeResolver`、`IRepositoryDatabaseRouter`、
  `IBusinessObjectFactory` 或 `IRepositoryTypeResolver` 的 host；覆寫 `RepositoryFactory.CreateFormRepositoryCore`
  的 host；依賴「建構期間 session 進入另一家公司時，company-bound repository 會擲 `InvalidOperationException`」的程式；
  以及自行讀取 session 公司的 host business object 與 form plugin，或在呼叫結束後仍持有 business object 的程式。
- **原本：** 同一個請求裡，授權檢查、列範圍、資料庫路由、repository 蓋上的公司章與客製化，各自透過 access token 讀取
  session 的公司。可存取兩家公司的使用者在送出請求的同時讓同一個 token 在兩家公司間切換，一個請求就可能以某家公司的角色通過授權，
  接著讀寫另一家公司的資料。
- **現在：** business object 工廠每次呼叫只讀一次 session 的公司範圍，business object 把它保存為 `CompanyScope`。授權、
  列範圍、路由、repository 以及它呼叫的其他 business object 都使用這份快照。新增下列成員：

  | 型別 | 新增成員 |
  |------|----------|
  | `ICompanyAuthorizationService` | `Can(SessionCompanyScope, string, PermissionActions)` |
  | `IScopeResolver` | `ResolveFilter(SessionCompanyScope, string, PermissionActions, FormSchema)` |
  | `IRepositoryDatabaseRouter` | `Resolve(DbScope, SessionCompanyScope)` |
  | `IBusinessObjectFactory` | `CreateBusinessObject(Guid, string, bool, SessionCompanyScope)` |
  | `IRepositoryTypeResolver` | `Resolve(string customizeId, string progId)` |
  | `IRepositoryFactory` | `CreateFormRepository<T>(Guid, string, SessionCompanyScope)` |
  | `IRepositoryContext`、`IBusinessObjectContext` | `CompanyScope`（預設 `null`） |
  | `RepositoryFactory` | `CreateFormRepositoryCore(Guid, string, SessionCompanyScope)` |
  | `BusinessObject`、`FormBusinessPlugin` | `CompanyScope` |
  | `BusinessObjectFactoryExtensions` | 接受 `SessionCompanyScope` 的 `CreateFormBO` 與 `CreateSystemBO` 多載 |

  吃 access token 的多載仍保留，各自只讀一次 session。company-bound repository 的資料庫與公司取自同一次讀取，
  建構期間公司改變時不再擲出例外。
- **遷移：**
  1. 實作上述介面時補上新成員。吃 access token 的成員可以像框架的實作一樣，讀一次 session 後呼叫新成員。
  2. 覆寫 `CreateFormRepositoryCore(Guid, string)` 的 `RepositoryFactory` 子類，也要覆寫接受 `SessionCompanyScope`
     的多載；框架的 business object 經由它建立 repository。
  3. 自行撰寫的 business object 從 `CompanyScope` 讀取目前的公司，不要用 `SessionInfoService.Get(AccessToken)`；
     呼叫 `Can` 與 `ResolveFilter` 時傳入 `CompanyScope`，呼叫其他 business object 時也把它傳給 `CreateFormBO` /
     `CreateSystemBO`。form plugin 也以它自己的 `CompanyScope` 照做。
  4. 每次呼叫都建立新的 business object。呼叫結束後仍被持有的實例，在 session 離開公司、登出或過期後，
     仍會以原本的公司與角色運作。
- **背景：** [ADR-063](../../../maintainers/adr/adr-063-one-company-scope-per-request.md)

### 預設拒收 JSON-RPC 批次

- **影響對象：** 對 `AddPolhemFramework` 建立的伺服器，在一個請求中送出多個 JSON-RPC 呼叫的用戶端（陣列形式的 body，或
  `LocalApiProvider`、`RemoteApiProvider` 的 `SendBatchAsync`）。框架自己的用戶端與 polhem-connector-js 都不送批次。
- **之前：** 最多 100 個呼叫的批次會照常處理。以 HTTP 請求數計算的速率限制，讓一個請求可以帶 100 次匿名登入，每次都是完整的密碼金鑰衍生。
- **現在：** `PolhemJsonRpc.CreateServerOptions` 把 `MaxBatchSize` 設為 0，批次會以一個 invalid-request 錯誤回應。單一呼叫不受影響。
- **遷移方式：** 需要批次的主機在 `AddPolhemFramework` 之後設定大小，並讓速率限制把批次中的每個呼叫都算進去：

  ```csharp
  services.AddJsonRpcServer(server => server.MaxBatchSize = 20);
  ```
- **背景：** [帳號安全限制](../architecture/development-constraints.md#帳號安全限制)

### 登入拒絕長度超過帳號資料表的帳號

- **影響對象：** `SystemBusinessObject` 子類別覆寫 `AuthenticateUser`、改向其他地方（目錄服務、身分識別提供者）驗證，
  且帳號長度超過 20 個字元（例如電子郵件地址）的應用程式。
- **之前：** `Login` 會把任意長度的帳號交給鎖定計數、稽核與 `AuthenticateUser`。登入不需驗證身分，因此任意大小的帳號都會被當成
  鎖定計數的 key 保留數分鐘，並整段排入稽核佇列。
- **現在：** `Login` 會把長度超過新增的 `MaxLoginUserIdLength`（以 Unicode 字元計算）的帳號，或超過 1024 個字元的密碼，當成帳密
  錯誤拒絕，且在鎖定計數與 `AuthenticateUser` 之前就拒絕。這次登入失敗仍會寫入稽核，帳號截到該長度。預設上限是
  `UserInfo.UserIdMaxLength`，即 `st_user.sys_id` 的欄寬，資料庫初始化也改用它檢查。
- **遷移方式：** 驗證超過 20 個字元帳號的子類別，提高上限：

  ```csharp
  protected override int MaxLoginUserIdLength => 256;
  ```
- **背景：** [帳號安全限制](../architecture/development-constraints.md#帳號安全限制)

### 框架的 Department 與 Employee 表單需要權限授權

- **影響對象：** 使用框架 `Department` 或 `Employee` 表單的部署，以及所有會維護或查找部門、員工的角色。
- **之前：** 兩張表單都沒有宣告權限模型，公司內所有已登入使用者都能讀寫。`Dept` 與 `DeptAndSub` 記錄範圍讀的正是這些資料，
  所以使用者可以把自己的員工資料移到最上層部門，擴大自己在其他所有表單上的範圍。
- **現在：** 兩張表單宣告 `Department` 與 `Employee` 模型，這兩個模型隨框架的 `PermissionModels.xml` 提供。enforcement 為
  fail-closed：沒有授權的角色無法開啟、儲存或刪除這兩張表單，查找它們時也找不到資料，因為 `GetLookup` 會套用 `Read` 的記錄範圍。
  host 啟動時會對每個未受保護、寫入 `st_employee` 或 `st_department` 的表單記錄警告。
- **遷移方式：**
  1. `DefinePath` 已經有 `Department.FormSchema.xml` 與 `Employee.FormSchema.xml` 的部署會保留自己的副本，因為寫入框架預設定義時
     預設不會覆寫既有檔案（`MaterializeOptions.Overwrite`）。請在兩個檔案的根元素加上 `PermissionModelId="Department"` 與 `PermissionModelId="Employee"`。
  2. 在部署的 `PermissionModels.xml` 登記 `Department` 與 `Employee` 模型，動作與框架提供的檔案相同。在本版之前寫入過預設定義的部署
     都有自己的副本，這份副本不會自動加上新模型。
  3. 需要挑選部門或員工的角色授予 `Read`；`Create`、`Update`、`Delete` 只授予負責維護組織的角色。範圍請用 `All`：這兩張表單都沒有標記
     部門或擁有者欄位，所以這兩個模型上的 `Dept`、`DeptAndSub` 或 `Own` 授權不會放行任何資料：

     ```sql
     -- 每個動作一列：action 為 Create=1、Read=2、Update=4、Delete=8；scope 1 = All。
     INSERT INTO st_role_grant (sys_company_id, role_id, model_id, action, scope) VALUES
       ('acme', 'HrAdmin', 'Employee',   1, 1), ('acme', 'HrAdmin', 'Employee',   2, 1),
       ('acme', 'HrAdmin', 'Employee',   4, 1), ('acme', 'HrAdmin', 'Employee',   8, 1),
       ('acme', 'HrAdmin', 'Department', 1, 1), ('acme', 'HrAdmin', 'Department', 2, 1),
       ('acme', 'HrAdmin', 'Department', 4, 1), ('acme', 'HrAdmin', 'Department', 8, 1),
       ('acme', 'Clerk',   'Employee',   2, 1), ('acme', 'Clerk',   'Department', 2, 1);
     ```
- **背景：** [權限與授權 §4](../security/permission-authorization.md#4-連結使用者與員工部門-scope-需要)

### 繼承 `GridControlBase` 的 grid 改在 `Dispose(bool)` 釋放資源

- **影響對象：** 框架以外繼承 `GridControlBase`、並自行宣告 `DisposeAsync`（不論有沒有 `@implements IAsyncDisposable`）的
  grid 元件。MudBlazor 與 Fluent UI 的 grid 已經遷移。
- **之前：** `GridControlBase` 只實作 `IDisposable`。衍生 grid 若加上 `IAsyncDisposable`，就只經由它釋放，base 從未取消對
  data object 的訂閱。
- **現在：** `GridControlBase` 實作 `IAsyncDisposable`，它的 `DisposeAsync` 會取消訂閱並釋放 grid 的編輯器腳本。衍生類別的
  `DisposeAsync` 會隱藏它（警告 CS0108，在 `TreatWarningsAsErrors` 下是錯誤）；若又重新實作介面，外洩就會回來。
- **遷移方式：** 移除衍生類別的 `DisposeAsync` 與 `@implements IAsyncDisposable`，改在覆寫的 `Dispose(bool)` 釋放 grid 自己的
  資源，並呼叫 base：

  ```csharp
  protected override void Dispose(bool disposing)
  {
      if (disposing) _myResource.Dispose();
      base.Dispose(disposing);
  }
  ```

### `GridEditorCell` 改收資料列與欄位

- **影響對象：** 框架以外、自己放置 `GridEditorCell` 的 grid。MudBlazor 與 Fluent UI 的 grid 已經更新。
- **之前：** grid 傳入 `EditorParameters`（每次重繪都為每一格建立的字典），以及 `IsNumeric` 與 `IsCheck`。
- **現在：** 儲存格收 `Row` 與 `Column`。它從欄位的 `ControlType` 判斷是不是數值或勾選框，並只在持有編輯器時，透過
  `GridEditorHost` 的 `EditorParametersBuilder`（由 `GridControlBase` 設定）取得編輯器的參數。只有在它的文字、勾選狀態、
  編輯器型別、資料列、欄位或是否持有編輯器改變時才重繪。
- **遷移方式：** 把 `EditorParameters`、`IsNumeric` 與 `IsCheck` 換成 `Row="row"` 與 `Column="column"`。繼承
  `GridControlBase`、但原本傳入自己組的字典（例如多加一個編輯器參數）的 grid，要把 `EditorHost.EditorParametersBuilder`
  設成建立該字典的方法。不是繼承 `GridControlBase` 的 grid，要在它傳入的 `GridEditorHost` 上設定
  `EditorParametersBuilder`；host 沒有設定時，儲存格第一次渲染就會擲出例外。

### `DbAccess` 批次失敗時丟出原本的例外

- **影響對象：** 攔截 `DbAccess.ExecuteBatch` 或 `ExecuteBatchAsync` 例外的程式，或攔截會執行批次的框架呼叫的程式：表單刪除、
  稽核紀錄寫入與 `db seed-admin`。
- **之前：** 指令或 commit 失敗時會回滾，並包成 `InvalidOperationException`（「Failed to execute batch at index …」或
  「Failed to commit transaction.」），取消也一樣。表單刪除在資料庫失敗時，JSON-RPC 用戶端收到的是使用者訊息
  （「The request could not be completed.」）。
- **現在：** 批次回滾後原樣丟出例外，例如資料庫錯誤是 `DbException`，不支援的指令種類是 `NotSupportedException`。
  `ExecuteBatchAsync` 的 token 取消之後才到的 `DbException`，會改以帶著它的 `OperationCanceledException` 丟出，因為 SQL Server
  就是這樣回報被取消的指令。所有指令執行完之後，commit 不再受取消影響。失敗指令的位置放在
  例外的 `Data`，鍵為 `DbBatchSpec.FailedIndexDataKey`。表單刪除在資料庫失敗時，用戶端收到的是內部錯誤，與單道指令失敗時
  相同；兩者在非偵錯模式下都不會顯示資料庫的訊息。
- **遷移方式：** 改攔截失敗實際可能的型別（通常是 `DbException`），而不是 `InvalidOperationException`，並讓 `OperationCanceledException` 傳回發出取消的程式。
  失敗位置改從 `ex.Data[DbBatchSpec.FailedIndexDataKey]` 讀取，不要解析訊息。

### 只有框架自己使用的成員不再公開

- **影響對象：** 指名使用下列成員的程式；框架只在它們所屬的組件內使用它們。
- **之前：** 下列成員是公開的：
  - `Polhem.Web.Blazor.Components.BlazorDefinitions`，表單頁與對話框載入定義用的輔助類別。
  - `Polhem.Db.DbConnectionScope`，`DbAccess` 內部的連線生命週期。
  - `ApiSessionContext.NextSequence`，session 重放 frame 的序號。
  - `FieldEditorBase.BuildCssClass`，沒有任何編輯器呼叫它。
  - `FilterGroup.ShouldSerializeNodes` 與 `DepartmentNode.ShouldSerializeChildren`。
- **現在：** 前三項改為 internal，`BuildCssClass` 已移除。`FilterGroup.NodesSpecified` 與 `DepartmentNode.ChildrenSpecified`
  取代兩個 `ShouldSerialize` 方法，與其他定義型別一致；因此 JSON 與原本的 XML 一樣，省略空的 `nodes` 或 `children`。
  讀取端兩者都找不到時，得到的仍是空群組與葉節點，與之前相同。
- **遷移方式：** 資料庫呼叫改用 `DbAccess`，定義由表單頁自己載入，session 改用 `PolhemApiClient`。原本呼叫 `ShouldSerialize`
  方法的地方，改讀 `NodesSpecified` 或 `ChildrenSpecified`。

### 表單存檔會正規化時刻值，並拒絕不是時刻的值

- **影響對象：** 以 JSON-RPC API 儲存含 `Time` 欄位表單的客戶端（例如 JavaScript 客戶端），以及在 `DoBeforeSave` 或
  `BeforeSave` 寫入時刻值的自訂 business object 或 plugin。
- **之前：** 伺服器照收到的值存下時刻值。`8:30` 會存成 `8:30`，它排在 `10:00` 之後，也落在
  `BETWEEN '08:00' AND '17:00'` 之外；`noon` 之類的文字也照樣存入。以 `8:30` 過濾的清單找不到存成 `08:30` 的列。
- **現在：** 存檔時把新增與修改列的每個時刻值寫成 `HH:mm`，在 `DoBeforeSave` 之前與 plugin 之後各做一次。呼叫端
  送來的值若不是時刻（`25:00`、`noon`、`08:30:15`），以 `-32602 InvalidParams` 拒絕並指出欄位；伺服器端程式寫入的
  不合法值則擲出 `InvalidOperationException`。空字串仍代表沒有填寫。時刻欄位的過濾值以同樣方式轉換。不經過存檔的
  寫入（例如自寫 SQL）不會正規化。
- **遷移方式：** 送出 `HH:mm` 或 `H:mm`。這個版本之前存入的值不會被改寫。沒有改到它的存檔會保留它，但以 `8:30`
  過濾時，找不到存成 `8:30` 的列。[時間型別](../database/temporal-types.md)中的查詢可以找出它們，再以
  `ValueUtilities.CTimeString` 取得要寫回的儲存格式。

### session 過期的行程內呼叫會被拒絕

- **影響對象：** 以已登入使用者的存取權杖在行程內呼叫 API 的主機，主要是 Local 模式的 Blazor Server 網站，以及保留權杖、
  稍後再用它呼叫的伺服器端程式。
- **之前：** 行程內呼叫會略過存取權杖檢查，所以已過期的 session，只要行程內的 client 持續使用就一直有效。
- **現在：** 帶存取權杖、呼叫需要登入之方法的行程內呼叫，會與遠端呼叫一樣檢查，過期或不存在的 session 以
  `-32001 Unauthorized` 拒絕。保護等級與 `LocalOnly` 限制仍會略過；不帶權杖的行程內呼叫（伺服器自己的程式）
  與之前一樣受信任。以 client 目前的 session 發出的呼叫被這樣拒絕時，client 會觸發 `PolhemApiClient.SessionRejected`，
  Blazor shell 隨之登出並回到登入畫面。`SystemApiConnector.LogoutAsync` 遇到伺服器已結束的 session 視為已登出，
  直接返回而不丟出例外。
- **遷移方式：** 以 Blazor shell 建置的網站不需要處理。其他前端在呼叫被以未授權拒絕時重新登入，與遠端客戶端相同，
  可以監聽 `SessionRejected` 集中處理；伺服器端程式自行執行的呼叫不要帶權杖。

### 沒有用到的成員已移除，授權判定物件建立後不能再修改

- **影響對象：** 指名使用下列成員的程式，或在授權判定物件建立後修改它的程式。
- **之前：**
  - `ClientInfo.CreateFormApiConnector` 與 `ClientInfo.CreateAuditLogApiConnector` 轉交 client 的 connector。
  - `ApiHeaders.ContentType` 與 `FieldMappingCollection.FindByDestination` 是公開的，但沒有任何程式使用。
  - `FormPluginChain.TypesForStage` 是為了一個從未做出來的維護工具而公開。
  - `CacheInfo.NotifyVersions`、`SaveContext.AffectedRows`，以及 `ApiAuthorizationResult` 與 `ApiCallContext` 的屬性都有公開的
    setter；`SessionCompanyBinding.Capabilities` 是 `Dictionary`。
- **現在：**
  - 兩個 `ClientInfo` 方法、`ApiHeaders.ContentType` 與 `FindByDestination` 已移除。
  - `TypesForStage` 改為 internal。
  - `CacheInfo.NotifyVersions` 與 `SaveContext.AffectedRows` 只能讀取；`DoSave` 改為填入字典，不再整個替換。
  - `ApiAuthorizationResult` 與 `ApiCallContext` 只在建立時給值（`init`），filter 或替換的 validator 無法在判定後把拒絕改成成功。
  - `SessionCompanyBinding.Capabilities` 改為 `IReadOnlyDictionary`。
- **遷移方式：**
  - 改呼叫 `ClientInfo.ApiClient.Form(progId)` 與 `ClientInfo.ApiClient.AuditLog`。
  - 原本用 `ApiHeaders.ContentType` 的地方直接寫標頭名稱 `"Content-Type"`；以 LINQ 搜尋 `FieldMappingCollection`。
  - 覆寫 `DoSave` 且不呼叫 base 的程式，把筆數加進 `context.AffectedRows`，不要指派新的字典。
  - 以 `Success` 或 `Fail` 建立 `ApiAuthorizationResult`；以建構子或物件初始設定式建立 `ApiCallContext`。

### 經由 JSON body codec 傳遞的 `DateTime` 以 UTC 時間點送達

- **影響對象：** 經由 JSON body codec 交換 `DateTime` 值的用戶端與伺服器：篩選值、參數值與訊息的 `DateTime` 屬性。
  `DataTable` 儲存格、MessagePack 與 Plain 格式都不變。
- **之前：** MessagePack 把 `DateTime` 當成絕對時間點傳遞（`Local` 值以寫入端的時區換算成 UTC，`Unspecified` 值視為 UTC，
  送達時一律是 `Utc`），JSON body codec 則保留原本的 kind。同一個請求經由 JSON 送達的是 `Unspecified` 值、經由 MessagePack
  送達的卻是 `Utc` 值；`Local` 值則以讀取端自己的時區讀回。
- **現在：** JSON body codec 套用與 MessagePack 相同的規則：寫出 UTC 時間點，沒有時差的值讀成 UTC。原本就是 UTC 的值寫出內容
  與過去完全相同，polhem-connector-js 送出的正是這種值。伺服器讀回時 kind 為 `Unspecified` 的訊息屬性（例如 session 或
  API key 的 `expiredAt`）會帶 `Z` 寫出，把它交給 `new Date()` 的 JavaScript 用戶端會讀到正確的時間點。
  `wire-fixtures/bodies/value-datetime.json` 呈現新的格式。
- **遷移方式：** 送出不帶時差、意指當地時間之值的 JSON 用戶端，改送 UTC 或帶時差的值；直接顯示這類回應字串的用戶端會看到
  `Z`。`DataTable` 儲存格仍保留由用戶端 connector 換算的未帶時區值，如 ADR-032 所述。

### `ICompanyRepository` 新增 `GetCompanyDatabases`

- **影響對象：** 自行實作 `ICompanyRepository` 的 host，以及 repository 工廠不是衍生自 `RepositoryFactory` 的 host。
- **之前：** `db seed` 與 `db upgrade` 指令在 `Polhem.Hosting` 組 SQL。
- **現在：** 改經由框架 repository 寫入。第一位管理員、公司與存取權由新的 `IAdministratorSeedRepository` 寫入；升級時要指派給
  公司的列，由 `ICompanyRowAssignmentRepository` 找出並指派；兩者都經由 `IRepositoryFactory.Create<T>` 建立。
  `ICompanyRepository` 新增 `GetCompanyDatabases`，列出一個 common 資料庫中的每家公司與其資料庫項目。種子資料改經由路由器的
  `Common` 範圍抵達 common 資料庫，不再直接使用名為 `common` 的項目，因此替換過的路由器會決定寫到哪裡。使用框架自己的
  repository 工廠與路由器時，指令行為不變。
- **遷移方式：**
  1. 自行實作 `ICompanyRepository` 的 host 要補上 `GetCompanyDatabases`。
  2. repository 工廠不是衍生自 `RepositoryFactory` 的 host，要在 `Create<T>` 中建立 `IAdministratorSeedRepository` 與
     `ICompanyRowAssignmentRepository`；少了它們，`db seed-admin` 與 `db upgrade` 會失敗，並指出缺少哪一個 repository。
- **背景：** [ADR-046](../../../maintainers/adr/adr-046-api-evolution-policies-for-1-0.md) 允許 repository 合約在 minor 版
  新增成員；實作者應衍生自框架的實作。
