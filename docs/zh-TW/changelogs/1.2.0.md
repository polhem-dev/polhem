# Polhem 1.2.0 — 詳細發佈說明

[English](../../en/changelogs/1.2.0.md)

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.2.0]` 條目的詳細版。變更記錄每項變更只列一行；原因與背景
留在這裡。

> JSON-RPC 改建在 [`Polhem.JsonRpc`](https://github.com/polhem-dev/polhem-jsonrpc) 套件上，payload 外殼改建在它的選用
> payload 套件上。決策、考慮過的替代方案與完整的遷移步驟記錄在
> [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md)（英文）。

## 為什麼把協定移出去

到 1.1.0 為止，Polhem 自帶一份 JSON-RPC 2.0 實作：`Polhem.Api.Core` 的 executor 與它的訊息型別、`Polhem.Api.AspNetCore`
的 controller，以及 `Polhem.Api.Client` 的兩個用戶端 provider。這些都不是 Polhem 特有的。Polhem 特有的部分疊在它上面：
API key 與 access token 檢查、方法層級的存取控制、錯誤合約、異常紀錄，以及 payload 外殼背後的 session 金鑰與線路型別。

協定這一半現在是獨立維護的套件，它們對 Polhem 一無所知，不用 Polhem 也能使用。Polhem 透過它們的擴充點掛上自己的行為，
集中在 `Polhem.Api.Core.Dispatch`。payload 外殼、加密與重放 frame 也基於同樣的理由跟著移出：它們本身就是一套協定，
[polhem-connector-js](https://github.com/polhem-dev/polhem-connector-js) 也在使用，因此現在放在
`Polhem.JsonRpc.Payload` 與 `Polhem.JsonRpc.Payload.Server`。

## 為什麼在次版號做破壞性變更

協定移出後，`ApiServiceController` 除了呼叫端點之外已無事可做；`ApiServiceOptions` 則成了第二套設定介面，必須和 payload
套件的選項保持一致。保留任何一個，就會有兩種提供 API 的方式、兩種設定 payload 的方式，之後每次修改都得讓兩邊同步。
本版把兩者都移除，這會讓 host 編譯失敗。

[ADR-048](../../../maintainers/adr/adr-048-rename-base-to-core-in-1-1.md)（英文）說 1.1.0 的改名是 1.x 內唯一一次違反語意化
版本的例外。ADR-049 是第二次，並規定 1.x 內往後的破壞性變更都需要自己的 ADR。同一份 ADR 也列出了**框架管線型別**：只為了讓
`Polhem.*` 套件彼此協作而公開的型別，例如 `Polhem.Api.Core.Dispatch` 裡的所有型別。它們的變更不算破壞性變更，
因此應用程式不應建立在它們之上。

## 破壞性 API 變更

- 移除 `Polhem.Api.AspNetCore` 套件，連同 `ApiServiceController` 與 `UsePolhemFramework()`。host 改用
  `Polhem.JsonRpc.AspNetCore` 提供 API：`AddJsonRpcServer()` 與 `MapJsonRpc("/api")`。覆寫過 controller 成員的檢查改寫成
  filter。`UsePolhemFramework()` 原本執行的啟動檢查移到 `AddPolhemApiKeyGateCheck()`；它需要自行加入，因為 in-process 的
  host 沒有需要 API key 保護的 HTTP 端點。([#46](https://github.com/polhem-dev/polhem/pull/46))
- 移除 `IJsonRpcProvider`、`JsonRpcExecutor` 與 `Polhem.Api.Core.JsonRpc` 的訊息型別。provider 改實作套件的
  `IJsonRpcTransport`。([#46](https://github.com/polhem-dev/polhem/pull/46))
- 移除 `ApiServiceOptions`，連同 payload transformer 與它的 serializer、壓縮器、加密器型別、外殼型別及重放相關型別。
  伺服器以 `AddPolhemPayload()` 註冊 payload 選項，.NET 用戶端把它放在 `ApiClientInfo.PayloadOptions`；`PolhemPayload`
  以框架的方式組出這些選項。codec、重放紀錄與 frame 設定移到套件的 `PayloadOptions`，`IApiAuthorizationValidator`
  改從 service collection 取得。([#47](https://github.com/polhem-dev/polhem/pull/47))

host 的升級方式列在變更記錄裡。所有步驟，包括多數 host 用不到的（自訂 codec、共用的重放紀錄、同一行程也呼叫 API 的
host），見 [ADR-049](../../../maintainers/adr/adr-049-jsonrpc-packages-in-1-2.md)（英文）的決策 3 與決策 5。

## 行為變更

- **線路。** 參數與結果外殼的位元組與 1.1.0 相同，wire fixtures 沒有變動。原本屬於 Polhem 自己的兩處改為符合 JSON-RPC 2.0：
  內部錯誤改回規格為它定義的錯誤碼 -32603，不再是 -32000；回應不再以 `method` 成員回傳方法名稱。比對 -32000 或讀取
  `method` 的用戶端要和伺服器一起升級；polhem-connector-js 對應的是以 1.2.0 為目標的版本。
  ([#46](https://github.com/polhem-dev/polhem/pull/46))
- **被拒的憑證。** API key 或 `Authorization` header 被拒時，回 HTTP 200 與 JSON-RPC 錯誤，不再回 401。檢查現在在建立
  business object 之前、於 JSON-RPC 管線內執行，所以它的失敗和其他失敗一樣回報，.NET 用戶端丟出的是錯誤合約重建的例外，
  而不是 `HttpRequestException`。([#46](https://github.com/polhem-dev/polhem/pull/46))
- **方法名稱。** 格式錯誤的方法名稱依規格回 `MethodNotFound`，不再回使用者訊息。不存在的 action 由 dispatcher 直接以固定訊息
  回應，debug 模式也一樣，且不寫異常紀錄。([#46](https://github.com/polhem-dev/polhem/pull/46))
- **in-process 呼叫**與遠端呼叫一樣會序列化參數，所以伺服器永遠不會持有呼叫端的物件。`Plain` 本文裡的篩選值會以文字送達，
  和過去經由 HTTP 時一樣。([#46](https://github.com/polhem-dev/polhem/pull/46))
- **payload 格式。** `format` 不是 0、1 或 2 的外殼以無效參數拒絕，過去會先被接受，到後面才失敗。
  ([#47](https://github.com/polhem-dev/polhem/pull/47))
- **log category** 改為寫出 log 的型別：被遮蔽的失敗記在 `Polhem.Api.Core.Dispatch.PolhemExceptionMapper`，API key 啟動檢查
  記在 `Polhem.Hosting.ApiKeys.ApiKeyGateWarningService`。依舊 category 過濾的 log 設定要改用新名稱。
  ([#46](https://github.com/polhem-dev/polhem/pull/46))
